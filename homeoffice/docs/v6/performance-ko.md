# 실측 성능과 남은 비용

[원시 수치](../../evidence/v6/performance.json). Windows 한 대에서 실제 Chromium/WebGL을 여러 프로세스로 실행했다. 독립된 네 PC의 성능으로 일반화하지 않는다. 기본 장치 감지로 저사양 설정이 선택되었다. p95는 Godot 실제 프레임 간격 최근 240개 표본이며 단순 1000/fps를 p95라고 부르지 않았다. Web staticMemory=0은 측정 불가로 취급한다.

| 조건 | 그래픽 | 작업대 열림 | fps | p95 ms | draw |
|---|---|---|---:|---:|---:|
| 4브라우저 / 1 | low | True | 12 | 83.6 | 500 |
| 4브라우저 / 2 | low | True | 43 | 29.2 | 0 |
| 4브라우저 / 3 | low | True | 41 | 27.1 | 0 |
| 4브라우저 / 4 | low | False | 15 | 90.4 | 490 |
| 캠퍼스 1브라우저 최종 | low | False | 20 | 55.3 | 259 |

수리 전 네 브라우저 회의는 8–11fps였다. 층별/재질별 메시 병합과 외피·내부 분리, 멀리 있는 층·문·가구의 시각 갱신 제한, 기존 설비 145→13 노드 병합을 수행했다. 문서 작업대가 화면을 덮는 동안 해당 클라이언트의 3D만 숨겨 시뮬레이션·문서 동기화는 유지했다. 위 스냅샷 중 편집 창이 열린 두 클라이언트는 draw 0 / 41–43fps였다. 패널 전환 직후 표본은 이전 상태를 포함하므로 이를 통제된 네 클라이언트 편집 평균이라고 주장하지 않는다.

보행 렌더 비용과 결합 부하는 아직 품질 미달이다. 전체 층 자산을 PCK에 포함하고 있어 실제 자산 스트리밍, baked lightmap/LOD, 2/4/8인 음성·자막·자료·승강기·CCTV 동시 측정이 남아 있다. 테스트 성공 개수나 줄어든 draw만으로 성능 완료를 선언하지 않는다.
