## 0. 이번 작업을 해석하는 가장 중요한 규칙

사용자가 말한 불편을 코드로 반박하여 지우지 마라. **사용자 경험, 코드 사실, 원인 가설, 설계 제안, 실제 검증 결과를 서로 다른 기록으로 유지하라.** 예를 들어 제작 파일에 책상 다리가 있어도 사용자는 다리가 없는 것처럼 보이는 책상을 경험할 수 있다. 그 경험을 지우지 말고 무엇이 그렇게 보이게 했는지 끝까지 조사하라.

이번에 만드는 것은 단순한 3D 편집기, 이름표만 있는 큰 건물, 교육용 퀴즈 앱, 예쁜 단일 렌더가 아니다. 친구들이 자기 캐릭터로 움직이고, 실제로 함께 문서를 만들고, 생활·게임·회의를 하고, 저장한 공간을 다시 여는 하나의 작동하는 장소다.

원래 엔진과 정상 기능은 보존한다. 건물의 잘못된 동선·미술·접촉·코드 구조는 필요하면 재설계한다. 기존 세계를 작은 기본 시제품으로 교체하거나 기존 요구를 '추후 확장'으로 조용히 밀어내지 마라. 단계는 나눌 수 있지만 전체 완료 기준을 줄이지 마라.

첨부 이미지가 최신 **시각적 기준**이다. 이전의 '사실적·현실적' 요구는 앞으로도 실제 동선·구조·접촉·조작·협업의 개연성을 뜻한다. 외형은 차가운 초실사 오피스가 아니라 **따뜻한 고급 수공예 미니어처/디테일한 디오라마**로 바꾼다. 귀여운 외형은 저품질·저기능의 허가가 아니다.

이 문서의 6층 계획, 치수, 시간·용량·성능 예산은 사용자의 예시를 바탕으로 구체화한 **설계 기본안**이다. 사용자가 처음부터 지정한 수치나 실제 건축 법규라고 말하지 마라.

## 1. 현재 기준과 조사 범위 — main과 실제 배포를 혼동하지 마라

이번 연결 도구 조회에서 `main`은 `27dccb8adeccb51690a5f5c4abbebebf339b850c`, 실제 Pages 배포 브랜치 `codex/homeoffice-v3`는 `7cab26a28db6df949378b6a4ac9e470661b36c7b`였다. 최근 Pages run `35353153450`은 후자 커밋의 성공으로 반환되었다. 같은 저장소여도 default branch만 읽으면 최신 공개 앱의 V5 수리를 놓칠 수 있다.

배포 브랜치의 TASK_STATE.md는 Build ID `9fa65de6-20d0-4a7a-b315-f3b388891e24`, V5 수리와 필수 잔여 작업을 기록한다. 이 기록은 원 개발 환경의 보고이며 본 프롬프트 작성자가 모든 시험을 재실행한 결과가 아니다. 현재 task 문서는 완전한 회의, 외부 두 계정 원본 편집, 마이크/방송, 전체 건물 적용 등의 미완료를 명시한다.

실제 조회한 `homeoffice/package.json`에는 Quill, y-quill, Yjs 등이 있고 `homeoffice/web/document-registry.mjs`에는 Google Docs/Slides/Excel 원본 등록·별도 창 열기가 있다. 따라서 '협업 코드가 전혀 없다'고 시작하지 마라. 하지만 의존성·링크·버튼의 존재는 원활한 공동작업을 입증하지 않는다.

본 프롬프트 작성 환경에서는 공개 사이트를 열려는 웹 요청이 실패했고 별도 HTTP 요청도 DNS 해결에 실패했다. 현재 앱을 직접 플레이하거나 최신 화면·마이크를 실증한 것으로 표시하지 않았다. 이번에는 새 배포 아티팩트의 해시 전수 검증도 수행하지 않았다. 사용자 제공 이미지 3장은 직접 확인 가능한 미술 참고 자료다.

구현자는 시작 때 현재 HEAD, Pages ref, Build ID, source digest, export preset, Godot/템플릿/Blender 버전을 다시 확인한다. 근거가 바뀌면 기록을 추가하되 과거 사용자 관찰을 삭제하지 마라. 테스트/분석할 커밋과 실제 사용 중인 앱의 버전을 맞추고 캐시·소스/배포 불일치를 따로 검사한다.

## 2. 사용자 불편 기록은 독립적이며 삭제할 수 없다

`USER_OBSERVATIONS.md`에 아래 원칙과 이번 문서 말미의 초기 기록을 넣는다.

- 원문 quote는 그대로 보존하고, 해석/개발 설명은 별도 칸에 쓴다. 오탈자나 감정 표현을 정리한 문장을 원문처럼 바꾸지 않는다.
- 코드 사실과 다를 때 상태를 '사용자 오류'로 닫지 않는다. 예: 코드상 다리 있음 / 실제 사용자 화면에서는 다리가 없어 보임 / 원인 재현 대기.
- UI, 조작, 네트워크, 특정 체형, 카메라 각도, 조명, 배포·캐시, 다른 objectId 등 재현 환경을 추적한다.
- 상태는 기록됨 → 재현 중 → 원인 확인/가설 → 수정 중 → 개발 재검증 통과 → 사용자 재확인 대기로 나눈다. 사용자 확인 전 '사용자가 만족했다'고 쓰지 않는다.
- 사용자 피드백이 아직 없어도 다음 개발은 진행한다. 다만 미술과 사용감의 최종 사용자 확인을 자동 테스트 점수로 대체하지 않는다.
- 이전 사용자 증상도 유지한다: 상대방 안 보임, 책상 지지대, 멀리 떨어진 화장실, 계단 위치, 다리 떨림, 소파/의자 겹침, 레이저와 실제 협업, 불안정한 농구/축구, 사격 품질, 딱딱한 디자인.
- 새 요구와 기존 결함을 섞지 않는다. '엘리베이터 추가'는 신규 요구, '회의 공동작업에 무리가 있음'은 현재 경험 문제다.

기록 필드: id / 사용자 원문 / 관찰 시점·버전(모르면 미확인) / 시도한 행동 / 불편 결과 / 기대 경험 / 관련 이미지·영상 / 코드 사실 / 가설 / 재현 절차 / 수정 / 회귀 증거 / 현재 상태.

## 3. 기존 환경·비용·권한 보존

Godot/GDScript와 Jolt 및 검증된 웹 export를 유지한다. 현재 기록은 Godot 4.6.1이다. 다른 렌더러가 더 멋져 보인다는 이유로 웹 호환을 없애지 않는다. 기능 지원은 설치된 엔진 버전의 문서로 확인하고 latest 문서의 미출시 기능을 전제하지 마라.

BlenderMCP는 제작용이고 사용자가 포트 9876 연결을 알려 주었다. 실제 scene 조회 등으로 연결을 확인한다. 원본 scene/컬렉션/GLB와 사용자 남자 캐릭터를 보존한다. 원본이 있으면 또 업로드를 요구하지 않고, 필요한 원본을 확인하지 못한 경우에만 요청한다. 배포된 브라우저가 9876에 접근하게 만들지 않는다.

GitHub 학생 Pro, 기존 Firebase Blaze와 비용 보호, Clerk 연결과 관리자 검증 경로를 임의로 삭제·교체·완화하지 않는다. 익명/게임 세션 사용자, simulation host, 실제 administrator는 서로 다르다. 먼저 들어온 학생이 관리자 권한을 얻으면 안 된다.

추가 운영 비용 0원을 기본 목표로 한다. 새 플러그인·API가 반드시 무료라고 가정하지 않는다. 서비스 생성, 결제/크레딧 사용, 운영 키 발급/권한 변경, 외부 서비스로 비공개 자료 전송은 승인된 범위를 확인한다. 설정이 없으면 로컬/모의 시험은 진행하고 운영 미연결은 명확히 표시한다.

API 키를 '찾는다'는 것은 공식 문서의 발급·설정 방법과 사용자가 소유한 합법적인 연결을 확인한다는 뜻이다. 인터넷의 유출 키나 타인의 키를 찾거나 사용하지 마라. 비밀키를 공개 Git, 프런트 env, Godot PCK, 소스맵, 문서, 로그, 저장 파일에 넣지 마라. 이 프롬프트에는 실제 관리자 PIN을 넣지 않는다.

낮은 층수의 크림색 건물, 따뜻한 목재 창틀과 차양, 안쪽 활동이 보이는 넓은 창, 노란 실내 조명, 둥근 사람과 수목, 타일 보도와 가로등의 작은 생활 장면이 핵심이다. 카페 간판이나 특정 인물/동물을 복제하라는 뜻은 아니다.

초록빛 정류장 지붕, 줄무늬 차양, 화분과 꽃, 사람들이 머무는 자리를 구체화한 벤치·보도 경계가 핵심이다. 부드러운 점토/펠트처럼 보이는 재질과 따뜻한 생활 밀도를 차용한다. 버스 운전·교통 시뮬레이터를 자동으로 신규 필수 기능으로 추가하지 않는다.

### R3 — reference_03_city.jpg (원래 파일 Sims.jpg)

가로 블록, 낮은 건물들의 서로 다른 외관, 도로/보도/횡단보도, 나무, 스포츠 공간을 읽기 쉽게 배치한 도시 모형의 조직을 참고한다. 파일 이름만으로 특정 게임의 실제 스크린샷이라고 단정하지 않는다. 앞의 두 장보다 선명한 조감 구조를 동선·지도·캠퍼스 배치에 활용한다.

### 최종 합성 방향

R1/R2의 따뜻한 근접 미술 + R3의 읽기 쉬운 거리/캠퍼스 구조를 결합한다. 이름은 작업 용어로 **Warm Crafted Campus**를 사용한다. 스타일 지정은 작업 지침이지 검증된 상표나 특정 렌더 기술 명칭이 아니다.

- 대부분 무광·반무광. 점토/도자기/나무/직물의 미세한 차이를 주되, 전체가 젤리·젖은 플라스틱·거친 돌처럼 보이지 않게 한다.
- 벽·창·가구 모서리에 실제 두께와 작은 둥근 모서리. 접히는 문·다리·피벗·받침 구조는 기능에 맞게 유지한다. 둥글게 만들다 충돌체가 문을 막으면 안 된다.
- 나무는 완벽한 구 하나가 아니라 크기가 다른 둥근 수관 묶음과 가지/줄기, 관목·화분·꽃의 조합. 단순히 고폴리 잎을 무한히 늘리지 않는다.
- 큰 면, 중간 구조, 작은 생활 소품의 비례를 구분한다. 건물 높이가 늘어도 1–2층 가로 입면, 차양, 코너 카페, 식재, 셋백을 이용해 압도적이고 차가운 타워가 되지 않게 한다.
- 실내 따뜻한 빛과 창밖의 부드러운 환경광을 결합한다. 화면·문서는 중립적인 색과 충분한 명암을 유지한다. 모든 방을 노란색으로 물들이지 않는다.
- 참고 사진의 강한 얕은 심도/틸트시프트는 입장 미리보기·선택적 사진 모드에서만 검토한다. 실제 이동·회의·문서·스포츠 중에는 깊이 흐림과 모션블러로 가독성을 떨어뜨리지 않는다.
- 기본 물리 단위는 1 unit = 1 m를 유지한다. 미니어처 '인상'을 위해 물리 세계를 수백 배 축소하지 않는다. 실제 1/3인칭 플레이와 선택적 조감 보기의 역할을 구분한다.
- 사용자 남자 GLB를 갑자기 다른 캐릭터로 대체하지 않는다. 우선 재질·의상·머리카락의 미술을 통일한다. 머리/몸 비례를 크게 바꾸려면 미리보기와 호환성·기존 사용자 의도를 확인하고 파생본으로 작업한다.

## 5. 외부 도구·에셋·API의 실제 활용 전략

도구를 더 많이 연결하는 것 자체를 성과로 삼지 마라. 대상 결함을 어떤 도구로 줄일지 명시하고, 작은 실제 테스트 asset으로 Blender→GLB→Godot 웹 화면을 먼저 통과시킨다.

### 5.1 기본 경로: BlenderMCP + Blender의 제작 기능

건축 모듈, 엘리베이터, 의자·소파, 그립·좌석·충돌 기준은 Blender에서 직접 관리한다. Geometry Nodes/Python으로 반복 창, 보도, 수관, 모듈형 벽을 만들 수 있다. procedural material과 반복 인스턴스는 웹 런타임에 실제로 반영되는 표준 재질·mesh·texture로 내보내거나 bake한다. Blender 노드가 glTF에 그대로 따라간다고 가정하지 않는다.

### 5.2 무료 에셋 우선: Poly Haven

공식 라이선스에서 CC0를 확인한 모델·HDRI·재질을 제작 재료로 사용할 수 있다. 2026-09-19 조회한 공식 API 설명은 기본 엔드포인트에 로그인/API 키가 필요 없고 라이브 API에 출처 표시와 고유 User-Agent를 요구한다. 과거 API 유료 정책을 현재 조건으로 잘못 재사용하지 말고 실제 구현 시 재확인한다.

API 수집은 제작용 Python/Node 쪽에서 캐시·호출 제한·해시·라이선스 manifest와 함께 한다. 모든 플레이어가 실행 때마다 API를 호출하게 하지 않는다. 내려받은 재료는 현재 미술 팔레트에 맞춰 재작업하고, 저작권과 서비스 이용 조건을 구분한다.

### 5.3 Blendkit(이전 명칭 BlenderKit)

무료 범위의 가구/재질을 후보로 비교할 수 있다. 무료 add-on과 모든 asset의 무료/재배포 가능 여부는 다르다. CC0와 Royalty Free를 개별 확인한다. 특히 이 프로젝트는 공개 저장소에 GLB 원본이 들어갈 수 있으므로 '게임에 넣을 수 있다'를 '소스 형태로 누구에게나 재배포 가능하다'로 바꾸지 않는다. 원본 공개 배포가 불명확한 asset은 쓰지 않거나 별도 허가를 확보한다. 난독화나 PCK 압축만으로 라이선스를 해결했다고 하지 마라.

### 5.4 선택적인 생성 서비스

ChatGPT 플러그인 디렉터리에서 to3D, fal 등의 3D 후보가 조회되었다. 현재 연결/유료 여부를 이 문서가 보장하지 않으며 이번 대화에서 설치·생성 호출하지 않았다. to3D의 소개는 단순한 glTF 변환에 가깝다. 상세 실내/리깅/피벗이 자동 완성된다고 취급하지 않는다.

정말 필요한 경우에만 공식 가격·권한·입력 자료 처리·반환 라이선스를 비교하고 사용자 승인 후 사용한다. 생성 결과는 topology, UV, 축·단위, 숨은 면, 재질, 관통, polycount, animation/rig를 검사한다. 건물의 겉모습이 생성되었다고 내부·엘리베이터·가구가 작동한다고 간주하지 않는다. 외부 서비스가 없어도 기본 경로로 계속 구현 가능해야 한다.

`ASSET_REGISTRY` 필드: assetId, 출처, 저작자/라이선스, 무료/지불 여부, 공개 원본 배포 가능 여부, 원본·수정본, hash, 크기, 삼각형/재질/texture 수, 기준 단위, 충돌체, pivot, 기능 anchor, LOD, 검수 장면.

## 6. 사용자가 제공한 일반 회사 층별 예시를 선별하라

사용자의 예시는 저층 공용/방문, 중층 업무, 고층 관리, 옥상 휴게로 나눈 참고안이다. 모든 회사가 이 순서로 배치된다거나 HR/법무/재무가 반드시 높은 층에 있어야 한다는 사실로 인용하지 않는다. 우리 제품의 실제 필요와 이미 요청한 기능을 기준으로 **채택·통합·이동·미채택**을 명시한다.

채택: 안내 데스크, 방문자 접견, 큰/작은 회의실, 세미나·프로젝트 설명 공간, 팀별 업무실, 층별 탕비/화장실/휴게, 조용한 폰부스, 관리자실, 관리 회의실, 옥상정원, 주차/전기·기계/수납 지원, 엘리베이터·계단·실내 CCTV.

통합: 마케팅·영업·개발·디자인이라는 경직된 부서는 프로젝트별 스튜디오로 재해석하되 예시 이름은 바꿔 쓸 수 있다. HR/재무/법무/전략·CEO 영역은 이 규모에 불필요하게 각각 한 층을 주지 않고 5층 관리자/운영/프로젝트 관리로 합친다. 실제 인사·급여·금융 서비스와 개인정보 수집은 만들지 않는다. 구내식당과 매점은 생활 기능과 연결되는 1층 카페·스낵과 6층 공용 식사/휴게로 분담한다. 체력단련은 기존 관리자 전용 SPORTS 별동과 연결한다.

미채택/보류를 공개적으로 기록: 여러 지하층의 대형 주차 타워, 실제 은행 ATM/결제, 법무·급여 시스템, 흡연 기능은 핵심 협업/생활에 필요하지 않으므로 기본 범위에서 제외한다. 옥상 휴게를 없애는 것이 아니라 비흡연 정원/휴식으로 구성한다. ATM 외형 소품이나 차량 운전/버스 NPC는 필요성 확인 후 별도 확장이지 기본 완료를 지연시킬 의무가 아니다.

교육장/세미나룸은 다목적 발표·워크숍 공간으로 구성한다. 입장 하단의 교육용 문구 때문에 과제·퀴즈·진도·점수·학습 강제 시스템을 만들지 않는다.

## 7. 제안하는 완성 규모 — OFFICE B1 + 1F~6F + RF

업무동은 **지하 1층 + 지상 6층 + 옥상**을 기본 설계안으로 한다. 기존 2층에서 약 네 개의 업무 층을 늘리는 규모다. 주거동은 별도 **2층 HOME**으로 보존·재설계하고, 관리자 전용 SPORTS와 전술/공룡 PLAY를 주변에 연결한다. 실제 현행 건물 높이를 먼저 확인하고 숫자만 더하지 않는다.

큰 6층 직사각형을 쌓기보다는 아래층의 따뜻한 가로 입면, 3층 이상 일부 셋백, 테라스와 중정, 지붕 녹지를 이용해 참고 이미지의 작은 동네 인상을 유지한다. 업무동/집/스포츠의 역할은 간판뿐 아니라 동선·소리·재료로도 드러나야 한다.

첫 기본안은 업무동 기준층 바닥 약 26×22m 범위 안에서 코어·수납·위생·업무 면적을 배분하는 방식이다. 이것은 가상 게임 설계값이며 실제 건축 구조/소방/접근성 법규 충족의 보증이 아니다. 너무 넓은 빈 면적은 줄이고 밀도·사용 시나리오·웹 성능을 함께 검토한다.

건축 지원실은 최소한 방·문·설비·읽을 수 있는 가상 상태·안전한 상호작용을 가진다. 하지만 가상의 전기실 스위치를 누르는 것이 실제 Firebase/서버/비용 차단 설정을 바꾸면 안 된다. 장소 연출과 운영 인프라를 분리한다.

## 8. 층을 늘릴 때 같이 설계할 공통 코어

층별 평면도만 각각 만들지 말고 하나의 수직 코어 도면을 먼저 만든다. 제안 구성은 승객용 엘리베이터 1기, 넓은 운반/서비스용 1기, 주계단과 반대편 보조계단 2개, 같은 위치에 정렬된 화장실/설비 샤프트·전기/통신 수납이다. 2기의 필요성과 성능은 평가하되, 줄이면 원인과 대체 이동/운반 계획을 설명하고 임의 생략하지 않는다.

코어는 B1~6F에 일관된 좌표를 쓰고, 옥상 접근도 연결한다. 층간 슬래브, 엘리베이터 홀, 출입구, 문턱, 계단참, 난간, 천장고, 서비스 통로를 함께 만든다. 벽·샤프트·문짝은 물리 충돌과 시각을 맞춘다.

모든 사용층의 화장실은 같은 층의 공용 동선에서 접근한다. 회의실 또는 개인실을 통과하거나 관리자 전용 방을 지나야만 화장실에 갈 수 있으면 실패다. 위아래 위생 시설은 가능한 같은 축으로 모으고, 문을 열 때 세면/칸막이와 시야·사용 여유를 고려한다. 계단이나 옥상에서 떨어지지 않도록 난간과 정상 collider를 갖춘다.

로비·각 층 홀·승강기 패널·모바일/화면 안내는 같은 FloorDirectory 데이터를 사용한다. 현재 층, 방 이름, 출입 가능 상태, 회의 예정/사용중을 일관되게 보여 준다. 안내표가 옛 이름·층을 표시하지 않아야 한다.

실제 안전 인증이나 건축 법규를 준수했다고 표기하지 않는다. 접근하기 쉬운 폭, 길찾기와 출구 등 현실적 설계 원리를 게임에 적용하는 것이다.

## 9. 엘리베이터 — 장식이나 순간이동 메뉴가 아닌 실제 탑승

필수 흐름: 홀에서 호출 → 대기/현재 위치 표시 → 문 열림 → 사람·사물 탑승 → 층 선택 → 문 닫힘 → 이동 → 층 정렬 → 문 열림 → 하차.

상태를 IDLE, ARRIVING, OPENING, OPEN, CLOSING, MOVING, LEVELING, HOLD, FAULT로 분리하고 호스트가 권위 있는 liftId·tripId·targetFloor·상태시각을 관리한다. 같은 호출은 큐에서 중복 제거하며 여러 층 동시 요청을 버리지 않는다. 버튼을 누른 사람에게 등록되었음을 표시한다.

문이 닫히는 동안 사람이나 큰 가구가 끼면 멈추고 다시 연다. 승강기가 없는 층의 문은 열리지 않는다. 승강로에 떨어지거나 문 닫힘으로 몸이 튀지 않게 한다. 과적/적재 부피 한도를 게임 설계값으로 명시하고 숫자만 실제 법규처럼 쓰지 않는다.

Godot AnimatableBody3D 등 실제 moving platform 방법을 검토한다. 물리 이동과 플랫폼 속도 승계가 이미 적용되는데 별도로 캐릭터 좌표를 다시 더해 두 번 이동하지 않게 한다. 사람이 걷고, 점프하고, 의자를 들고 탑승해도 안정되어야 한다. 클라이언트 보간·바닥속도·사물은 cabin-relative transform 기준과 world 기준을 명확히 구분한다.

늦게 입장하거나 호스트가 이전된 경우 이동 중 승강기·사람·사물 위치를 복원한다. loading되지 않은 도착층으로 문을 열지 않는다. 도착층 prefetch와 충돌체 준비가 끝난 뒤 정차한다. 실패하면 문을 닫은 안전한 hold 상태를 유지하고 복구 위치를 제공하되 몰래 전체 세계를 초기화하지 않는다.

접근 제어는 층 버튼과 별도 권한을 연동한다. 승객이 섞였을 때 제한층 로비에서 무권한 사용자가 바로 제한 방으로 나오게 하지 마라. 5층은 공개 대기/퇴로와 관리자실 내부 경계를 분리할 수 있다. SPORTS는 별동의 ADMIN_ONLY 경계를 유지한다. 출구를 잠가 사용자를 가두지 않는다.

## 10. 가상 CCTV와 시설 관리 — 프라이버시를 침해하지 않는 게임 기능

사용자가 말한 CCTV는 **게임 세계 안에 놓인 가상 카메라**다. 실제 기기 웹캠, 다른 사용자의 바탕화면/탭, 외부 Google 문서, 마이크를 자동 수집하는 기능이 아니다.

배치 대상은 로비·공용 엘리베이터 홀·주차·공용 출입구로 한정한다. 화장실·샤워실·수면실·침실·의상방·비공개 개인실 내부에는 설치하지 않는다. CCTV 모델이 열린 문을 통해 비공개 방을 들여다보지 않도록 FOV와 위치·가림/마스킹을 검수한다. DM, 문서 화면, 원음, 사용자 실명 정보를 모니터에 표시하지 않는다.

관리자실의 실물 모니터/콘솔에서만 권한 검증 후 선택한다. Camera3D/SubViewport 등으로 현재 장면을 표시하고, 비공개 자료 수신 권한을 CCTV 때문에 추가하지 않는다. 클라이언트에 전달된 정보를 진짜 비밀로 보장할 수 있는 범위는 정직하게 설명한다.

처음에는 선택된 화면 1~2개만 제한된 해상도/주기로 갱신하는 예산을 설정한다. 나머지는 '선택 후 연결' 또는 갱신 시각을 명시한 썸네일을 표시한다. 정지된 이미지를 LIVE라고 속이지 않는다. 콘솔을 닫으면 추가 viewport와 렌더 비용을 중단한다. 모든 카메라를 60fps로 계속 렌더링하지 않는다.

기본 녹화는 꺼 둔다. 감사 로그가 필요하면 운영 행위의 최소 이벤트와 보관 정책을 분리하고 대화 내용을 저장하지 않는다. 출입 관리, 가상 시설 상태, 실제 앱 network status/오류 진단을 서로 다른 영역으로 표시한다.

## 11. 회의실은 더 멋진 가구보다 먼저 '같이 일할 수 있는 상태'가 되어야 한다

'아직 공동 작업하는데 무리가 있다'를 P0/P1 사용자 경험으로 보존한다. 코드에 Yjs가 있고 원본 링크를 열 수 있다는 이유로 해결 처리하지 마라. 먼저 두 사람이 어떤 단계에서 막히는지 실제 시나리오를 재현한다: 입장, 자료 권한, 같은 문서 식별, 한글 동시 입력, 서로의 위치/커서, 페이지, 레이저, 재접속, 저장.

2층 주회의실에는 눈에 읽히는 화면, 서로 겹치지 않는 좌석, 실제 책상 지지/발 여유, 보드·마카·레이저·발표 콘솔, 밝기/발화 상태, 회의 도구가 필요하다. 예쁜 테이블에 작은 문서창만 띄우는 것은 불합격이다.

작업 모드: 3D 공간/타인의 아바타는 유지하면서 큰 2D 읽기·편집 영역, 발표자 패널, 참가자/역할, 음성·자막, 문서 상태를 제공한다. 에디터에 초점이 있으면 WASD/E/Q/클릭이 게임 동작이나 발사로 새지 않아야 한다. 회의 자료를 편하게 읽는 모드와 돌아다니는 모드를 명확히 전환한다.

단일 로비의 전역 document 배열을 모든 층에서 공유하는 구조로 확장하지 마라. `workspaceId / buildingId / floorId / roomId / meetingId / projectId / documentId`의 관계를 정의한다. 같은 프로젝트 문서를 다른 회의에서 의도적으로 공유할 수 있지만, 다른 회의가 우연히 같은 보드·슬라이드를 덮어쓰면 안 된다. 물리적 방에 들어온 것과 문서 편집 권한은 다르다.

## 12. 공동작업 데이터·편집·재접속 명세

### 회의 준비 → 진행 → 종료

준비: 제목/의제/자료 등록 → 링크와 실제 편집 권한 확인 → 초대/방 연결.
진행: 동시 문서/보드/마인드맵 → 발표/레이저 → 질문/손들기/타이머/투표.
종료: 결정 사항·담당자·할 일 → 회의 결과 확인 → 파일 내보내기 → 다음 모임에서 가져오기.

내장 문서는 Yjs/검증된 CRDT 및 에디터 바인딩을 활용한다. 기존 구현과 호환을 확인하고 유료 기능으로 무단 전환하지 않는다. 실제 편집 source를 찾고, minified build 파일만 수동 수정하지 마라.

- 2명 이상이 같은 위치에 한글 IME로 입력하고, 붙여넣고, 표/목록을 수정해도 글자가 사라지거나 composition이 깨지면 안 된다.
- collaborator 이름/색·커서·선택·읽기/편집 상태를 보인다. Awareness/presence는 영구 문서 내용과 분리하고 권한 있는 상대에게만 전달한다. 숨긴 UI를 보안이라고 하지 않는다.
- Undo는 가능한 자신의 transaction origin을 기준으로 하고 다른 사람의 글을 통째로 되돌리지 않는다. 충돌 정책과 지원 범위를 문서화한다.
- 오프라인 초안/기기 저장, 상대 수신, 세션 확정, 외부 원본 저장을 다른 상태로 표시한다. Yjs 상태 수렴이 모든 내용의 의미적 정확성을 자동 보장하는 것으로 오해하지 않는다.
- 재접속은 state vector 등 필요한 차이만 교환하고, 오래된 문서 전체 JSON으로 최신 공동작업을 덮어쓰지 않는다. IndexedDB 캐시는 cloud 영구 보관이 아니다.
- 문서 변경 권한은 peer 메시지 수신 시도마다 확인한다. 권한 취소/다른 프로젝트 참가/host migration 때 stale lease·epoch·connection을 처리한다.
- 여러 회의가 같은 채널을 쓰지 않도록 문서/meeting scope를 검증한다. 입력/문서/음성/큰 자료 전송 큐를 분리해 파일 업로드 중 타이핑과 음성이 멈추지 않게 한다.
- 저장은 문서 상태, 메타데이터, 보드·마인드맵, 결정/할 일, 첨부 hash를 일관된 checkpoint로 묶는다. 모순된 시점의 서로 다른 부품을 합쳐 복원하지 않는다.

Google Docs/Slides/Microsoft Excel은 실제 원본 공동작업을 유지한다. 각자의 정상 계정/공유 권한으로 같은 원본을 열게 하고, 읽기 전용 URL·게시본·PDF를 편집 서비스라고 부르지 않는다. 현재 코드의 링크 검증, 원본 변경에 따른 공유 링크 차이, 팝업 실패 메시지와 사용자 흐름을 실제 계정으로 시험한다.

외부 iframe을 강제로 우회하지 않는다. 허용되는 방식만 임베드하고, 제한 시 같은 원본을 별도 창으로 여는 흐름을 제공한다. 원본 공유 상태를 API/권한 없이 확인했다고 표시하지 않는다. 외부 원본 내용은 `.homeworld`에 링크만 저장되는지 실제 파일도 들어가는지 분명히 한다.

발표를 편하게 보기 위해 선택적인 화면/탭 공유를 추가할 수 있다. 반드시 사용자의 직접 선택/브라우저 허가로 시작하고 종료 상태·대상 범위를 표시한다. 사람 몰래 외부 문서를 캡처하거나 로그인 세션을 공유하지 않는다. 화면 공유와 공동 편집은 다른 기능이다.

호스트가 외부 문서 탭으로 이동해도 어떤 방식으로 세션이 유지되는지 검증한다. 브라우저 백그라운드 제한을 삭제 가능한 if 하나로 해결했다고 하지 않는다. 호스트 인계·별도 창 배치·승인된 지속 호스트 등의 실제 선택과 한계를 명시한다.

## 13. 발표·보드·레이저·회의 음향

발표 상태는 `presentationId, sourceId, pageRevision, pageIndex, presenterId, lease/epoch`로 묶는다. 레이저 포인터는 화면의 local UV뿐 아니라 해당 자료/페이지/버전과 함께 전달한다. 이전 페이지의 늦은 포인터를 새 페이지에 표시하지 않는다. 실물 레이저의 총구 방향/표면 raycast와 확대 발표 패널 포인터의 좌표계를 통일한다.

같은 회의에서 발표자 인계, 늦은 입장, 자료 전송 실패/재시도, 페이지 변경과 주석, 레이저 동기화를 시험한다. 별도 회의실에는 다른 발표 상태가 있어야 한다.

화이트보드는 손의 마카 접촉, 확대 그림, 한글 텍스트, 색/굵기, 지우기, 선택/이동, Undo를 모두 실제 공유 상태로 연결한다. 브레인스토밍 메모·그룹·투표, 마인드맵 노드·선, 질문·할 일은 동일 meeting의 결과로 남는다.

층이 겹쳐도 수직 거리만으로 윗층의 회의 음성이 새면 안 된다. floor/room/문 열림과 acoustic portal을 기반으로 근거리 모드의 범위를 결정한다. 전체 방송, 현재 회의, 개인 대화, 근거리와 자막의 수신 범위를 분리한다. 가까운 두 회의가 서로 덮어쓰지 않게 한다.

발표자 lease와 microphone consent는 다르다. 손들기/발표권을 주어도 마이크를 몰래 켜지 않는다. CCTV가 회의 음성을 수집하지 않는다. 한국어 자막, 기존 음성 거리 조절, 실제 방송실 기능을 유지·개선하며 실제 마이크 검증이 없는 경우 그 한계를 기록한다.

## 14. 사물·캐릭터·미술이 만나는 기능 계약

모든 playable asset은 외형뿐 아니라 `pivot`, `unitScale`, `support_footprint`, `colliderProfile`, `interactionPoint`, 필요한 `leftGrip/rightGrip`, `seatPelvis/seatFoot`, `standExitCandidates`, `screenPlane`, `doorSweep`, `floorAttachment`를 함께 가진다. 모든 asset에 의미 없는 같은 anchor를 붙이지 말고 해당 기능에 필요한 계약만 정의한다.

책상: 상판·지지대·프레임/케이블과 무릎 여유·바닥 지지를 함께 검수한다. 다리가 바닥에 묻히면 메시 추가가 아니라 충돌·높이·복원 좌표를 확인한다. 소파/의자: 좌석별 점유·골반·발·등받이·입장/퇴실과 운반 부피를 모델 재작업 시 함께 갱신한다.

애니메이션은 V5에 있는 AnimationTree/phase/grounded/contact weight를 먼저 조사한다. 다시 없다고 오진하거나 sin 보행으로 회귀하지 않는다. 원래 사용자 다리 떨림과 겹침은 사용자 기록에 남겨 두고, 조명/재질 변경과 별도로 재검증한다.

체형 변경/얼굴 UV/의상방 현장 편집은 계속 유지한다. 부드러운 미술을 위해 큰 머리·짧은 다리를 무단으로 적용해 원본 남자 캐릭터와 접촉을 깨뜨리지 않는다. 얼굴 texture는 actor별로 분리하고 미확정 초안/타인의 외형을 덮어쓰지 않는다. 체형·의상 mesh fitting은 슬라이더 UI가 아니라 실제 rig/충돌·카메라·가구에서 검증한다.

물건 설치는 옆 패널 버튼→썸네일 drag→화면 raycast→ghost/회전/스냅→drop 요청→호스트 검증→한 개 생성이다. 층별 floorId와 support surface, 엘리베이터/계단/문/좌석·관리 구역 보호를 포함한다. elevator cabin에 동적 소품을 '운반'하는 것과 고정 가구를 '설치'하는 것은 다르다. 샤프트/문틈에는 설치하지 않는다.

기본 E 집기/내리기, Q 던지기, 좌클릭 현재 도구, F 기능 사용, R 보조, 시점 전환·채팅 입력 우선순위를 유지한다. 의상 편집은 의상방 현장 상호작용으로만 시작하며 전역 단축키를 새로 만들지 않는다. 입력 focus stack을 한곳에서 관리한다.

| 음성/방송 | 근거리/전체·한국어 자막·방송실·공지 유지. 층간/회의별 scope와 consent 개선 |
| 캐릭터 | 사용자 남자 원본 보존, 일반 1/3인칭·다양한 동작·소품 접촉·현장 의상방 유지 |

| 교실 | 첫 화면 고정 '교실', AAA-AAA 초대 코드와 링크. 고정 주소·현재 host·영구 저장을 구분 |
| 교육용 표시 | 입장 하단 '교육용으로 활용할 수 있는 메타버스입니다.'만 표시. 문구로 교육 앱/퀴즈/새 권한을 생성하지 않음 |
| 저장 | 공간 전체 내보내기/가져오기 + 검증된 버전 migration. chat 원음/비밀/PIN 자동 포함 금지 |

## 16. 다층 세계의 시스템 설계

또 다른 거대한 `world_v6`를 기존 V5/V4/V3에 계속 상속시키는 것으로 확장을 끝내지 마라. 기존 정상 경로를 테스트하며 점진적으로 구성/서비스를 분리하고, 아래 상태의 단일 소유자를 정의한다.

- World/Building/Floor/Room registry: topology, portal, navigation, stable ID, room-local transform, asset mapping.
- ElevatorService: car state/queue/occupancy/relative transforms. DoorService: swing/sweep/lock/exit policy.
- AccessService: verified administrator, room locks, court roles. 실제 비밀은 신뢰된 서버에만.
- MeetingService: meeting lifecycle/roles/resources. CollaborationService: per-document CRDT/state vector/persistence/awareness.
- PresentationService: source/page/presenter/laser. Messaging/AttachmentService: channels/chunks/retry/availability.
- Voice/Caption/Broadcast: authorized recipients, acoustic portals, device consent.
- Player/Interaction/Animation: local prediction, remote replication, pose/phase/grips/seats.
- CCTVViewService: allowed virtual camera/render budget; not user device surveillance.
- SaveMigrationService: versioned world manifest, docs, attachments, profiles/consent, old-layout mapping.

렌더링 데이터와 논리 상태를 분리한다. 어떤 층의 mesh를 숨겨도 그 층의 문서·회의·권한·엘리베이터의 상태를 삭제하지 않는다. 반대로 화면 밖 모든 층에서 모든 rigidbody, CCTV, 문서 canvas, 조명과 애니메이션을 계속 실행하지 않는다.

현재 층/보이는 연결 공간/승강기 도착층을 우선 로딩한다. host는 다른 층에 실제 사용자가 있거나 활성 물체가 있으면 그 활동에 필요한 simulation을 유지한다. empty/sleeping 영역만 안전하게 휴면 처리한다. 동결된 물체가 다시 켜질 때 폭발하거나 문서가 초기화되면 실패다.

6층의 모든 파일을 첫 로딩에 무조건 넣지 않는다. 자산 공유·LOD·instancing·묶음/분할 배포 가능성을 실제 Godot web에서 검증한다. 추가 PCK/리소스 로딩을 선택하면 버전·CORS·hash·cache 무효화와 실패 복구를 구현하고 미완성 스트리밍을 완료로 발표하지 않는다.

## 17. 웹 품질·조명·성능 예산

설치된 Godot 4.6.x의 Compatibility 조건을 확인한다. Forward+ 전용 GI/효과를 웹에서도 당연히 쓸 수 있다고 하지 않는다. 미리 구운 lightmap, UV2, 단순하고 일관된 PBR/색/normal, 적절한 reflection과 제한된 실시간 광원으로 참고 이미지 분위기를 만든다.

정적 lightmap과 움직이는 문·가구·캐릭터·스위치 조명을 분리한다. 사용자가 끌 수 있는 전등의 빛/그림자가 영구적으로 bake되어 스위치를 꺼도 그대로 밝은 문제가 없어야 한다. 필요하면 정적 자연광/간접광과 동적 task lamp를 분리하고 한계를 표시한다.

품질 예산은 실제 장치와 최종 빌드에서 정한다. 초기 목표안은 데스크톱 1080p 60fps 지향, 저품질 720p 30fps 지향이며 보장값이 아니다. 평균뿐 아니라 p95/p99 frame time, memory, draw calls, 활성 물리 개수, 전송량, 초기 로딩과 층 전환 지연을 기록한다. 이름만 '최적화'하고 실제 수치를 생략하지 않는다.

시험 조합: 여러 층에 2/4/8명, 두 회의의 동시 한글 편집, 음성/자막, 큰 파일 한 개 전송, 엘리베이터 탑승, 관리자 CCTV 1개를 함께 켠다. 같은 PC의 8개 브라우저 수치를 서로 다른 PC 8명의 경험으로 주장하지 않는다.

품질 저하는 reflection/CCTV fps/먼 거리 LOD부터 조절하고 문서 가독성·입력·물리/권한 검증을 먼저 제거하지 않는다. 사실적인 접촉/동선 문제를 DOF·안개·어둠으로 숨기지 마라.

## 18. 기존 저장 파일을 잃지 않는 구조 개편

기존 layoutVersion과 schemaVersion을 읽고 실제 파일을 기준으로 migration을 설계한다. roomId와 objectId를 유지/매핑하며 변경된 층은 room-local anchor 기반 변환을 우선한다. 옛 세계의 절대 XYZ를 새 건물에 그대로 적용해 가구가 바닥 아래나 허공에 남지 않게 한다.

미리보기에는 이동한 방·사물, 변환할 수 없는 항목, 누락된 asset/첨부물을 보여 준다. 자동 배치가 안전하지 않은 사물은 삭제하지 않고 **미배치 보관함**에 원래 ID/상태와 함께 보존한다. 원본 파일은 그대로 두고 임시 세계에서 검증 후 성공할 때만 교체한다. 여러 번 가져와도 중복 변환/생성이 없어야 한다.

저장 대상: 건물/층/방 구성, 개인실 슬롯, 가구 상태·문·등, 프로젝트/meeting documents/board/mindmap/results, 발표 자료 hash와 실제 포함 여부, 외형 프로필과 동의된 자산 참조. 승강기/좌석/손 점유·peer ID·host lease는 지속할 설정과 재개 때 초기화할 상태를 구분한다.

가져오기 중 관리자 권한, PIN, token, raw microphone, DM, 실제 CCTV 녹화가 포함되면 안 된다. 원본 외부 문서 링크와 외부 문서 내용의 백업은 구분한다. 기록은 cloud 영구 보관으로 오해시키지 않는다.

## 19. 개발 순서와 자기 검수

1. 사용자 관찰/최신 ref/실행 조건을 기록하고 기존 기능의 재현 기준을 만든다.
2. **완결된 4인 회의와 두 회의실 데이터 분리**를 우선 수리한다. 새 층·소품 때문에 핵심 협업 결함을 미루지 않는다.
3. 첨부 미술을 적용한 대표 실제 장면 3개(로비/카페, 주회의실, 가구/캐릭터 근접)를 만든다. Godot 웹 캡처로 검토한다. 이는 전체 제품을 세 장면으로 축소하는 것이 아니라 미술 기준 확정이다.
4. 전체 B1~RF 수직 단면, 공용 코어, 층별 프로그램을 구현하고 모두 직접 걸어 다닐 수 있게 한다. 층별 장식보다 elevator/stair/toilet/방 ID/migration을 먼저 묶는다.
5. 각 층의 업무·생활·관리·휴게를 실제 데이터와 연결한다. 가상 CCTV와 방송의 접근/프라이버시·렌더 예산을 검증한다.
6. HOME, SPORTS/PLAY, 의상방, 메신저/음성/저장·기존 게임을 회귀하고 새 미술을 통일한다.
7. 다층·다회의·네트워크/음성/첨부 동시 부하와 저장 왕복을 같은 빌드에서 실행한다.

역할별 검수 관점은 아트/건축, 캐릭터 접촉, 협업, 네트워크/보안, QA로 나눈다. 실제 독립 에이전트/사람을 쓰지 않았다면 여러 팀이 검수했다고 하지 않는다. 개발 코드를 아는 상태의 자기 테스트와 처음 쓰는 사람의 사용성을 구분한다.

관찰→원인 가설→분리 시험→수리→실행→비평→재수리→회귀의 루프를 수행한다. 시간이 길다는 이유로 고품질이라고 말하거나 인위적 sleep/대기·거짓 백그라운드 작업을 하지 않는다. 도구/권한 제약으로 미실행한 것을 기록한다. 자동 테스트 통과 수로 사용자 불편을 지우지 않는다.

짧은 AGENTS.md는 실행 지도로, 전체 명세는 기능별 문서로, TASK_STATE.md는 현재 우선 결함/빌드/실행 결과/다음 작업으로 사용한다. 거대한 명세를 매번 다시 생성하는 데 작업 시간을 쓰지 않는다. 문서는 실제 코드·장면·검증을 지원하는 최소 충분량으로 관리한다.

## 20. 필수 산출물과 최종 완료 보고

실행 가능한 Godot 프로젝트/웹 빌드, 원본을 보존한 Blender 제작 파일, 모델·재질·애니메이션·anchor manifest, 층별 평면/단면·동선·의도된 배치표, 각 협업 모듈, 외부 연동 설정 예시, 저장/migration, 테스트와 실제 화면/영상, 라이선스/비용 표, 한국어 실행 안내를 제공한다.

최종 보고는 기능별로 코드 있음 / 실제 실행 / 자동 검증 / 사람 사용 확인 / 품질 미달 / 운영 미설정 / 미실행을 구분한다. 최신 사용자 발언을 반박하거나 감추지 않고 해당 관찰 ID에 증거를 연결한다.

최소 통합 장면: 로비에서 들어와 층 안내를 보고, 서로 다른 사람들이 엘리베이터로 이동하고, 두 회의가 문서/음성/발표를 섞지 않고 동시에 진행된다. 관리자만 관리 콘솔과 코트를 쓰며 공개 공간의 가상 CCTV를 확인하고 공지한다. 일반 사용자는 HOME/개인실/의상방/휴게와 물건 설치를 사용한다. 모두 나가기 전 공간을 내보내고 다음 모임에 가져와 같은 프로젝트와 자료를 이어간다. 이 전 과정의 미술이 첨부 이미지의 따뜻하고 세밀한 수공예 인상과 일관되어야 한다.

"기본 구조가 마련되었다", "앞으로 확장 가능하다", "코드에 함수가 있다", "스크린샷 세 장이 예쁘다"는 최종 완료 문장이 아니다.

```text
이제 깃허브 코드를 볼 때, 내 말이 틀렸다고 해서 지우지 말고 프롬프트에 넣어(따로 사용자의 불편함 이런 식으로)
일단, 디자인이 현재 매우 딱딱해. 다른 플러그인을 찾거나, api 키를 찾거나 등등을 이용해서 위 이미지와 같이 고쳐줘.
그리고, 좀 더 시스템을 고도화 해줘.(특히 회의실을 고도화 해줘야해. 아직 공동 작업하는데 무리가 있어)
그런 과정에서 확장도 해야 해.
예시: **1. 저층부 (로비 및 외부인 공용 공간)**

- **지하층 (B1 ~ Bn):** **주차장**, 전기·기계실, 구내식당, 매점, 체력단련실(기타 복지시설)
- **1층 (로비):** **안내 데스크(인포메이션)**, 보안 게이트, 방문객 접견실(미팅룸), 카페, 은행 ATM
- **2층 ~ 3층:** 외부인 출입이 가능한 **대형 회의실**, 교육장, 세미나룸, 면접실

**2. 중층부 (일반 업무 공간)**

- **중층 전체:** **부서별 사무실(오피스)**
  - **현업 부서:** 마케팅, 영업, 개발, 디자인 등 실제 실무를 담당하는 부서들이 배치됩니다.
  - **공용 공간:** 층마다 **탕비실(OA룸/바)**, 소형 회의실, 폰부스, 화장실, 휴게 공간이 함께 위치합니다.

**3. 고층부 (경영진 및 핵심 관리 공간)**

- **고층 (경영진 공간):** **임원실**, 대표이사(CEO)실, 이사회 회의실(대회의실)
- **관리 부서:** 보안과 기밀 유지가 중요한 **인사(HR), 재무/회계, 법무, 전략기획** 부서가 대개 고층부에 임원실과 가깝게 배치됩니다.

**4. 최상층 및 옥상**

- **최상층/옥상:** 직원들을 위한 **옥상정원(스카이라운지)**, 흡연 구역, 휴게실

라는 것을 자세히 분석하고 고쳐서 프롬프트 고도화 해줄래?
```
