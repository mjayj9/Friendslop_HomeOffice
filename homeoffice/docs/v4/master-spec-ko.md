# COMMONS WORKSPACE — 전문 협업·생활 메타버스 V4 통합 개발 프롬프트

갱신일: 2026-09-17. 제품명은 가칭이다. 기존 저장소/배포 URL의 자동 변경을 뜻하지 않는다.

**이 문서는 이전 HomeOffice V1~V3 개발 프롬프트보다 우선하는 최신 통합 명세다. 목표는 설명·모형·체크리스트가 아니라 실제 실행되는 전문 메타버스다. 기존 기능을 지우고 또 다른 작은 시제품으로 돌아가지 않는다.**

## 0. 가장 중요한 방향 전환

너는 게임 클라이언트/멀티플레이 엔지니어, 테크니컬 아티스트, UX 디자이너, 테스트 엔지니어 관점에서 일한다. 이름만 바꾸거나 스스로 전문가라고 선언하지 말고 결과로 입증한다.

이번 제품을 Friendslop류의 엉성한 장난감, 학습용 Three.js 데모, 임시 집 샌드박스, 오브젝트 좌표 편집기로 프레이밍하지 마라. 참고작의 상호작용은 참고 이력으로 남기되 제품 요구는 **전문 협업·생활 메타버스**다. 전문적인 건축/환경 미술, 일관된 UI, 한국어 협업, 풍부한 사물 조작, 자연스러운 아바타, 완결된 게임 루프를 함께 만든다.

Roblox의 장점은 캐릭터 중심 조작, 3인칭 카메라, 빠른 상호작용 피드백, 액션/이모트, 손쉬운 소셜 합류, 이해하기 쉬운 게임 규칙과 재시작 흐름으로 구체화한다. Roblox 브랜드·블록형 외형·플랫폼 엔진·과금/확률형 상품까지 복제하라는 뜻이 아니다. Godot를 유지한다.

카카오톡과 비슷하다는 것은 노란색 말풍선만 붙이라는 뜻이 아니다. 대화 목록, 텍스트/이미지/파일, 답장과 반응, 읽음과 실패 상태, 검색/미디어 모아보기, 편안한 한국어 입력을 갖춘 실제 메신저 UX를 뜻한다. 카카오톡 로고·상표·유료 이모티콘을 복사하지 않는다.

이번 최신 변경은 다음과 같다.
- 일반 탐색의 3인칭을 기본안으로 추가하고 1인칭도 자유롭게 전환한다. 수면 때만 3인칭인 구현은 부족하다.
- 방별 사용자 승인 목록/출입 금지 권한 UI를 폐기하고, 각 실제 방의 관리자 PIN 잠금/해제로 대체한다.
- 총은 들기만 하면 **회의실·집·오피스·교실을 포함한 어디서나** 사용할 수 있다. 무기 사용 승인·무기 구역 제한을 되살리지 않는다.
- 보안, 입력 포커스, 현재 실제 소유권, 물리적 벽/거리, 피해/점수 검증, 전송 속도 제한은 유지한다. 이것은 위의 게임 사용 허가와 다르다.
- 빠른 응답/파일 개수/클립 개수/소요 시간 대신 실제 검토·재현·수정·회귀 증거를 완료 기준으로 삼는다.

작업 시작 시 현재 branch/head·실제 Pages 배포 ref·Build ID·source digest를 다시 확인한다. 위 ref 이후 변경이 있으면 현재 코드로 진단한다. 이전 PR의 결함을 검증 없이 현재 결함으로 반복하지 않는다.

이번 프롬프트 작성 시 GitHub와 최신 Pages 아티팩트의 67개 파일 해시·크기는 확인했으나, 공개 URL 조회와 로컬 브라우저 실행은 환경 제약으로 실패했다. 작성자가 최신 3D 화면과 동작을 직접 플레이해 검증했다고 가정하지 마라. 사용자 체감과 코드 사실, 과거 제작자의 시험 기록, 이번 네가 재현한 결과를 구분하라.

현재 코드에서 확인된 출발점:
- 실제 엔진은 Godot 4.6.1/Jolt다. 'Three.js 초보 느낌'은 품질에 대한 비유다.
- `web/social.mjs`에는 400자/최근 40개 텍스트 채팅이 있다. 카카오톡식 첨부물·대화 UX와는 다르다.
- `scripts/v2/avatar.gd`에는 AnimationPlayer와 IK 경로가 있고, 일반 탐색용 자유 3인칭과 수면 카메라를 분리할 필요가 있다.
- V3 보고서는 13본/62 Action을 기록하지만 모든 접촉/전이를 인수했다고 하지 않는다.
- `scripts/v3/world.gd`는 `scripts/v2/world.gd`를 상속한다. 일부 모듈화는 이미 진행됐다. 과거 정규식 코드 합성기는 중단했다는 현 코드를 확인한다.
- 총/방패 집기와 피해 처리, classroom 특수 제한, 상속받는 `allowed_weapon/allowed_entry`와 회수 루프는 새 정책과 충돌할 수 있다.
- 농구의 charge/backspin/steal, 축구 foot-touch가 이미 있다. 없는 기능처럼 새로 붙이지 말고 실제 품질을 측정한다.
- `web/document-registry.mjs`의 원본 문서 링크와 별도 창은 이미 있다. 이것을 내장 Google/Excel 완전 연동이라고 확대하지 않는다.

자체 제작 기록의 '통과'는 참고일 뿐이다. 정확히 같은 빌드와 환경에서 새로 검증한 것만 이번 통과로 기록한다. `dirty=true`나 commit 문자열 차이만으로 배포 불일치를 단정하지 말고 source digest와 실제 패키지를 대조한다.

## 2. 유지할 환경·범위와 안전한 작업

Godot와 BlenderMCP를 유지한다. 사용자가 알려 준 BlenderMCP 포트는 9876이며 제작 환경에서 실제 도구와 읽기 전용 씬 조회로 확인한다. 네 컨테이너 localhost와 사용자 PC localhost를 혼동하지 않는다. 제작 포트를 학생 브라우저나 인터넷에 공개하지 않는다.

기존 남자 GLB 원본과 파생본이 저장소에 있는지 먼저 검사한다. 같은 파일을 불필요하게 다시 요구하지 않는다. 원본이 없거나 대상이 다를 때만 “사용할 남자 캐릭터 원본 GLB와 별도 리깅/애니메이션을 업로드해 주세요”라고 요청한다. 남자 캐릭터를 우선 완성한다.

GitHub 학생 Pro, 기존 Firebase Blaze, 추가 비용 0원 목표, 기존 비용 보호 보존 조건을 유지한다. Firebase가 있다는 이유로 원음·틱 상태·첨부물 모두를 DB로 보내지 않는다. 필요한 관리자 검증 서비스/저장 서비스가 있으면 범위·비용·기존 앱 영향·권한을 설명하고 운영 생성/변경은 승인 범위에서 한다. 미확인 상태로 기존 DB·Rules·버킷·Auth를 덮어쓰지 않는다.

기존 작업을 백업/브랜치로 보존한다. 저장소명·Pages URL은 현재 사용자 링크를 깨뜨리므로 브랜드 변경과 분리한다. 원격 push·PR merge·운영 배포·결제 변경은 별도 승인에 따른다. 로컬 리팩터링/검증은 불필요한 확인 대기로 중단하지 않는다.

웹 export에서는 실제 지원하는 렌더러/스레드/물리/오디오를 확인한다. Compatibility 기반으로 가능한 미술을 먼저 설계하고, 네이티브 전용 효과를 웹에 된다고 쓰지 않는다. 현재 안정적인 버전과 템플릿을 고정하며 무조건 최신으로 올려 회귀를 만들지 않는다.

## 3. 전문적인 디자인을 측정 가능한 작업으로 바꿔라

목표 미술은 **실제 건축 비례에 기반한 contemporary campus + refined co-living**이다. 극단적인 포토리얼리즘이나 블록아웃 중 하나만 가능한 것으로 생각하지 마라. 정돈된 재질·빛·스케일·가구·정보 계층으로 전문성을 만든다.

처음 다음을 작성하고 실제 대표 장면과 연결한다.
1. Art direction: HOME/OFFICE/PLAY의 재질군, 색채, 채광, 조명, 카메라, 소품 밀도.
2. Design system: 색·타이포그래피·간격·그리드·컴포넌트·상태·반응형·키보드 포커스.
3. Architecture: 전체 동선/층별 도면/단면/문·창/계단/설비/음향/개인실 확장 계획.
4. Reference comparison: 실제 참고 화면이나 자료의 출처와 '차용할 원리/제외할 요소/검증할 동작'.
5. Quality rubric: 참조와 같은 눈높이·해상도·조명 조건의 실제 게임 캡처와 차이 목록.

필수 시각 기준:
- 메시 모서리/두께/베벨, 가구의 기능적 비례, 문틀·걸레받이·창틀·하드웨어, 적절한 UV/텍스처 방향.
- 나무·직물·유리·금속·타일의 roughness/반사 특성이 구별되고 모든 면이 동일한 플라스틱처럼 보이지 않을 것.
- 과도한 ambient로 평평하게 밝히거나 bloom/색 필터만으로 마감하지 않을 것. 지원 경로에서 조명·접촉 그림자·색 대비를 검토할 것.
- 반복 텍스처/늘어난 무늬, z-fighting, 뜬 가구, 깨진 노멀, 공간을 뚫는 창/계단, 단순 원색 큐브는 결함 목록에 포함할 것.
- 낮은 품질 옵션에서도 공간의 용도·길 안내·UI 계층이 유지될 것. 저품질을 빈 흰색 평면으로 만들지 않을 것.

한 개 회의실 대표 장면을 실제 게임에서 미술 완성 수준으로 만든 뒤 같은 기준을 전체에 적용한다. 그러나 대표 장면만 만들고 나머지 요청 공간을 생략하지 않는다. 블록아웃은 내부 제작 단계이며 최종 결과로 부르지 않는다.

## 4. HOME과 OFFICE의 명확한 분리

공용 도착 로비에서 OFFICE, HOME, PLAY가 건축적으로 구분되면서 걸어서 연결된다. 표지판 이름만 다르게 하거나 같은 방 색을 바꾸는 것으로 끝내지 마라.

```text
도착 로비 / 고정 교실 입구
├─ OFFICE: 리셉션 → 핵심 회의실 → 자료/협업 공간 → 개인실 확장 복도
│                         └─ 방음 방송실 / ON AIR
├─ 중정·연결 복도·테라스
├─ HOME: 현관/수납 → 거실 → 식당·주방/팬트리
│                        └─ 실제 계단·계단참 → 침실/수면실·욕실·휴식
└─ PLAY: 자유 제작방 / 아케이드·총 게임 공간 / 농구 / 축구
```

게임/총 공간은 전용 경기와 장비가 모인 장소일 뿐 전역 총 사용을 금지하는 경계가 아니다.

회의실은 가구와 화면의 배치, 좌석에서의 시인성, 음향, 이동 동선, 전원/조명/자료 조작이 실제 회의 목적에 맞아야 한다. HOME은 거실 대화·소파 점프·주방 조리·식사·취침과 욕실의 생활 디테일이 있어야 한다. 개인실은 사람 수에 맞춰 연결 복도 끝에서 생성되고 기존 방·가구·사람을 재배치하지 않는다.

계단은 단높이·단너비·참·난간·머리 공간과 충돌을 일치시킨다. 실제 높이는 게임 캐릭터/행동에 맞춰 검증하며 건축 법규 인증이라고 말하지 않는다. 욕실은 변기·속이 빈 세면대·수전·샤워 공간·문·조명·거울/환기 표현·타일을 목적 있게 모델링하고, 물내림·수도·조명을 조작할 수 있게 한다. 복잡한 위생/생존 시스템을 새로 만들 필요는 없다.

개인실·복도·각 방 상태는 저장 파일로 보존한다. 새 사람의 동일 닉네임을 관리 신원으로 사용하지 않는다. 방 PIN 정책은 §8에 따르며, 입장 로비/교실 시작 화면까지 암호 입력 때문에 아무도 접근하지 못하게 하지 않는다.

## 5. Roblox에서 가져올 장점을 구체화하라

공식 Creator Hub와 실제 경험의 공식 설명을 확인한다. 소스가 없는 Roblox 게임의 내부 구현을 안다고 주장하지 않는다. 직접 플레이할 수 있으면 짧은 조작 영상/관찰 기록을 남기고, 설명만 읽었으면 이를 분리한다.

| 참고할 강점 | 이 프로젝트에 구현할 기능 | 완료 증거 |
|---|---|---|
| 캐릭터 중심 카메라 | 자유 3인칭, 휠 거리 조절, 1인칭 전환, 조준 어깨 시점 | 벽·좁은 계단·앉기·수면·조준에서 카메라 충돌/전이 영상 |
| 빠른 조작 이해 | 일관된 E/Q/F/클릭, 상황 힌트, 실제 도구 아이콘/핫바 | 새 사용자가 설명서 없이 물건 집고 사용/던지기 |
| 사회적 표현 | 닉네임·발화 표시·손들기·인사·고개 끄덕임·박수·앉기·춤/휴식 | 여러 사람이 실제 동작과 이벤트를 같은 상태로 관찰 |
| 연속된 놀이 경험 | 경기 참가·관전·규칙·점수·재시작과 빠른 원위치 복귀 | 실제 2인 경기 종료 후 다시 시작 |
| 응답성 | 로컬 예측·원격 보간·소유권 전이·검증된 물리 결과 | 지연/손실 조건에서 입력/공/점수 일치 |
| 자기 공간 꾸미기 | 가구 카탈로그·미리보기·배치·실제 사용·파일 저장 | 배치 후 사용과 내보내기/가져오기 왕복 |

## 6. CameraRig·입력·액션을 하나의 체계로 만들어라

### 카메라
기본 자유 이동은 3인칭을 설계 기본안으로 한다. 1인칭을 설정/단축키로 언제든 전환한다. 휠 zoom, SpringArm3D 또는 검증된 shape cast 충돌, 좁은 문/계단의 부드러운 거리 보정, 어깨 시점, 감도·반전·FOV·효과 감소를 제공한다.

카메라 yaw와 아바타 facing을 분리한다. 이동 중 방향 회전, 시점만 돌리기, 제자리 회전, 조준 시 몸 방향 정렬을 상태별로 정의한다. 3인칭에서는 자기 전신이 보여야 하며 1인칭에서는 머리 내부만 적절히 숨긴다. 원격 전신/그림자는 유지한다. 수면·앉기·UI 종료 시 이전 카메라 모드를 복원한다.

3인칭 사격은 카메라 ray의 목표와 총구 ray의 실제 경로를 분리해 벽 뒤를 관통하지 않게 한다. 모델의 머리·가구·자기 collider가 조준을 불필요하게 막지 않게 하되 다른 물체의 충돌을 해제하지 않는다.

### 입력 기본안
- WASD 이동, Shift 달리기, Space 점프, Ctrl 웅크리기.
- E 이동 가능한 물건 집기/내리기. Q 던지기.
- F 기능 사용: 앉기/일어나기, 책 읽기, 문/스위치, 컴퓨터/보드/침대.
- 좌클릭 현재 도구: 총 발사, 농구 슛 충전/릴리스, 마카/레이저 사용.
- R 재장전/명시된 보조 동작. 숫자키 핫바. C 1/3인칭 전환을 후보로 한다.
- Enter 채팅 포커스, Esc UI 닫기/포인터락 해제. 액션 휠은 충돌 없는 키를 배정한다.

이것은 기본 키안이며 재설정 가능해야 한다. 현재 코드의 C crouch/기존 read/drop 이름과 혼동하지 않도록 InputMap와 웹 binding/UI 안내를 함께 갱신한다. Q는 바닥 축구공 패스라는 맥락 동작을 할 수 있지만, 손에 물건이 있으면 명확히 그 물건 던지기가 우선한다. 전문 UX를 위해 한 입력이 동시에 두 동작을 실행하지 않는다.

PLAY, BUILD, AIM, BALL_CONTROL, SEATED, SLEEPING, CHAT_FOCUSED, DOCUMENT_FOCUSED, PASSWORD_DIALOG, MINIGAME 상태를 명시한다. 한글 IME/파일 선택/비밀번호 입력/문서 편집 중 이동·발사·카메라 회전이 발생하면 실패다. UI를 닫았을 때 눌린 키/trigger가 남아 계속 발사되지 않게 한다.

### 액션과 모델
이미 있는 남자 원본을 우선 살리고, 손목·손·발목 등 필요한 본을 제작/보완한다. 본 수 자체를 목표로 하지 않는다. 13본이 요구 접촉 품질을 충족하지 못하면 리깅을 보완하고 파생본을 만든다.

걷기/달리기 전후좌우, 출발/정지/회전, 경사/계단, 점프/착지, 집기/들기/던지기, 앉기/일어서기, 잠들기/호흡/깨기, 손들기/인사/박수/가리키기/고개 끄덕임, 글쓰기/타이핑, 농구/축구/총/방패, 음식/조리 동작을 실제 전이와 연결한다. 필요한 root motion 정책과 물리 이동의 중복을 방지한다.

클립에 이름만 다르게 붙이거나 sin 루프만 복제해 행동 수를 늘리지 않는다. 발 미끄러짐, 떠 있는 손, 물건과 그립 이탈, 급격한 자세 팝, 상/하체 충돌을 실제 영상의 구간과 연결해 고친다. Blender 원본·GLB·애니메이션 manifest·그립 anchor·검토 영상을 남긴다.

## 7. 공통 사물·물리 엔진 개편

'모든 사물과 가지고 놀 수 있음'을 권한 예외가 계속 늘어나는 거대한 if문으로 구현하지 마라. PropDefinition/Capabilities, Interactable, Carryable, Throwable, Usable, Seat, Switchable, DocumentSurface 같은 조합으로 구성한다. 구조 부재·배관처럼 고정된 시설은 기능 사용이 가능하고, 책·컵·마카·공·상자·도구·이동 가구는 E/Q로 다룬다. 무게나 앉은 사람 때문에 즉시 움직일 수 없는 물건은 이유를 표시한다.

집기→유지→기능 사용→내리기/던지기→충돌→정지→재집기를 한 계약으로 만들고 주체/거리/가림/현재 소유권을 호스트가 검증한다. 붙어 있는 물체 teleport로 무한 힘을 주지 않는다. 좌석 사용 중 삭제/이동·손에 든 소품의 저장·전등 상태·서랍 내용물·동시 집기·퇴장 정리를 처리한다.

Jolt 설정을 무작정 교체한다고 모든 문제가 해결되지 않는다. 고정 tick, meter 단위, 캐릭터 motor, collision layer/mask, 접촉 재질, 질량·관성·중심, CCD, 손 constraint, 보간/보정을 각각 시험한다. 필요성이 입증된 백엔드 변경은 별도 비교 후 결정한다.

물리 소유권은 참가자 입력의 응답성과 게임 판정의 진실을 구분한다. 손에 든 물건은 빠른 로컬 시각 예측을 할 수 있지만 공의 득점·피해·도난/소유권은 하나의 권위에서 확정한다. Roblox의 분산 물리 개념을 차용하더라도 조작된 클라이언트 결과를 무조건 신뢰하지 않는다.

## 8. 방 권한 폐기 → 방별 관리자 PIN 잠금

이 절은 기존 `entry_grants`, 사용자별 '방 출입 허용', 게임방 전용 승인, `classroom` 권한 제한의 제품 정책을 대체한다. 동시에 총 사용 허가를 완전히 분리·삭제한다.

### 사용자 의도의 구현 기본안
사용자는 '방마다 비밀번호, 그 비밀번호는 오직 관리자 본인만 안다'고 했다. 이를 **각 물리적 방에 관리자만 조작하는 PIN 잠금장치를 두고, 관리자가 열어 둔 방은 학생이 승인 목록 없이 드나드는 방식**으로 해석한다. PIN을 아는 학생만 개별로 입장시키는 방식이나 학생에게 PIN을 배포하는 방식으로 몰래 바꾸지 않는다. 다른 의미가 필요하면 이 지점만 확인하고 나머지 개발은 계속한다.

모든 실제 방은 zoneId별 잠금 설정을 지원한다. 출입 로비/교실 공개 입장 경로는 유지한다. 초기 잠금 대상은 명시적으로 표시하고, 모든 방을 일괄 잠가 제품을 못 쓰게 만들지 않는다. 관리자는 방별 PIN 변경·잠금·해제·열어 둠을 제어한다. 기본 초기 PIN 값은 비공개 설정 노트를 참조하고 공개 명세/소스에 넣지 않는다.

문 닫힘과 보안 잠금을 구분한다. 잠금 시 이미 안에 있는 사람의 퇴로를 막거나 사람을 문에 끼이게 하지 않는다. 잠긴 방 밖에서 도구 ray·보드 편집·파일 요청 등으로 비공개 데이터에 접근하는 경로도 검사한다. 3D 벽만 세우고 방 안의 모든 협업 데이터를 전원에게 전송해 비밀이라고 주장하지 않는다. 단순 게임 문 잠금과 기밀 데이터 경계를 구분한다.

### 실제 관리자와 세션 호스트의 분리
시뮬레이션 호스트는 먼저 들어온 학생일 수 있다. 호스트가 됐다는 이유로 관리자 PIN을 보거나 변경하게 하지 않는다. `displayName='관리자'`, `isHost`, 클라이언트 role, URL query는 운영 관리자 인증이 아니다.

PIN 원문·공개적으로 검증 가능한 짧은 PIN의 hash·관리자 토큰을 JS/GDScript/PCK/GLB/소스맵/HTML/공개 README/저장 파일에 넣지 않는다. VITE_*나 빌드 환경변수로 바꿔도 브라우저에 포함되면 비밀이 아니다. 클라이언트 난독화로 감추었다고 하지 않는다.

실서비스의 '관리자만 안다'를 충족하려면 신뢰된 서버의 검증/비밀 저장과 실제 관리자 신원이 필요하다. 서버에는 salted password KDF와 시도 제한을 적용하고, 운영 관리자 계정/UID와 짧은 PIN을 함께 확인하는 기본안을 제시한다. 방별 잠금 명령은 session/zone/revision/만료에 바인딩된 검증 가능한 결과를 사용하고 재생·위조를 거절한다. 공개키만 브라우저에 둘 수 있고 private key는 서버에 둔다.

4자리 PIN은 가능한 값이 적으므로 긴 관리자 비밀번호나 계정 인증과 동등한 강도라고 말하지 않는다. 사용자 지정 초기값을 임의로 바꾸지는 말고, 변경 권고/시도 제한/실제 계정 인증을 함께 제안한다.

서버를 아직 쓸 수 없으면 신뢰된 호스트 메모리로만 동작하는 로컬 프로토타입은 가능하지만 '관리자만 아는 운영 보안'을 완료로 보고하지 않는다. 공개 서비스의 제한을 숨기거나 게임 코드를 공개해 놓고 무조건 비밀이 보장된다고 하지 않는다. 기존 Firebase 운영 변경은 별도 승인, 로컬 에뮬레이터 구현은 계속한다.

## 9. 총은 꺼내면 어디서나 작동한다

**집, 오피스, 회의실, 교실, 개인실, 마당, 게임 공간의 발사를 모두 허용한다.** 방별 비밀번호와 무기 권한을 연결하지 않는다. 특정 방에서 `allowed_weapon=false`로 자동 회수하거나 피해를 무효화하는 옛 동작을 남기지 않는다. 물리적 벽·잠긴 문을 뚫고 발사되는 뜻은 아니다.

기본 자유사격은 무제한 탄약, 좌클릭 누르고 연사, 즉각적인 로컬 발사 피드백, 호스트 확정 피해/KO/킬 게이지다. 제한 탄약 경기 모드는 명시적으로 선택하는 별도 게임 규칙이며 기본 발사를 막지 않는다. 어느 구역에서나 사용 가능과 초당 무한 이벤트 발생을 혼동하지 않는다.

이전 구현에서 반드시 추적할 경로:
`allowed_weapon`, `allowed_entry`, `entry_grants`, `weapon_grants`, `weapon_zones`, `game_gate`, `classroom` 무기 제한, `carry`, `place_object`, `fire_tag`, 피해 대상 체크, 상속된 `update_living`의 강제 drop, 라운드 종료의 grant clear, 저장/복원과 호스트 이전의 권한 복원, 웹 UI와 테스트.

같은 정책을 UI뿐 아니라 모든 권위 판정 경로와 회귀 테스트에 적용한다. 낡은 테스트가 이제 허용되어야 할 행동을 계속 금지하는지 확인하고, 최신 명세로 변경한 근거를 기록한다. 반대로 숫자/소유권/프로토콜/과속 요청 검증을 지워서 테스트를 통과시키지 않는다.

발사 가능 조건은 살아 있는 플레이어, 현재 소유한 총, 유효 입력/세션, cooldown, 명시한 장전 규칙, 총구가 물리적으로 막히지 않음이다. 사용자별 승인/지역 허가는 아니다. 명중·피해·방패 방향·HP·KO·복귀·킬/콤보 게이지·결과판은 모든 참여자에게 일치한다. 복귀 무적은 시간 상태이며 '회의실 무적 지역'으로 몰래 바꾸지 않는다.

회의 중에도 총은 쏠 수 있다. 다만 문서 입력·채팅·비밀번호 입력에 쓴 마우스 클릭이 발사로 전파되면 안 된다. 총알이 Google 원본이나 보드 내용을 삭제하지 않는다. 소리 믹싱과 개인 효과음 볼륨으로 업무 집중을 조절하되 무기 기능 자체를 금지하지 않는다.

## 10. 카카오톡식 채팅: 실제 메신저 UX

현재 최근 40개 텍스트 패널을 '채팅 있음'으로 완료하지 마라. 게임 위에 접기/펼치기 가능한 채팅 dock과 확장 workspace를 제공하고 화면 크기에 맞게 배치한다. 대화 중 마이크는 사용자가 정한 대로 계속 작동할 수 있지만 게임 키는 멈춘다.

### 대화 기능
- 세션 전체, 현재 Zone 대화, 선택한 참여자와 1:1 대화를 명시한다. 음성 발화 모드와 텍스트 채널을 분리한다. 근거리 버블은 별도 표시 옵션이며 모든 텍스트가 음성과 같은 거리로 사라지게 하지 않는다.
- 닉네임/작은 아바타, 시간, 날짜 구분, 읽지 않은 위치, 실제 delivery/read 상태, 입력 중 표시, 답장 인용, 반응/이모지, 내 메시지 수정/삭제 표기를 제공한다.
- 채널·메시지·파일 검색, 멘션, 알림/음소거, 공지 고정, 참여자 목록, 파일·사진 모아보기.
- Enter 전송/Shift+Enter 줄바꿈 설정, 한글 IME 조합 중 Enter 처리, 복사/붙여넣기·드래그앤드롭·멀티라인·스크롤 유지·새 메시지 점프를 검증한다.
- 보낸 메시지 queued/sending/accepted/delivered/read/failed의 의미를 구분한다. 실제 화면에 표시되지 않은 것을 읽음으로 만들지 않는다. 수정/삭제가 이미 수신된 사본을 완전히 회수한다고 약속하지 않는다.

### 데이터/권한
메시지는 messageId, channelId, sender의 연결 기반 ID, sequence/revision, type(text/image/file/system), replyTo, timestamps, reaction/edit/delete 상태를 가진다. 호스트가 주체와 채널 참여 자격을 검증하고 중복을 제거한다. 전원에게 먼저 보내고 DM만 UI로 감추지 않는다. 1:1을 E2EE로 구현하지 않았다면 호스트 중계 신뢰 한계를 안내하고 암호학적 비밀 대화라고 하지 않는다.

출입 승인 UI 폐기는 채팅 주체 검증·스팸 제한·첨부물 검증을 없애라는 뜻이 아니다. 사용자별 mute, 신고/관리 도구는 남길 수 있지만 이것을 옛 방 입장 허가 목록으로 되돌리지 않는다.

### 이미지·파일 업로드/전송
파일 선택, 여러 파일, 이미지 클립보드 붙여넣기, 드롭, 썸네일, 원본 확대, 파일명/용량/형식, 진행률·취소·재시도·다운로드를 제공한다. 초기 한도 제안은 파일당 20MiB, 동시 전송 2개이며 설정/실측으로 조정한다. 이미지 해상도·총 디코드 메모리·세션 총량을 별도로 제한한다. 큰 미디어를 로딩하면서 프레임이 멈추지 않게 한다.

jpg/png/webp는 서명과 디코드 결과를 검사하고 위험한 HTML/SVG/실행 코드는 자동 렌더하지 않는다. PDF/docx/pptx/xlsx 등 업무 파일은 검증된 미리보기 또는 다운로드로 처리하고 매크로/임베디드 코드를 실행하지 않는다. 파일명은 표시와 내부 storage key를 분리한다. 압축 파일은 기본 무차별 풀지 않는다.

첨부물 binary는 채팅 텍스트/세계 state와 별도 chunk transport로 보낸다. hash, size, chunk index, bounded queue, cancel/resume와 낮은 우선순위를 둔다. 전송이 수락되기 전 거대 메모리를 예약하지 않는다. bytes/chunks/시간 단위 rate limit을 두고 권한없는 파일Id 재요청을 막는다.

기본은 현재 세션 P2P 공유다. 수신자가 얻은 파일, 호스트가 갖고 있는 파일, 발신자에게만 남은 파일을 구분한다. 발신자가 나갔는데 사본이 없으면 '원본 제공자 오프라인'이라고 표시한다. 업로드라는 UX 용어를 쓴다고 중앙 서버 영구 저장이 생긴 것으로 표시하지 않는다. 영구 클라우드 파일함은 별도 선택 서비스/예산/보존 정책이 필요하다.

채팅 기록/첨부물의 기기 캐시와 공간 내보내기 포함 범위를 사용자가 선택한다. 기본 공동 저장에서 DM과 동의없는 사적 대화/음성전사를 제외한다. 잔존 사본·삭제 범위와 보관량을 표시한다. 파일의 MIME 검사나 checksum을 완전한 악성코드 검사가 끝났다는 뜻으로 쓰지 않는다.

## 11. 회의실: 가장 중요한 제품 기능

전문 메타버스의 대표 완성 장면은 회의실이다. 단순 테이블과 흰 패널 + 전체 화면 폼은 충분하지 않다.

긴 회의 테이블 또는 U자 좌석, 모든 인원의 앉기/기립 여유, 발표자 자리, 읽기 쉬운 주/보조 화면, 실제 화이트보드/펜 트레이, 마이크/스피커, 조명/블라인드, 자료 보관, 전원/케이블 디테일을 용도 있게 배치한다. 좌석에서 화면 글자 크기와 레이저 점이 보여야 하고 과한 반사·소음이 없어야 한다.

회의 UX는 의제·참석 → 자료 열기 → 발표/페이지/레이저 → 질문/손들기 → 보드/브레인스토밍/마인드맵 → 공동 보고서/표 → 결정/담당/기한 → 저장으로 이어진다. 각 단계가 기능 이름만 있는 메뉴면 미완료다.

현재 Google Docs/Slides/Microsoft Excel 링크 연동을 보존하고 실제 두 계정 원본 공동편집 검증을 추가한다. Google Sheets는 별도 선택지이며 Excel이라고 부르지 않는다. 원본 편집·게시용 보기·화면 공유·내장 협업 도구를 구별한다. iframe 정책이나 계정/공유 제한을 우회하지 않는다. 허용되는 임베드는 검증 후 적용하고 제한되면 원본 창/탭을 여는 실제 사용 흐름을 제공한다. 게시본만 보여주고 공동편집 완료라고 하지 않는다.

원본을 새 탭으로 여는 동안 호스트 탭 background 제한·음성·입력·세션을 검사한다. 강제 freeze 삭제만으로 모든 환경에서 호스트가 영구 실행된다고 보장하지 않는다. 필요하면 별도 창 배치/호스트 이전/사용자 승인된 지속 호스트를 명시한다.

내장 공동 보고서는 검증된 CRDT/OT와 한글 IME·커서·Undo·재접속 수렴을 갖춘다. 링크 목록은 원본 파일의 내용 백업이 아니다. PDF/이미지 슬라이드, 보드, 주석은 오프라인 내보내기/복원에서 실제 재현되어야 한다.

레이저는 손에 든 도구→ray/발표 표면→surface UV→발표자와 페이지 revision→모든 참여자의 동일한 점으로 이어져야 한다. 2D panel의 포인터만 보이는 구현, 오래된 페이지 위의 포인터, 좌표축 반전, 거리에 따른 오작동을 수정한다.

채팅 이미지/파일을 사용자가 선택해 회의 보드/발표 자료로 연결할 수 있다. 자동 공개나 외부 서버 업로드는 하지 않는다. 컴퓨터의 Google 검색은 실제 원본을 열되 검색어를 전체 채팅에 자동 전송하지 않는다.

## 12. 농구 — Roblox식 접근성과 납득되는 물리

이미 있는 V3 charge, spin, steal 경로를 기준으로 재현한다. 없다고 쓰고 같은 기능을 중복 구현하지 않는다.

명확한 상태: LOOSE → CATCH/CONTROL → DRIBBLE → GATHER/SHOT_CHARGE → RELEASE → FLIGHT/CONTACT → SCORE/REBOUND → RESET. 입력 주체와 소유권, 공의 실제 물리상태를 분리한다.

필수: 달리며 드리블, 손 바꾸기/크로스오버, 패스/캐치, 상대 타이밍 스틸과 공 경합, 보이는 슛 게이지, 릴리스 타이밍 피드백, 약한 선택형 조준 도움, 백스핀, 림/백보드/바닥의 서로 다른 접촉, 리바운드, 자유연습/짧은 팀경기/점수·재시작.

게이지는 charge/time과 실제 입력을 표시하고, green 영역을 사용하면 그것이 성공 확률/릴리스 오차 보정 중 무엇인지 명세한다. 'green이면 공 순간이동'은 하지 않는다. 스핀은 angular velocity와 접촉 마찰에 실제 반영하고 회전 텍스처만 돌리지 않는다. 스핀 자체가 모든 슛을 성공시킨다는 거짓 물리도 금지한다.

공·림·백보드·캐릭터의 단위를 확인하고 표면 재질을 calibration fixture로 비교한다. 정면/비스듬한 bank, rim in/out, swish, 아래→위/옆 통과, 고속 CCD, 중복 득점을 시험한다. 아래에서 밀어 넣은 공을 골로 세지 않는다.

슛·스틸·패스의 효과/음향/아바타 접촉과 공 상태가 같은 시점에 보여야 한다. 손과 공의 접촉 이벤트를 시각에 연결하되 점수의 진실은 호스트다. 경쟁 판정의 cooldown·거리·방향·지연 보정은 짧고 명확하게 하고, 모든 접촉마다 임의 확률로 공을 빼앗지 않는다.

참고작의 참가 흐름을 차용하되 현재 8인 기준에서 5v5를 완료했다고 주장하지 않는다. 1v1~4v4 중 실제 지원 모드를 안내한다. 인원 수 확장은 별도 부하 검증 후 한다.

## 13. 축구 — 손을 쓰지 않는 드리블과 경기 루프

기존 foot-touch impulse를 출발점으로 한다. 바닥 공에 접근해 이동하면서 발로 연속 터치·방향 전환·정지·짧은 패스·강한 슛·가로채기·볼 경합이 가능해야 한다. 손으로 집었다 내려놓는 절차를 정상 축구 흐름에서 제거한다.

공은 자석처럼 영구 접착되지 않고 자유 물리와 제한된 터치 impulse 사이에서 움직인다. 빠른 이동 때 터치 간격/힘, 감속 시 공과의 거리, 몸 방향/카메라 조준을 구분한다. 상대와 접촉시 룰에 따른 경합, 짧은 태클 동작과 cooldown, 골/경계선/재시작을 구현한다. 발 애니메이션 없이 멀리서 공만 움직이지 않는다.

기본 조작은 기존 E/Q/F 체계와 충돌하지 않도록 스포츠 맥락을 알려준다. 공 요청/팀 표시·패스 목표·슛 게이지·점수판·연습/라운드·관전 흐름을 제공한다. 공식 설명의 키 배치를 그대로 복사해서 전역 키 의미를 깨뜨리지 마라.

공 구름/스핀/바운스/벽 반사/골망 시각 피드백, 빠른 공·골라인 전체 통과·중복 골을 시험한다. 네트워크 지연 속 양쪽 화면에서 패스/골 결과가 일치해야 한다.

## 14. 총 게임 — 빠른 피드백과 완결된 규칙

Arsenal 등의 공식 경험/실제 확인 가능한 화면에서 조작·명중 피드백·명확한 점수·빠른 재시작 원리를 분석한다. 특정 저작물의 무기/캐릭터/맵을 그대로 추출하지 않는다.

전역 자유 발사 정책은 §9다. 전용 경기장에서는 추가로 준비·설명·카운트다운·라운드·팀/개인 점수·결과·재시작을 제공한다. 회의실과 집에서 발사는 가능하지만 경기장 밖 발사가 진행 중 공식 경기 점수를 자동 오염시키지 않도록 casual stats와 matchId를 분리한다. 발사 허가를 다시 구역에 묶는 방식으로 해결하지 않는다.

HP 감소/회복, KO/리스폰, 킬 게이지 증가/시간감소/사망시 변화는 설정 가능한 단일 CombatRules가 정의한다. 내장/웹 HUD·네트워크·저장 모두 같은 상태 계약을 따른다. 스폰 캠핑 완화는 짧은 respawn 시간 보호 등 상태 규칙으로 구현하며 사용자 요청을 무효화하는 회의실 금지 구역은 만들지 않는다.

사운드/발사 애니메이션·반동·히트마커·피해 피드백은 즉시 이해되게 조정한다. 시각 효과 pool과 발사율 제한으로 연사가 장시간 누적 비용/메모리를 만들지 않게 한다. 적절한 host validation을 없애는 것은 환각을 줄이는 방법이 아니다. 동작을 단순화하되 진실을 검증한다.

## 15. 음성·한국어 자막·방송실

근거리/현재 Zone/세션 전체 음성의 의미를 유지한다. 근거리는 사용자가 범위를 조절하고 실제 벽·문·층 경계를 반영한다. 전체 모드는 거리와 무관하게 전달한다. 이는 reverb를 과하게 넣는 뜻이 아니다. 수신 차단/개인 볼륨을 존중한다.

실제 마이크 선택, 레벨/테스트, PTT/열린 마이크, 에코/잡음/AGC 지원 확인, 재접속·autoplay·장치 분리·중복 재생·mute 이후 늦은 패킷을 처리한다. 타자 중 PTT 키가 글자 입력과 충돌하지 않게 한다.

한국어 STT는 현재 provider를 확인하고 실측으로 비교한다. 이름/수치/날짜/한영 혼합/회의 용어·조용한/잡음 환경·여러 화자를 시험하며 CER, 정의한 WER, 발화 종료→최종 자막 지연, FPS 영향을 분리한다. 기존 합성 6문장 수치를 실제 사람 정확도로 확대하지 않는다. 모델 지원·언어팩/가속기/용량·외부 전송 여부를 확인한다.

자막 interim/final·화자·순서·동일 utterance 갱신·크기/대비·스크롤을 처리한다. 녹음/전사는 별도 동의이고 원음은 기본 저장하지 않는다. 근거리/잠긴 회의실 대화를 자막이나 파일 라우팅으로 밖에 누출하지 않는다. 로컬 처리를 고른 사용자에게 외부 STT를 몰래 적용하지 않는다. 인식 실패는 표시하고 음성/텍스트 채팅을 유지한다.

방송실에는 콘솔/마이크/ON AIR·송출 구역·입력 레벨·시작/종료·공지문이 있다. 관리자 제어는 실제 신원/PIN 설정과 통합하고 단순 세션 호스트에게 관리자 비밀을 주지 않는다. 방송 시작 고지, 일반 음성/효과음 ducking, 종료 시 믹스 복귀, 방송 자막/공지 채널 연결을 실제 검증한다.

## 16. 고정 교실·짧은 초대·호스트/저장

기존 AAA-AAA 초대와 URL 복사, 시작 화면의 '교실' 카드를 보존·마감한다. 카드의 연결 중/열림/비어 있음/재시도/정원 초과를 실제 상태와 맞춘다. 주소 복사 성공 여부와 코드 형식을 명확히 한다.

교실 고정 주소 ≠ 현재 물리 호스트 ≠ 저장된 세계다. 빈 방의 첫 참가자가 호스트가 될 수 있어도 관리자는 아니다. PIN과 관리자 도구를 참가 호스트에게 자동 제공하지 않는다. 동시에 둘이 들어올 때 하나의 세션으로 합류하거나 명확히 충돌을 처리한다. 고정 peer alias의 사칭/점유 한계가 있으면 검증된 directory와 관리자 서명/권한을 분리하고 기존 무료 인프라의 한계를 설명한다.

상시 서버 없이 '아무도 없을 때도 모든 물리 계속 진행'을 보장하지 않는다. 기기 밖 자동 상태 복원을 요구하려면 별도 지속 저장이 필요하며, 기본 파일 저장 흐름을 몰래 클라우드로 바꾸지 않는다.

내보내기/가져오기는 집·오피스·확장 개인실·가구·조명·수납·보드·내장 문서·발표 첨부·선택된 공개 채팅/사진·게임 결과를 일관된 snapshot으로 보존한다. 외부 Google/Microsoft 링크와 원본 내용은 구별한다. PIN/관리자 token/원음/DM/동의없는 전사는 공동 파일에 넣지 않는다.

새 session epoch, 안전한 손/좌석 상태, 현재 관리자 정책으로 복원하고 옛 파일이 PIN/잠금 정책/호스트 권한을 덮어쓰지 못하게 한다. 비밀번호 hash도 모두에게 배포되는 저장 파일에 넣지 않는다. 입력 파일 검증·임시 복원·실패 시 현 세계 보존·버전 migration을 구현한다. 다운로드 요청을 실제 디스크 보관 확인과 혼동하지 않는다.

## 18. 시스템 구조: 큰 상속 파일에 새 코드를 계속 덧대지 마라

현재 개선된 모듈을 살리되 `v4/world.gd extends v3/world.gd`로 다시 거대한 상속 계층을 만드는 것을 기본 해법으로 삼지 않는다. 전체를 한 번에 지우지 않고 feature별로 회귀 시험과 함께 분리한다.

책임 경계 기본안:
```text
bootstrap / scene composition
session / transport / replication / authority
player motor / CameraRig / AnimationController / ContactIK
input context / UI focus / hotbar / actions
interactions / carry / throw / seats / fixtures
zone topology / room locks / trusted admin adapter
chat / channels / receipts / reactions / attachments
meeting / documents / board / presentation / laser
voice / captions / broadcast
sports basketball / football / scoring
combat / damage / respawn / effect pool
world generator / asset registry / save migration
telemetry / replay fixtures / tests
```

모든 모듈이 world의 Dictionary와 브라우저 전역을 마음대로 바꾸지 않는다. state owner, command, event, snapshot schema, 오류와 취소 흐름을 정한다. 외부 경계 데이터는 validation 후 안으로 들인다. UI의 색/패널 변경이 물리/네트워크 권한 코드를 건드리지 않아야 한다.

peer transport, engine state, slow attachments, STT inference를 분리한다. 거대한 첨부가 input/voice/lock event를 막지 않게 별도 우선순위와 backpressure를 둔다. 에셋 생성기는 에셋/데이터만 생성하고 런타임 .gd를 정규식으로 덮어쓰지 않는다. '파일을 작게 나눔'만으로 스파게티가 해결됐다고 하지 않는다.

## 19. 성능·품질 예산

대상 하드웨어/브라우저/해상도를 먼저 기록한다. 초기 2~8인, 대표 기기에서 1080p 60fps 지향·저품질 30fps 지향은 제품 목표이지 측정 전 보장값이 아니다. FPS 중앙값만 아니라 프레임 p95/p99, 메모리/GC, 물리시간, draw calls, 다운로드/PCK/GLB, STT 모델, 미디어/네트워크 큐를 분리한다.

LOD/culling/인스턴싱/텍스처 공유/물리 sleep/소리·효과 pool을 적용한다. 숨기기만 하고 다운로드를 모두 했다면 streaming이라고 부르지 않는다. 채팅 virtual list와 이미지 해제, object URL revoke, peer/audio track/timer 정리를 검사한다.

미술을 보강한 대표 회의실을 원격 캐릭터·보드·채팅 이미지·음성·STT와 함께 측정한다. 구조 전체를 지우거나 대화·게임을 꺼야만 목표가 나오는 최적화는 요구 충족이 아니다. 한 PC의 8개 브라우저 표본은 다른 8대의 성능이 아니다.

## 20. GPT-6 Astra 계열 개발 에이전트에게 요구할 실행 방식

사용자가 원하는 것은 짧은 시간에 대충 끝내지 않고 스스로 문제를 찾아 고치는 개발이다. 특정 모델명만으로 자율성·정확성·실제 도구 접근·무한 실행이 보장된다고 쓰지 않는다. 현재 런타임이 제공하는 높은 추론/실행 설정이 있으면 그 기능 범위에서 사용하되 없는 API 옵션을 만들어내지 않는다.

'최소 몇 시간 생각' 또는 인위적인 sleep을 품질 장치로 쓰지 않는다. 내부 사고 과정을 공개하도록 요구하지도 않는다. 대신 의사결정 요약과 실제 실행 증거를 남긴다.

각 작업 단위에서 다음 루프를 실행한다.
1. Observe: 실제 코드·이벤트·로그·화면·재현 입력을 수집한다.
2. Specify: 사용자에게 보이는 기대 동작, 실패 조건, 담당 모듈/상태를 정한다.
3. Compare: 최소한 합리적인 대안/기존 구조 활용 여부를 비교하고 선택 근거를 짧게 남긴다.
4. Implement: 하나의 확인 가능한 변경을 구현한다.
5. Execute: 같은 경로로 실제 실행하고 before/after 자료를 만든다.
6. Critique: 기능 QA와 미술/UX QA를 별도로 실시한다.
7. Repair: 발견한 결함을 수정하고 관련 회귀를 실행한다.
8. Record: 통과/실패/미실행, Build ID, 남은 제약과 다음 작업을 기록한다.

실제 도구가 여러 에이전트를 지원하면 코드·미술·QA 담당을 나눌 수 있다. 그렇지 않으면 같은 에이전트가 관점을 분리해 검토하되 독립 심사자가 실제로 존재한 것처럼 쓰지 않는다. 병렬 작업에는 파일 소유 범위/통합 계약을 정하고 같은 파일을 무작위로 덮어쓰지 않게 한다.

실패한 테스트의 기대값을 현재 버그에 맞춰 낮추지 않는다. placeholder, 숨긴 오류, 하드코딩된 성공 메시지, 사용하지 않는 클립, bodyCount만 확인하는 테스트로 통과시키지 않는다. UI/golden screenshot을 바꿀 때는 시각 차이와 이유를 검토한다.

미술 QA는 0~4 기준의 architecture/material-lighting/animation/UI/interactions/meeting-clarity를 사용해 최소 3 수준(실사용 가능한 일관성)을 목표로 한다. 점수만 쓰지 말고 각각 실제 화면과 결함 목록을 첨부한다. 자기평가는 사용자 미술 승인이나 외부 품질 인증을 대체하지 않는다. 더 좋은 이미지를 새로 생성해 현재 실제 게임 캡처처럼 제출하지 않는다.

동일 원인의 반복 실패가 계속되면 진단을 변경하거나 막힌 조건을 보고한다. 무한 retry/과금/공개 서버 부하 시험을 하지 않는다. 시간·권한·도구 제한에 도달하면 진행 파일을 남기고 부분 완료로 명확히 끝낸다. 대화가 끝난 뒤 백그라운드 작업이 지속된다고 약속하지 않는다.

### 작업 컨텍스트를 설계하라 — 거대한 프롬프트 반복 금지

이 통합 명세는 요구사항의 원본이지 매 작업마다 전부 펼쳐놓을 유일한 지시 파일이 아니다. 저장소의 `AGENTS.md`는 짧은 실행 지도(목표·최신 정책·명령·핵심 경로·금지사항·검증 방법)로 관리하고, 세부 명세는 미술/카메라/채팅/방 잠금/게임/회의/저장/검증 문서로 나눈다. 이전 V1~V3의 폐기된 정책을 활성 문서에서 명확히 표시하고, 최신 요구와 테스트 ID의 연결을 유지한다. 문서를 복제해 서로 다른 정답을 만들지 않는다.

`TASK_STATE.md`에 현재 Build ID, 최우선 결함, 담당 파일, 재현 절차, 최근 실행 결과, 미완료 항목, 다음 한 가지 작업을 기록한다. 각 구현 단계는 관련 명세·현재 코드·직전 실패 증거만 추가로 읽어 집중한다. 전체 요구 범위는 추적표로 보존하되 한 번에 전부 변경하지 않는다. 한 단계의 완성도 높은 결과를 요구 전체의 완료로 보고하지 않는다.

## 23. 최종 산출물·완료 보고

실행 가능한 Godot 프로젝트·고정 템플릿/의존성·실제 GLB/애니메이션·Blender 원본과 제작 스크립트·웹 bridge/채팅·저장 schema·보안 검증 adapter·테스트·한국어 README·라이선스 고지·승인된 배포 결과를 제공한다. PIN/키/개인정보/폰트 무단 재배포는 산출물로 넣지 않는다.

기능표에는 '없음/설계/구현/가상 검증/실사용 검증/제약'을 구분한다. 모든 기능에 이름을 붙이고 '완료 100%'라고 쓰지 않는다. 보고서는 의도→관찰된 결함→원인/가설→변경→실행 결과→잔여 위험 순서로 짧고 추적 가능하게 작성한다. 실제 실행 커맨드와 종료 코드·화면/영상의 Build ID를 첨부한다.

이전 약 62개 클립, 67개 파일 hash, 수십 개 테스트는 존재/무결성/일부 동작의 증거일 뿐 전문적인 미술·완전한 조작감의 증거가 아니다. 이 차이를 끝까지 유지한다.

**최종 기준: 친구들이 고정 교실에서 만나 자연스럽게 3인칭으로 이동하고, 전문적인 회의실에서 자료와 이미지를 채팅으로 주고받으며 함께 문서를 만들고, 집에서 사물을 사용하고 쉬며, 농구·축구·사격을 납득되는 조작으로 즐기고, 관리자만 각 방 잠금을 관리하면서 전체 세계를 저장·복원할 수 있는가? 실제 화면·입력·네트워크·소리·파일 결과로 답하라.**
