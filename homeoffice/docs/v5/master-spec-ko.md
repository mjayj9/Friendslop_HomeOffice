## 0. 역할·제품 목표·이번 작업의 성격

너는 Godot 멀티플레이 엔지니어, 환경·건축 레벨 디자이너, Blender 캐릭터·애니메이션 아티스트, 테크니컬 아티스트, UI/UX 개발자, QA 역할을 수행하는 구현 에이전트다. 역할별로 결과를 검토하되 실제 별도 에이전트나 사람 검수가 없었다면 있었다고 표현하지 마라.

목표는 **친구들과 생활하고, 실제 업무·회의를 하고, 완성된 운동·게임을 경험할 수 있는 전문 협업·생활 메타버스**다. 기본 세계는 HOME, OFFICE, SPORTS/PLAY가 목적과 동선에 맞게 구분되는 하나의 장소다. 현재처럼 기능을 얹은 프로토타입에 머무르지 말고 건축·모델·물리·애니메이션·조작·소리·협업이 일관되게 작동하는 결과를 완성하라.

이번에는 단순히 방을 더 만들거나 텍스처를 바꾸거나 애니메이션 개수를 늘리지 마라. 책상 지지 구조, 가까운 화장실, 계단의 실제 연결, 착석 접촉, 들고 있는 의자와 몸의 분리, 코트 전용 동작처럼 **사용자가 보고 느끼는 구체적인 결함을 재현하고 수리**하라.

프로젝트 가칭 COMMONS WORKSPACE와 기존 저장소/URL을 유지한다. Friendslop이라는 이름 때문에 품질이 낮아졌다고 단정하거나 Three.js가 본질적으로 저품질이라고 주장하지 마라. 현재 엔진은 Godot/Jolt이며 사용자의 ‘초보 Three.js 느낌’은 구현·미술·경험의 품질에 관한 표현이다.

큰 스케일의 설계를 허용하되 빈 공간이나 미완성 기능으로 규모를 부풀리지 마라. 한 구역의 완성은 스타일·기술 기준을 확인하는 중간 단계이지 전체 제품 완료가 아니다. 개발 순서는 나눌 수 있지만 이 문서의 기능을 조용히 선택사항으로 내려놓지 마라.

이 문서의 공간 치수, 허용 오차, 예시 상태명은 **구현을 위한 설계 제안**이다. 사용자가 원래 지정한 값, 건축 법규, 상용 게임의 내부 구현으로 표시하지 마라. 공식 규격을 선택할 때는 해당 출처와 적용 범위를 별도로 기록하라.

## 2. 기존 환경과 작업 안전

Godot/GDScript와 검증된 웹 export를 유지한다. 현재 조회한 엔진/템플릿은 Godot 4.6.1, 물리는 Jolt다. 작업 시 실제 버전과 웹 지원을 다시 확인하되, 이름이 더 최신이라는 이유만으로 엔진을 교체하지 마라. Compatibility 렌더러와 웹 실행에 맞는 자산/조명/오디오를 검증한다.

BlenderMCP는 사용자가 포트 9876에 연결했다고 알려 준 제작 도구다. 실제 도구 목록·씬 조회로 연결을 확인한다. 원본 씬을 보존하고 새 컬렉션/파일로 작업한다. 포트를 외부에 열거나 배포 게임이 그 포트에 접속하게 만들지 마라. 프로토콜 불일치가 있으면 기록하고 무단 업그레이드하지 마라.

남자 GLB 원본과 13본/62클립 파생본이 현재 저장소에 기록되어 있다. 원본·가공본·실제 런타임 사용 파일을 먼저 대조한다. 없거나 사용자가 지정한 모델이 아닐 때만 다음과 같이 요청한다.

> 사용할 남자 캐릭터 GLB 원본을 업로드해 주세요. 리깅·애니메이션·텍스처가 별도 파일이라면 함께 보내 주세요. 기존에 올린 원본이 확인되면 다시 요청하지 않고 그 모델을 보존해 개선하겠습니다.

사용자는 GitHub 학생 Pro와 기존 Firebase Blaze, 비용 보호 설정을 사용한다. 현재 V4에는 Clerk 개발 공개 설정이 추가되어 있다. 인증을 다른 서비스로 재작성하거나 기존 Firebase/Clerk/비용 설정을 임의로 바꾸지 마라. 관리자 서버의 배포·보안 설정과 게임 개발은 별도 작업이다. 추가 비용 0원을 목표로 하며 유료 STT, TURN, 상시 GPU/게임 서버를 자동 도입하지 마라.

이 문서를 전달받은 것만으로 원격 push·PR 병합·운영 배포·새 결제·기존 데이터 삭제에 대한 포괄 승인이 생기지 않는다. 사용자가 허용한 범위에서만 실행하고, 로컬/에뮬레이터/검토 브랜치 작업을 분리한다.

## 3. 현재 저장소를 먼저 진단하라 — 오래된 분석 재사용 금지

현재 HEAD, 배포 ref, Build ID, PCK/WASM/JS/asset hash를 기록한다. 이 문서 작성자는 내려받은 Pages 아티팩트의 73파일 크기·SHA-256 일치를 확인했으나 직접 게임 플레이에는 접근하지 못했다. 따라서 다음 항목은 **현재 소스 사실과 재현 과제**이지 모든 증상의 확정 원인이 아니다.

1. `art/author_v4_meeting.py`에는 ConferenceTop, Pedestal, PedestalFoot가 있다. ‘책상 다리를 모델링하지 않았다’고 단정하지 말고 사용자가 보고 있는 objectId를 고정한 뒤 원본→export→mesh packing→GLB→런타임 가시성·재질·LOD·중복 메시를 추적한다. 다른 종류의 책상은 별도로 확인한다.
2. `world/meeting_finish.gd`는 새 상판 충돌체와 마감을 추가하면서 기존 ID/좌석을 유지한다. 시각 메시가 바뀌었는데 좌석·손·충돌 기준이 옛 치수로 남아 있는지 조사한다.
3. `tools/design_v2.py`의 오래된 큰 중앙 홀, 구석 화장실, 계단과 개인실 확장 좌표에 새 마감을 얹는 구조다. 필요하면 인접 관계를 재설계하고 저장 좌표 마이그레이션을 제공한다. 색만 바꾸지 마라.
4. `scripts/v2/avatar.gd::animate()`는 여러 if가 한 clip을 순차적으로 덮어쓴다. clip 이름이 바뀔 때 play하는 구조이므로 ‘매 프레임 무조건 play한다’고 오진하지 않는다. 경계값 진동·pose 우선순위·원격 grounded 판정·gesture 만료·state 갱신을 계측한다.
5. `player/contact_ik.gd`는 발 앵커의 문턱 갱신, 종류별 손 목표 오프셋, 가상 손끝을 사용한다. 명시적인 foot-contact curve와 시간 기반 IK weight가 충분한지 확인한다. 애니메이션과 IK가 서로 다른 목표를 강제하는지 A/B 시험한다.
6. 일반 3인칭, 메신저 파일/이미지, 전역 사격, 농구 스핀/스틸, 축구 발 터치, 회의 링크/레이저, 방송, 교실은 이미 코드에 존재한다. 다시 ‘없다’고 쓰지 말고 실제 연결과 품질을 평가한다.
7. `security/room_access.gd`의 ‘잠금을 열면 누구나 진입’과 이번 ADMIN_ONLY는 다르다. 별도의 역할 검증을 넣는다.
8. README/TASK_STATE에 운영 관리자 UID/PIN 검증 서버가 아직 미연결로 기록되어 있다. 로그인창 표시를 관리자 인증 완료로 취급하지 않는다.
9. 기존 `activities.mjs` 카탈로그 버튼→build_begin 방식과 최신 드래그 패널 방식의 차이를 실제 UI로 조사한다.

각 결함은 `symptom → reproduction → evidence → hypothesis → isolated test → root cause → fix → regression` 형식으로 남긴다. 직접 재현하지 못한 원인은 가설이라고 명시한다. 기존 해결을 되돌리거나 전체 앱을 또 작은 시제품으로 교체하지 마라.

## 4. 브라우저·게임 영상·현실 공간 자료 조사

외부 자료는 이 문서 말미의 [S01–S18]에서 시작하되 구현 시 다시 접근 가능성과 내용을 확인한다. 공식 자료는 관찰 기준이지 게임 코드/모델을 무단 복제하는 허가가 아니다.

### 4.1 게임명 해석

‘EA SPORTS NBA’는 EA의 **NBA LIVE**를 우선 참고 후보로 삼는다. NBA 2K를 EA 작품으로 표시하지 마라. ‘EA SPORTS ONLINE’은 **FC ONLINE**을 우선 후보로 삼고, EA FC 26 개발 설명은 다른 작품의 보조 자료라고 구분한다. 작품·연도가 추가 지정되면 그 자료를 우선한다. 현재 서비스 운영 여부나 최신작 지위를 확인 없이 주장하지 마라.

Roblox는 블록형 외모를 복제할 대상이 아니라 카메라·캐릭터 이동·액션 전이·조작 피드백을 분석할 대상이다. VALORANT는 총기의 화면상 무게감, 반응과 피격 정보, 라운드/지도 완결성을 분석한다. 고유 맵·캐릭터·UI·음원·브랜딩을 복제하지 않는다.

### 4.2 실제 영상 관찰 산출물

공식 게임플레이 또는 원출처가 분명한 실제 플레이 영상을 브라우저에서 재생한다. 제목·검색 요약·자동 자막만 읽고 장면을 봤다고 하지 마라. 영상 재생이 막히면 접근 실패를 기록하고 접근 가능한 원자료/사용자 제공 영상으로 보완한다. 관찰하지 않은 타임스탬프를 만들지 마라.

농구/축구/사격 각각 다음 기록을 작성한다.

| 기록 필드 | 내용 |
|---|---|
| 출처·신뢰성 | URL, 게시 주체, 작품/버전, 공식 소개인지 실제 플레이인지 |
| 관찰 장면 | 실제 시작/끝 timestamp와 재생 속도 |

| 피드백 | 게이지·조준점·소리·명중·득점·오류 안내 |

농구는 무볼 준비, 수비 사이드스텝, 손 교체 드리블, gather, 릴리스, 착지, 리바운드를 본다. 축구는 첫 터치, 보폭과 볼 터치의 관계, 급회전, 패스 지지발, 킥 후속 동작, 가로채기를 본다. 사격은 장착, 견착, 이동 중 조준, 발사와 회복, 재장전, 피격 정보, 라운드 재시작을 본다.

현실 공간은 평면도·가구 제품 치수·실내 사진을 함께 검토한다. ‘사진이 예쁘다’만으로 끝내지 말고 화장실 접근, 방문자 동선, 조리 순서, 의자 뒤 여유, 창과 화면의 눈부심, 문 회전 공간을 도면에 적용한다. 접근하지 못한 유료 설계 지침 전체를 읽었다고 주장하지 마라.

## 5. 전체 건축 기본안 — 집/회사/스포츠의 목적 분리

다음은 사용자 요구를 구체화한 **기본 설계안**이다. 더 나은 안으로 변경할 수 있으나 공간/기능을 삭제하지 말고 인접성과 동선을 설명한다.

```text
정문·안내 / 공개 도착 로비 / 고정 ‘교실’ 입장
    │
    ├─ OFFICE 동
    │    리셉션·대기 → 중앙 업무 홀 → 주회의실 ↔ 자료·브레인스토밍
    │                            ├─ 소회의실·전화 부스
    │                            ├─ 공동 업무실 → 확장 개인실 복도
    │                            ├─ 프린트·문서 보관 / IT·관리 수납
    │                            ├─ 가까운 화장실 / 팬트리
    │                            └─ 방음 전실 → 방송실
    │
    ├─ 중정·연결 갤러리·테라스·공용 휴게
    │
    ├─ HOME 동
    │    현관·수납 → 거실 ↔ 식당 ↔ 주방 ↔ 팬트리
    │                 ├─ 손님용 화장실·세탁/다용도
    │                 └─ 실제 계단·계단참 → 침실/수면실
    │                                      ├─ 욕실·린넨 수납
    │                                      ├─ 의상방·거울·꾸미기 콘솔
    │                                      └─ 독서·휴식
    │
    ├─ 자유방 / 소품 실험 / 공룡 아케이드 / 전술 게임 공간
    │
    └─ SPORTS 관리 경계 [ADMIN_ONLY]
         출입 전실 → 농구관 → 운동 용품·장비 수납
                  └─ 축구장 → 벤치·탈의·샤워/화장실·볼 보관
```

오피스와 집은 방 이름표뿐 아니라 외관, 실내 재료, 음향, 가구, 조명, 동선에서 구별된다. 같은 세션의 연결된 공간으로 유지하고 모든 방을 순간이동 메뉴에만 의존시키지 않는다. 스포츠 관람 통로도 관리 경계를 침범하면 안 된다. 일반 학생에게 코트를 열어 주는 기능을 기본으로 추가하지 마라.

스케일이 커져도 구조 없이 넓히지 않는다. 전체 부지 크기는 축구장·농구관과 건물 동선을 배치한 뒤 정한다. 105×68m 피치를 택하면 그 부지와 여유 공간을 실제 도면에 넣고 기존 66×86m 부지 안에 억지로 구겨 넣지 마라. 넓은 장소와 지원 동시 접속자 수는 별도다.

## 6. 회사·집의 공간 프로그램과 인접 관계

화장실은 매 층의 공용 동선에서 도달하고, 다른 사람의 개인실·침실·관리자 전용 코트를 통과해야만 사용할 수 있게 하지 마라. ‘화장실이 외딴 곳에 있다’는 문제를 텔레포트 버튼으로 덮지 말고 평면 인접 관계를 고쳐라. 주방과 욕실을 위아래/인접 서비스 영역에 배치해 배관이 있을 법한 구조를 만들되 게임에 실제 설비 공학 계산까지 추가할 필요는 없다.

계단은 현관/홀에 계획된 수직 동선이어야 한다. 예시로 층고 3.3m, 20단×0.165m, 디딤판 약 0.28m, 유효 폭 약 1.4m, 충분한 계단참의 U자형을 검토할 수 있다. 실제 단수·평면 길이·개구부·난간·머리 여유를 계산하고, 2층 슬래브에 출구가 없는 계단을 만들지 않는다. 이는 설계 제안이지 법규 적합 선언이 아니다.

## 7. 건축 산출물과 모델 품질 기준

구현 전에 부지 배치, 층별 치수 평면, 계단 단면, 문·창·개구부, 사용자/방문자/관리 동선, 음성 구역, 관리자 코트 경계, 개인실 확장 예약 영역을 제출한다. 설계 데이터와 실제 모델을 연결하고 변경 시 동기화한다.

각 가구·시설은 다음을 갖춘다.

```text
assetId / assetVersion / 원본·라이선스
실제 단위와 local origin / 피벗 / 방향 / AABB
시각 메시 + 지원 장치에서의 LOD
물리 충돌체 + 질량·마찰·반발 또는 정적 상태
grip_left / grip_right / seat_hip / feet / approach / stand_exit 등 필요한 anchor
사용 가능한 행동 + 상태 + 동기화 + 저장 정보
카탈로그 thumbnail + 크기·용도
```

책상은 반드시 네 다리일 필요는 없다. 중앙 받침·패널 다리·벽 지지 등 형태에 맞는 지지 구조가 시각적으로 납득되어야 한다. 공중에 상판만 남거나 다리가 바닥 밑으로 사라지는 것이 실패다. 상판 아래, 좌/우 측면, 가까운 캐릭터 시점에서 실제 export를 확인한다.

의자·소파는 몸이 닿는 좌판과 등받이, 팔걸이, 발 위치를 모델과 함께 설계한다. 액션마다 별도의 수치 오프셋을 하드코딩하여 대충 맞추지 않는다. 화장실은 평면 위의 작은 표지판이 아니라 방의 벽·문·칸막이·기구·수건·거울·조명·재질까지 구현한다. 노출이나 선정적 연출 없이 시설 사용·수도·물내림·문 점유를 표현한다.

유사한 장식 큐브 수백 개를 세밀한 모델링이라고 부르지 마라. 필요 부위에 베벨·두께·이음·손잡이·기능 피벗을 주고, 타일/목재 텍스처는 실제 방향과 반복 크기를 맞춘다. 아틀라스/재질 공유/정적 메시 통합은 허용하되 사라진 받침, 뒤집힌 법선, alpha 문제, 겹친 메시, collision과 분리된 시각을 반드시 검출한다.

최종 미술 검수는 Blender 렌더가 아니라 같은 Build ID의 실제 Godot 웹 장면에서 한다. 전문적이라는 자기 선언이나 개수 점수로 사용자 미술 검토를 대체하지 않는다.

## 8. 캐릭터·애니메이션: 다리 떨림과 관통을 먼저 해결

### 8.1 계측으로 원인 분리

같은 캐릭터·경로에서 `애니메이션만`, `IK만`, `둘 다`, `원격 보간 포함`을 비교한다. 최종 게임에서는 미완성 경로를 숨기지 말고 디버그 시험에서만 분리한다.

로컬/원격별 현재 locomotion state, activity profile, posture, clip, 이전→새 clip 전이, normalized phase, speed_scale, 실제 속도, grounded, 좌/우 foot contact, IK weight, foot target, 발 위치 오차, actionId, snapshot tick을 기록한다. 안정된 보행 동안 불필요한 clip 재진입·위상 초기화·IK target jump가 반복되는지 찾는다.

30/60/높은 렌더 FPS와 지연 상황에서 같은 물리 이동이 보행 주기를 폭주시켜서는 안 된다. dt를 두 번 적용하거나 물리·렌더 양쪽에서 애니메이션 시간을 전진시키지 않는다. 원격 캐릭터의 `is_on_floor()`가 권위자 접지와 같은 의미인지 확인하고, 원격 이동을 단순 위치 보간하는 경우 접지는 권위 상태로 전달한다.

### 8.2 애니메이션 구조

단일 AnimationTree/애니메이션 소유자에서 다음 층을 명확히 합성한다. 구체적 API는 실제 Godot 버전에 맞춰 검증한다. [S03, S04]

```text
Locomotion: idle / start / walk / jog / run / strafe / pivot / stop / airborne / land
ActivityProfile: HOME / OFFICE / BASKETBALL / FOOTBALL / COMBAT
Posture: standing / crouched / seated / lying / sleeping / knocked_out
UpperBody: none / carry / book / marker / rifle / shield / ball_gather
OneShot: pickup / throw / shot / pass / kick / interaction / gesture
ContactCorrection: 명시적 foot/hand curve의 가중치에 따른 마지막 보정
```

모든 것을 하나의 문자열 clip에 순차 덮어쓰지 마라. 예를 들어 ‘뛰면서 총을 듦’은 하체 이동과 상체 도구 자세가 양립해야 한다. ‘앉아서 책 읽기’는 착석 자세 위 상체 행동이며 공중 점프 전이가 덮어써서는 안 된다.

속도 경계에 hysteresis·최소 유지 정책을 두고 start/stop/turn이 매 프레임 다시 시작되지 않게 한다. 보행 clip의 phase를 이어서 블렌딩하고 좌우 발 지지 구간을 보존한다. 걸음의 빈도는 실속도·보폭과 일관되어야 하며 목표 재생률을 급격히 튀게 만들지 않는다.

Blender 클립마다 `duration / loop / entry / exit / interrupt / root-motion policy / foot contact L/R / hand contact / release event / reference / tests`를 기록한다. 물리 위치와 root motion을 동시에 전체 적용해 이중 이동시키지 마라. 준비·접촉·체중 이동·릴리스·회복을 갖춘 실제 key pose를 만들고 단순 sin 흔들림의 이름만 바꾼 다수 클립으로 대체하지 않는다.

### 8.3 리그와 발·손 접촉

사용자 남자 모델의 외관과 원본을 보존하되, 13본이 손목·발끝·의상 조정에 부족하면 필요한 체인과 웨이트를 제대로 보강한다. 본 수 목표를 임의로 채우는 것이 아니라 골반·척추·목·쇄골·팔·손목/손·다리·발/발끝의 실제 작업 역할을 정한다. 모든 기존 클립은 rest pose와 축 규약에 맞게 리타깃한다.

발 고정은 **애니메이션의 stance 구간**에서만 적용하고 swing에서는 부드럽게 해제한다. 광선이 바닥에 닿는다고 항상 발을 붙이지 않는다. IK target은 시간 기반으로 보간하고 접촉점 변경을 제한한다. 계단에서 골반 높이, 발 법선, 무릎 pole, 다리 길이를 함께 고려한다. 손·발 해가 나오지 않으면 관절을 비정상 늘리지 말고 목표를 제한하고 행동을 조정한다. 발 지지면 탐색에서는 자기 몸과 현재 들고 있는 물건을 제외해 의자/총이 발의 바닥이 되는 오류를 막는다. 움직이는 지지체를 지원한다면 접촉점은 지지체 로컬 공간에 고정하고 그 운동을 반영한다.

rest/global/local/bone 공간을 명확히 하고 애니메이션·IK·원격 상태가 같은 본을 독립적으로 덮어쓰지 않도록 한다. 캐릭터 체형이 바뀔 때도 앵커·바닥·손끝 관계가 다시 맞아야 한다.

### 8.4 검수할 행동 묶음

일상 대기·시선·걷기·달리기·후진·사이드스텝·가속/감속·회전·계단·경사·점프·착지·웅크리기, 가벼운/무거운 물건 집기/들기/내리기/던지기, 의자/소파 착석/기상, 침대 눕기/취침/기상, 책/보드/컴퓨터/요리/식사/스위치/문/방송, 스포츠와 사격 전용 동작을 모두 연결한다.

각 동작은 1배속의 체감과 0.25/0.5배속의 접촉을 정면·측면·후면에서 검수한다. [S02] 총 클립 수가 아니라 이 검수를 통과한 행동을 보고한다.

## 9. 소파·의자·들고 있는 물건의 관통 방지

좌석은 `approach → reserve → align → sit_enter → seated → stand_exit → release`로 처리한다. 좌석마다 seat_hip, back direction, foot support, 접근 경로, 여러 출구, 좌우 사용자 점유 부피가 있어야 한다. 캐릭터 원점을 좌판 원점으로 옮기는 것만으로 착석을 끝내지 않는다.

소파는 쿠션별 슬롯과 실제 몸 폭을 고려한다. 옆 사람이 있으면 누울 수 있는 범위를 확인한다. 체형을 키운 사용자가 옆 슬롯과 겹치면 슬롯 간격·가능 여부를 조정한다. 충돌을 모두 끄는 방식으로 화면상의 관통을 숨기지 마라. 앉은 의자를 다른 사람이 집거나 지워 사용자가 떨어지게 하지 않는다.

의자를 들 때는 두 손 그립 위치와 의자의 전체 부피를 고려한다. 의자 중심을 가슴 안에 놓지 마라. 충돌 예외가 필요한 경우 holder↔held pair에만 적용하고, 바닥·벽·다른 사람과의 충돌은 적절히 유지한다. 내려놓기와 던지기에서 중력·속도·충돌 예외·점유 상태를 복원한다.

마카의 펜촉, 총의 손잡이/총구, 공의 릴리스, 책 양쪽 그립, 접시 운반, 의자 팔걸이/등받이의 grip anchor를 asset에 저장한다. 임의 ±0.13m 손 오프셋만으로 모든 물건을 맞추지 않는다.

검증: 의자·소파·침대 각 10회 이상 왕복, 접근 각도 변경, 주변 장애물, 다른 사용자 경합, 최소/기본/최대 체형, 1·3인칭, 원격 관찰에서 같은 행동을 확인한다. 횟수는 최소 재현 계획이며 10번 성공이 모든 조합의 무오류 보장을 뜻하지 않는다.

## 10. 이동·카메라·물리 제어

Roblox의 Character Controller Library처럼 ‘어떤 행동이 가능한가’와 ‘이번 틱에 어떻게 이동하는가’를 분리하는 원리를 참고하되 엔진과 코드를 복제하지 않는다. [S01]

카메라 기준 이동, 가속·감속, 경사, step-up/step-down, 계단참, 점프/착지, 작은 문턱을 별도 시험한다. 카메라 pivot과 캐릭터 회전을 분리하고 정지 상태의 orbit가 몸을 무한히 떨게 하지 않는다. 구체 기반 카메라 충돌과 근접 fade를 검증하고 좁은 문·천장·계단 아래에서 뷰가 벽 안에 들어가지 않게 한다.

1인칭과 일반 3인칭을 유지하며 스포츠 구역에서는 전용 3인칭 기본값과 사용자가 조절할 수 있는 거리/감도를 제공한다. 스포츠 진입 시 원치 않는 급격한 FOV·화면 흔들림을 강제하지 않는다. 조준점에서 보이는 표적과 실제 손 총구의 가림을 함께 판정한다.

물리는 1 unit=1m를 기준으로 크기·질량·중력·반발·마찰·angular damping을 일관되게 맞춘다. 검증된 Jolt 설정을 먼저 조정하고 ‘더 전문적인 엔진으로 변경했다’는 문구만으로 개선을 주장하지 않는다. backend 교체가 필요하면 동일 실험 장면 A/B와 웹 지원 결과를 제시한다.

고정 물리 tick, 렌더 보간, 입력 예측, 호스트 판정, 네트워크 보정을 분리한다. 중요한 공과 빠른 물건은 연속 충돌을 사용하고 충돌을 늘린다고 모든 오차가 해결되는 것으로 보지 않는다. 스스로 쌓이는 물체의 에너지, 벽 관통, 소파 무한 반동, 스폰 위 충돌을 시험한다.

## 11. 관리자 전용 농구·축구 구역과 자동 활동 프로필

### 11.1 권한 정책

농구장·농구관과 축구장은 ADMIN_ONLY다. **문이 열려 있음, 호스트임, PIN 입력 UI가 보임, 관리자 닉네임임**은 관리자 신원의 근거가 아니다. 운영 검증된 관리자 identity/capability를 사용한다.

`RoomLock`과 `ZoneAccessPolicy`를 구분한다. 다른 방의 잠금 해제는 공개 진입으로 이어질 수 있지만, 두 스포츠 구역은 열려 있어도 비관리자의 경계 통과·스폰·텔레포트·저장 복원·호스트 이전으로 들어갈 수 없어야 한다. 코트 내부 공 사용/점수/장비 행동도 권위자가 검증한다.

현재 관리자 서버가 미연결이면 일반 사용자에게 **잠금 유지(fail-closed)**하고 사유를 표시한다. 임시 관리자 fixture는 로컬 자동 시험에만 두고 운영 코드에서 자동 승격하지 않는다. 인증 미완료를 이유로 코트 모델/게임 로컬 구현 전체를 중단하지도 않는다.

클라이언트에서 이미 내려받은 3D 메시의 열람까지 완전히 막는다고 주장하지 마라. 진입·공유 상태 변경의 권위 검증과 자산의 기밀성은 다른 문제이며 P2P 호스트의 신뢰 한계도 명시한다.

관리자만 1명이라면 자유 연습·시간 도전·봇 상대 훈련이 가능해야 한다. 여러 관리자 계정의 동시 경기 테스트가 필요하면 시험 계정을 사용하되 학생에게 권한을 자동 부여하지 않는다. 봇은 사람이 접속한 숫자에 합산하지 않는다.

### 11.2 코트 진입과 경기 시작 분리

```text
ZonePresence: OUTSIDE → ENTERING → INSIDE → EXITING
ActivityProfile: DEFAULT / BASKETBALL / FOOTBALL
MatchPhase: PRACTICE / READY / COUNTDOWN / PLAY / RESULTS
BallState: FREE / CONTROLLED / GATHER / RELEASED / CONTESTED
```

농구장에 들어오면 경기를 시작하지 않아도 basketball_ready, 운동용 jog/stop/pivot/defensive shuffle, 스포츠 카메라가 활성화되어야 한다. 공이 없으면 무볼 자세다. 공을 잡거나 드리블할 때만 해당 공 동작을 재생한다. 축구도 football_ready, 작은 운동 보행·턴·수비 자세가 적용되고 실제 터치할 때만 킥/패스 이벤트가 발생한다.

입장 transition은 한 번만 재생한다. Area 중복/경계 왕복에서 여러 번 중첩되지 않게 debounce/유효 경계를 관리한다. 구역을 나가면 일반 프로필로 부드럽게 복귀한다. 옷과 외형을 자동 변경할 필요는 없고, 원하는 운동 의상은 의상방에서 선택한다.

총을 들고 코트에 들어간 관리자는 스포츠 기본 하체와 전투 상체의 우선순위를 명시적으로 처리한다. 활동 프로필 때문에 전역 총 사용 규칙을 몰래 취소하지 마라.

## 12. 농구: EA 농구 경험을 참고한 전면 플레이 재설계

EA NBA LIVE의 움직임과 1대1 상황이라는 참고점 [S05]을 실제 플레이 장면으로 확인하고, 단순 공 던지기에서 완결된 농구로 발전시킨다. 내부 애니메이션/물리 알고리즘을 안다고 주장하지 않는다.

코트는 한 규격 체계를 선택한다. 기본안은 [S14]의 28×15m 경기면·링 윗면 3.05m다. 이는 NBA 공식 코트와 같다고 표시하지 않는다. NBA식으로 바꾸려면 [S16]을 따라 선·골대·보드·3점선 등을 함께 바꾼다. 규격이 다른 수치를 섞지 않는다.

경기면 외에 사이드/엔드 여유, 실제 골대 지지 구조·패딩, 링·백보드·네트, 점수판·시계, 벤치·공 보관·코트 출입·관전 위치를 배치한다. 네트와 골대가 공의 통로를 막지 않게 하고 코트 바닥과 선의 높이가 물리적으로 돌출되지 않게 한다.

무볼 준비 → 공 받기 → 드리블 → 크로스오버/방향 전환 → 수비와 스틸 → gather → 슛 → 착지 → 리바운드의 상태와 입력을 설계한다. 카메라 방향과 몸 방향, 양손의 공 접촉, 지지발을 맞춘다. 달리면서 드리블 clip만 전신 재생해 다리가 원래 이동과 충돌하게 하지 않는다.

보이는 슛 게이지는 힘·릴리스 타이밍·가능 거리의 의미가 명확해야 한다. 공은 손에서 실제로 놓이는 순간 초기 선속도·각속도를 받는다. 현 코드의 백스핀 경로를 보존·개선하고, 회전 방향·크기·접촉 마찰이 납득되는지 확인한다. 스핀만 넣으면 자동으로 득점하는 것으로 설계하지 않는다.

슛 arc·릴리스 높이·방향·속도·이동 중 몸속도·백보드/림 반발을 함께 조정한다. 정상적인 swish, bank shot, rim-out이 모두 나와야 한다. 몰래 골대로 당기는 힘이나 득점 순간 teleport로 문제를 덮지 마라. 조준 보조를 제공한다면 명시적으로 표시하고 강도를 설정한다.

스틸은 거리·시야·공 노출·드리블 phase·쿨다운으로 권위 판정한다. 성공 즉시 상대 손의 강제 제어가 해제되어 루즈볼/새 소유로 넘어간다. 리바운드·블록·패스 차단도 공과 신체의 실제 타이밍에 맞춘다. 영구 소유권 때문에 어떤 수비도 불가능한 구조는 불합격이다.

자유 연습, 시간제 슈팅, 제한된 인원/봇의 반코트·전체 경기 중 완결된 지원 모드를 구현한다. 모든 모드는 시작/정지/득점/결과/재시작이 있고, 위→아래 링 통과만 한 번 득점하며 2·3점 판정을 선택 규칙과 연결한다. 계정·인원 제한 때문에 아직 완결되지 않은 모드는 완료로 표시하지 않는다.

## 13. 축구: FC ONLINE/EA FC를 참고한 발 제어·접촉·경기

FC ONLINE 공식 조작과 실제 플레이를 우선 보고 [S06], EA FC의 애니메이션 분기·터치 간격·입력 반응성 설명 [S07]은 보조로 구분한다. 두 제품의 기능을 같은 것으로 단정하지 않는다.

큰 완성형 경기장 기본안으로 FIFA 권장 105×68m 피치 [S15]를 검토한다. 친구 규모의 활동에는 별도 소규모 연습 영역과 봇 훈련을 제공할 수 있다. 큰 경기장으로 바꿨다고 네트워크 22인을 지원하는 것은 아니다.

잔디, 선, 골대·네트, 코너, 주변 여유, 벤치, 볼 회수, 점수판, 탈의·샤워·화장실·장비 동선을 함께 만든다. 출입 권한은 11절을 따른다.

공은 손으로 들 필요 없이 발 가까이에서 제어한다. 낮은 속도 작은 터치, 달릴 때 길어진 터치, 급회전의 발 디딤과 몸의 기울기, first touch, 패스와 킥의 지지발/follow-through를 구현한다. 발이 공에서 멀리 있는데 공 속도만 바뀌는 장면은 실패다.

공을 발 앞 transform에 매 프레임 붙이지 마라. 실제 물리 공을 유지하고 접촉 가능 거리, 발 터치 impulse, 잠깐의 제어, 상대 접근과 루즈볼을 설계한다. 달리는 사람에게 매 틱 foot_touch gesture를 덮어써 다리가 흔들리지 않게, 발 touch 이벤트를 보행 phase와 연결한다.

짧은 패스, 강한 슛, 낮은/높은 궤적, 트래핑, 가로채기/태클, 공 보호, 경계 밖 재개, 골 이후 킥오프를 연결한다. 과한 자석 보조나 상대를 무시하는 소유권을 금지한다. 골 판정은 선택 규칙에 맞는 골라인 전체 통과와 중복 방지를 다루고, 네트 충돌로 공이 무한 증폭되지 않게 한다.

혼자 사용 가능한 드리블 코스·패스 표적·슈팅/골키퍼 훈련과 지원 인원의 경기를 완성한다. 경기 AI를 구현한다면 이동 목표·수비·패스/슛 판단과 실패를 보이는 방식으로 검증하고 실제 선수 AI 수준이라고 과장하지 않는다.

## 14. 사격: VALORANT의 완성 원리를 적용한 자체 전술 게임

전문적인 사격은 명중 점수만 바꾸는 선과 소리가 아니다. [S08, S09]의 무기 식별과 피격의 정확성/명료성을 참고하여 입력·손 모델·애니메이션·반동·소리·피격·지도·라운드를 하나로 완성한다. VALORANT의 서버 인프라/치트 방어/자산을 그대로 재현했다고 주장하지 마라.

권총·소총·근거리 자동화기처럼 기능이 구별되는 자체 가상 무기를 정의한다. 실제 총기 사용법이나 실물 제작이 아니라 게임 수치와 피드백을 구현한다. idle/equip/aim/fire/recoil recovery/reload/empty/holster를 1인칭 손 모델과 원격 3인칭 몸체 모두에 연결한다.

견착 위치, 오른손/보조손 grip, 실제 muzzle socket, 시선/총구 가림, 조준 전환, 이동 정확도 변화, 연사 recoil/spread/recovery, 탄피/명중 표면 효과, 거리별 소리를 설계한다. 무작정 큰 화면 흔들림으로 ‘무게감’을 만들지 않는다. 효과 감소와 음량 설정을 제공한다.

로컬 총구 효과/소리는 반응성을 위해 즉시 보여 줄 수 있으나 피해·킬 확정 표시는 권위 응답과 구분한다. 입력 sequence/shotId/틱, 중복 발사, 쿨다운, 소유권, 적정 timestamp, 사거리·가림을 검증한다. 제한된 지연 보정을 도입한다면 과거 판정 범위와 현재 충돌 정책을 문서화한다. P2P 호스트를 변경할 수 있는 사용자를 완전히 막는 상용 anti-cheat라고 하지 마라.

기본 자유사격은 총을 들면 전 구역에서 작동한다. 회의실·집·교실을 hidden safe zone으로 바꾸지 않는다. HP·피격·KO·킬 게이지 증감·방패·안전한 복귀를 유지한다. 문서/채팅/의상/설치 패널 입력은 게임 발사로 전달되지 않는다.

별도로 **완결된 하나의 자체 전술 지도와 경기 모드**를 만든다. 시작 구역, 복수의 읽기 쉬운 경로, 엄폐, 시야 길이, 양쪽 동선, 관전/점수/재시작을 갖춘다. 라운드는 준비→시작→전투/명시적 목표→승패→다음 라운드로 이어진다. 별도의 탄약·장비 규칙은 사용자가 선택한 경기에서만 적용하며 일반 월드의 자유사격을 몰래 제한하지 않는다.

거대한 빈 사각형에 표적 3개를 놓고 전술 FPS 완료라고 하지 마라. 동시에 모든 상용 FPS 시스템을 이름만 나열하지 말고 지원하는 모드를 실제 플레이로 완결한다. 기존 회의·생활 소프트웨어와 통합된 성능·입력·저장 규칙도 지킨다.

## 15. 옆 패널 ‘물건 설치함’과 드래그 배치

항상 찾을 수 있는 ‘물건 설치’ 버튼을 제공한다. 누르면 화면 옆 패널이 열리고 월드가 계속 보인다. 카테고리, 검색, 실제 썸네일, 이름, 크기, 주요 행동, 설치 가능한 면/구역을 제공한다. 기존 B키가 있으면 보조로 유지할 수 있지만 화면 버튼과 drag 방식은 필수다. 의상방의 단축키 금지와 혼동하지 마라.

```text
패널 열기 → 카드 잡기 → 패널 밖 3D 화면으로 끌기
→ 실제 지지면 위 고스트 표시 → 유효/무효 표시
→ 포인터 놓기 → 호스트 검증 → 객체 1개 생성
```

단순히 버튼을 누르면 정면에 spawn하는 것으로 대체하지 않는다. ‘설치함 drag’와 ‘게임 안 물건 집기’는 다른 입력 모드이고, 드래그 중 클릭이 다른 UI 버튼이나 총 사용에 중복 전달되지 않아야 한다. UI drag가 진행되는 동안 pointer lock을 해제하고 카메라 회전·총 발사·물건 던지기를 차단한다. 패널 위치·브라우저 확대·DPR·Godot viewport 스케일·캔버스 letterbox를 반영해 화면좌표→카메라 ray를 정확히 계산한다.

바닥 배치, 책상 위 배치, 벽 장착 등 asset별 규칙을 적용한다. preview는 영구 객체/물리 장애물이 아니어야 한다. 지지면 경사, 전체 AABB/compound collider, 문 스윙, 계단·스폰·동선·좌석, ADMIN_ONLY 영역을 검사한다. 막힌 위치는 이유와 함께 거절한다.

회전·grid snap·표면 정렬을 제공하고, 패널 안에서 놓기/화면 밖 drag/포커스 상실/취소에서 객체가 생기지 않게 한다. 허용된 단 한 번의 drop만 requestId로 확정하고 재전송은 중복 생성하지 않는다. 두 사람이 같은 위치에 동시에 놓으면 호스트가 한 번씩 일관되게 판정한다.

Godot Control drag/drop 또는 JS overlay 방식 중 실제 구조에 맞는 하나를 선택한다. UI 구현 [S17]과 월드 배치 검증은 별도 책임으로 분리한다. 배치 후 기존 E집기·Q던지기·F사용·재배치·철거·내보내기/복원까지 연결한다.

## 16. 의상방에서만 가능한 캐릭터 편집

### 16.1 진입·권한·종료

HOME 동에 옷장, 전신 거울, 중립 조명, 회전해 보는 피팅 공간, 얼굴 그리기/체형/의상 콘솔을 가진 **실제 의상방**을 만든다. 사용자가 그 방에 가서 거울/콘솔의 ‘꾸미기 시작’을 직접 클릭하면 자기 캐릭터 편집이 열린다.

전역 단축키, 지도에서 원격 열기, ESC메뉴의 ‘외형 수정’으로 진입시키지 않는다. 다른 방에서 명령을 위조해 열거나 적용하는 것도 세션 규칙에 따라 거절한다. 열린 편집 UI 안의 Tab 이동·Undo·Esc 닫기 같은 접근성은 허용하되 ‘장소를 우회하는 열기 단축키’는 만들지 않는다.

시작 시 원래 외형을 보존하고 변경은 로컬 preview에 먼저 적용한다. 적용/취소/초기화/의상방 이탈/재접속을 처리한다. 실제 사용자 신원에 연결된 자기 외형만 수정하며 다른 사람의 프로필을 바꾸지 못하게 한다. 적용되지 않은 초안이 모두에게 마구 방송되지 않도록 한다.

### 16.2 얼굴 직접 그리기

안전한 얼굴 UV 캔버스와 회전 가능한 3D 미리보기를 제공한다. 브러시, 색, 굵기, 불투명도, 지우개, 되돌리기/다시하기, 초기화, 선택적 좌우 대칭, 레이어의 기본 기능을 제공한다. 얼굴 영역 마스크로 다른 몸 재질까지 오염시키지 않는다.

그린 결과는 실제 캐릭터 얼굴 텍스처에 나타나야 하며, 2D 메모장만 만들어 두지 않는다. 얼굴과 피부의 경계, 뒤집힌 UV, 투명도, 멀리서 읽히는 품질을 확인한다. 기본 텍스처 크기/레이어 수/압축 용량은 웹 예산에 맞게 정하고 화면에 안내한다. 예: 1024px 이하의 얼굴 텍스처는 시작 제안이지 고정 요구가 아니다.

텍스처는 PNG/WebP 등 허용 래스터로 검증하고 이미지 헤더/실제 디코드/픽셀 수/용량을 검사한다. HTML/SVG/실행 코드/임의 material shader를 얼굴 데이터로 받지 않는다. 썸네일과 실제 얼굴 자산의 hash/version을 사용하고 다른 캐릭터와 material 리소스를 공유해 전원의 얼굴이 바뀌지 않도록 한다.

실명·얼굴 사진 업로드나 생체 인식을 요구하지 않는다. 사용자는 직접 그리는 기능을 요청했다. 부적절한 사용자 그림에 대한 신고·기본 얼굴로 개인 숨김 같은 최소 운영 처리를 제공할 수 있으나 몰래 파일을 외부 분석 서버에 보내지 않는다.

### 16.3 몸 모양·의상

키, 어깨 폭, 몸통·팔/다리 비율, 체격처럼 의미가 다른 조절 축을 제한된 범위에서 제공한다. 단순 비균일 전체 scale로 사람·리그·충돌체를 찌그러뜨리지 마라. 필요한 blend shape, bone scale, 보정 shape, 의상 fitting을 조합하고 동작 안정성을 확인한다.

체형을 바꾸면 카메라 높이, capsule, 바닥 접촉, 보행 보폭, 좌석 골반/발, 손 grip, 도구/공 socket, 문/계단 통과를 함께 검토한다. 극단적 sliders 조합은 금지하거나 보정한다. 범위는 최소/기본/최대 체형 시험으로 정하고 근거 없이 무한 조절을 제공하지 않는다.

상의·하의·신발·색/재질 등을 실제 메시/허용 자산으로 선택한다. 의상이 몸이나 소파를 통과하지 않도록 변형과 마스킹을 검증한다. 사용자 남자 모델을 우선하며 다른 성별 모델을 임의로 추가하는 작업은 하지 않는다.

체형이 사격·스포츠의 속도/피해/힘에서 숨은 유불리를 만들지 않도록 표준 경기 프로필과 시각 커스터마이징의 관계를 정한다. 작아진 몸의 hitbox와 보이는 몸의 불일치를 숨기지 말고 경기 시 외형 보정/공통 범위 정책을 명시한다.

## 17. ‘교육용’ 입장 문구는 표시 전용

입장 화면 하단에 다음과 같은 작은 안내 문구를 표시한다.

> 교육용으로 활용할 수 있는 메타버스입니다.

이는 제품의 실제 활용 가능성에 관한 안내이며 학교·교육청의 승인/인증을 주장하지 않는다. 사용자가 원하는 정확한 문구가 정해지면 카피만 바꾼다.

이 문자열은 locale/UI copy 모듈에만 둔다. `educationMode`, `isStudentMode`, 학습 진도, 수업 점수, 과제 검사, 퀴즈, 교사용 기능을 자동 생성하지 마라. 무기 사용·스포츠 권한·채팅·디자인·캐릭터·장면 구성은 이 문구를 읽거나 파싱해 결정하면 안 된다.

회귀 시험에서 문구 표시/숨김 또는 동등한 카피 교체를 해도 입력·방 접근·게임·외형·저장 규칙이 바뀌지 않음을 확인한다. ADMIN_ONLY 코트는 사용자 명시 정책으로 독립 설정한다.

## 18. 회의실·회사 업무 기능 — 미술과 실제 협업을 함께 완성

회의실의 책상 형상과 좌석에서 보드·화면·서로의 얼굴이 보이는 관계를 먼저 정한다. [S11] 정면 좌석을 늘리는 것만이 답이 아니다. 참가 인원/화면 위치에 맞게 U자/타원/라운드 코너 등을 선택하고 스크린 글자가 후면 좌석에서도 읽히는 실제 테스트를 한다.

좌석·화면·보드·마카·레이저·자료 콘솔·마이크·시계·발언 표시·공동 자료 공간을 한 장면에 통합한다. 탁자 지지대와 소파/의자 접촉, 발 여유, 통행, 문 열림, 눈부심을 함께 검수한다. 소품이 장식처럼 보여도 요청된 도구라면 실제로 사용할 수 있어야 한다.

Google Docs·Slides·Microsoft Excel의 원본 공동작업을 유지한다. 실제 같은 원본을 서로 다른 계정이 편집하는 것과 HTML 링크 버튼/내장 Yjs/PDF를 구분한다. 임베드 제한은 공식 허용 방식으로 처리하고, 원본 새 창 흐름이 필요한 경우 사용자에게 표시한다. 원본 서비스의 공유 권한과 게임 역할은 별개다.

자료 준비→의제→발표→질문/손들기→보드/브레인스토밍/마인드맵→공동 보고서→결론/할 일→자료/세계 내보내기가 연결되어야 한다. 텍스트 입력 중 WASD·공격·설치가 실행되면 실패다.

물리 레이저는 손 도구의 ray→표면 local 좌표→자료/page ID→권위/발표자 확인→원격 포인터를 따른다. 패널의 pointermove만 작동하는 결과로 대체하지 않는다. 문서 팝업/탭 사용 중 호스트가 백그라운드가 될 때의 진행·인계·복귀를 시험한다. 제한을 숨기거나 background throttle이 사라졌다고 주장하지 마라.

## 19. 생활·메신저·음성·방송을 회귀시키지 마라

기존 집기·던지기·수납·서랍·문·스위치·전등·컴퓨터 Google 검색·책 읽기, 요리→담기→운반→식사→정리, 소파 휴식/점프, 침대 취침/기상, 화장실/욕실 시설의 실제 상태를 유지하고 새 모델에 재연결한다. 같은 기능이 다른 방마다 다른 키가 되지 않도록 한다.

메신저는 채널/공간/DM, 답장·반응·읽음·검색·편집/삭제, 이미지·파일·붙여넣기/drag, 썸네일·확대·다운로드, 전송 실패/취소/재시도를 유지한다. P2P 파일 전달과 서버 보관을 구분하고, 발신자가 나가 받아올 수 없으면 사실대로 알린다. 큰 첨부물이 음성/이동/슛 판정을 막지 않도록 한다.

근거리/공간/전체 음성, 거리 조절, 마이크·상대 음량·눌러 말하기, 한국어 실시간 자막, 방송실 콘솔·ON AIR·공지·송출 종료를 유지·개선한다. 실제 마이크·한국어 인식 품질·자막 지연을 측정한 것과 합성 입력을 구분한다. 원음과 개인 대화는 기본 기록하지 않는다. 교육 안내 문구를 이유로 상시 녹음·감시를 만들지 마라.

P2P 직접 연결 성공·공유 시그널링·TURN 필요 상황은 구분한다. 무료 계정이라고 모든 네트워크에서 항상 연결되는 것으로 쓰지 않는다. 서버형 기능을 새로 추가하면 비용과 운영 전제가 먼저다.

## 20. 세션·권한·개인실·고정 교실

기술 호스트, 실제 관리자, 일반 참여자, 실제 공간 Zone, 로그인 신원, 캐릭터 entity ID를 분리한다. 문/코트/방송 정책과 물리 호스트의 임의 명령을 혼동하지 않는다. 관리자 PIN은 공개 소스/PCK/JS/설정/로그/저장 파일에 넣지 않는다. 초기 PIN은 별도 비공개 설정으로만 취급한다.

짧은 AAA-AAA 코드, 실제 초대 URL 복사, 시작 화면의 고정 ‘교실’을 유지한다. 고정 링크·현재 호스트·영구 저장은 다른 기능이다. 빈 교실에서 세션을 여는 흐름, 동시 입장, 오래된 alias/host 종료, 재접속을 처리한다. 시그널링 장애를 가짜 접속 성공으로 표시하지 않는다.

개인실은 안정적인 roomSlotId에 연결하고 참가자 증가 시 복도 끝에 실제 새 방/복도/문/조명/충돌/음향 구역을 추가한다. 기존 사람과 가구를 이동시키거나 퇴장만으로 방을 삭제하지 않는다. 새 건축 설계의 확장 예약 영역을 사용해 욕실·계단·코트와 겹치지 않게 한다.

## 21. 전체 내보내기/가져오기와 레이아웃 변경 호환

공간 전체 파일 저장은 유지한다. 대표자가 호스트 확정 상태를 한 시점에 내보내고, 다음 세션은 한 사람이 가져와 모두 같은 세계로 합류한다. 브라우저 종료 이벤트만 믿지 않는다.

새 건물 배치를 만들 때 `layoutVersion`과 stable asset/entity/roomSlot ID를 관리한다. 기존 absolute 좌표를 그대로 새 벽 속에 넣지 않는다. 이전 방 로컬 좌표→새 대응 방 좌표로 안전하게 마이그레이션하거나 복원 미리보기와 충돌 해결을 제공한다. 변환할 수 없는 항목은 목록으로 알리고 사용자 동의 없이 버리지 않는다.

저장 대상은 구조 버전·확장 개인실·가구·시설·보드·내장 문서·발표 첨부·일반 설정·필요한 게임 결과다. 외부 Google/Excel 링크와 실제 원본 내용 백업은 구분한다. 얼굴/의상 프로필과 허용된 래스터 자산은 별도 버전/사용자 매핑으로 복원한다.

관리자 identity/PIN/token/서명키/실시간 잠금 우회 권한, 원음, 동의 없는 DM을 export에 넣지 않는다. 저장 파일의 old admin role로 운영 관리자 권한을 얻지 못하게 한다. 새 세션은 운영 권한을 다시 검증한다.

가져오기는 버전·용량·압축 해제 한도·경로·ID·수치·허용 asset·참조·이미지 decode를 검증하고 임시 상태에서 성공한 뒤 교체한다. 실패하면 현재 세계를 보존한다. 임의 코드/scene/shader를 실행하지 않는다.

## 22. 시스템 구조 — 기능·자산·화면이 같은 규약을 쓰게 하라

기존 V2→V3 상속 위에 다시 거대한 V5를 얹는 것을 개편이라고 하지 않는다. 레거시 정상 동작을 시험으로 고정하고 아래 경계로 단계적으로 옮긴다. 파일명은 제안이며 핵심은 책임·상태·API의 단일 소유자다.

```text
core/                 AppState, typed command/result, event IDs, scene versions
network/              session transport, baseline/delta, prediction/reconciliation
identity/             actual user / simulation host / admin capability
access/               room lock, admin-only zones, signed policy verification
character/            motor, animation graph, contact solver, camera rig, avatar profile
interaction/          target resolver, carry, use, throw, seat, fixtures
building/             semantic layout, portals, stairs, private-room expansion
placement/            catalog, drag bridge, preview, support/collision check, commit
wardrobe/             physical entry station, face canvas, body/clothes, profile sync
sports/basketball/    activity profile, control, possession, shooting, scoring, match
sports/football/      activity profile, touches, pass/shot, goal, match, practice AI
combat/               weapons, aim/recoil, damage, HUD, round/arena
meeting/              whiteboard, documents, slides, laser, meeting flow
social/               chat, attachments, voice, captions, broadcast
persistence/          world/profile schemas, migration, import/export
presentation/         shared UI design system, localization, entry notice only
```

각 액션은 actor/epoch/sequence/requestId/target/action/data를 명시하고 호스트/검증 서버의 책임에 맞게 처리한다. 입력자가 보낸 UID/role/점수/HP를 그대로 믿지 않는다. 복제와 UI가 상태를 독립적으로 변경하지 않게 한다.

Godot world와 웹 bridge의 동일 정보를 중복 저장할 때 권위자와 캐시를 구분한다. 좌석·드래그·체형·스포츠·총이 제각각 다른 objectId/anchor 규약을 쓰지 않도록 한다. 코드 생성은 에셋/레이아웃 데이터에 한정하고 정규식으로 런타임 함수를 합치는 방식을 되살리지 마라.

## 23. 큰 세계의 웹 성능과 시각 품질

완성형 큰 공간은 LOD, 구역별 가시성, 정적/동적 분리, 재질 공유, 적절한 lightmap/정적 조명과 개별 스위치, 제한된 동적 shadow, 단순 compound collider, 물리 sleep, 효과 pooling으로 다룬다. 웹에 지원되지 않는 효과를 넣고 품질 개선 완료라고 하지 않는다. [S18]

큰 축구장 때문에 카메라 far, 구역 검색, 좌표/전송 범위, spawn/낙하 복귀, 오디오 거리, 내비게이션, asset streaming의 기존 상수를 전수 점검한다. 지금 보이지 않는 곳이라고 네트워크 권위 상태를 지워서는 안 된다. 구역을 나갔다 돌아와도 공/물건/문서 상태가 일관되어야 한다.

실제 하드웨어·브라우저·해상도·품질·참가 인원을 적고 목표/실측을 구분한다. 초기 2–8인 검증에서 게임·음성·자막·파일·커스터마이징 자산 전송을 함께 시험한다. 1080p 60FPS 지향·낮음 30FPS 지향은 목표이지 달성 보장이 아니다. 큰 경기장과 미술 완성도를 핑계로 브라우저를 멈추게 하지 않는다.

최종 보고는 median/p95 frame time, 메모리 변화, 네트워크 큐/왕복/손실, 게임 tick, draw calls와 자산용량을 함께 적는다. 같은 PC 여러 브라우저와 여러 실제 PC의 시험을 구분한다.

## 24. 자가 수정 루프·중간 게이트·완료 정의

‘오래 생각하라’는 인위적인 대기나 추론을 한 척하라는 뜻이 아니다. 사용 가능한 실제 모델 설정과 실행 도구를 활용하되 특정 모델명만으로 무한 실행·AAA 품질·정확도를 보장하지 마라.

반드시 아래 루프를 수행한다.

```text
현재 결과 관찰 → 실패 기준/재현 → 자료·대안 검토 → 설계
→ 하나의 검증 가능한 구현 → 실제 실행 → 기능 검수 + 시각/동작 검수
→ 가장 큰 결함 수정 → 같은 장면 재시험 → 주변 기능 회귀 → 기록
```

첫 번째 구현이 돌아갔다고 제출하지 않는다. 같은 증상을 최소 두 가지 가능한 원인으로 분리해 검사하고, 변경 전후 같은 장면·같은 체형·같은 입력 경로를 비교한다. 테스트가 잘못된 기대값으로 통과시키는지도 검토한다. 모든 작업에 끝없는 반복을 강제하지는 않되 차단 조건과 미완료를 숨기지 않는다.

중간 게이트:

- **A 기준/설계:** 최신 코드·배포 인벤토리, 실제 외부 조사 기록, 전체 평면/동선, 접근 정책, 리그/자산 규약을 확정.
- **B 움직임/접촉:** 남자 캐릭터 직선/회전/계단/착석/의자 들기에서 떨림·관통 원인을 수리. 체형 변경을 고려한 기준 rig.
- **C 공간 기준:** 전체 필수 구역이 연결된 블록아웃과 대표 회의실·집 한 구역을 실제 완성 자산으로 검토. 블록아웃은 최종 미술이 아님.
- **D 전문 기능:** 드래그 설치, 의상방, 자동 스포츠 프로필, 관리자 코트, 완결 스포츠/전술 모드, 회의·생활·메신저·방송을 완성.
- **E 전체 마감/회귀:** 나머지 모든 공간·가구·액션을 같은 기준으로 마감하고 저장 마이그레이션·멀티플레이·웹 배포 묶음까지 검증.

AGENTS.md는 짧은 실행 지도, 본 문서는 기준 명세로 둔다. TASK_STATE.md에 실제 build, 현재 가장 큰 결함, 관련 파일, 재현, 최근 결과, 다음 작업, 차단된 외부 계정/권한을 남긴다. 작업 한도를 만났다면 현재 상태와 재개 지점을 명시하지, 전체를 완료했다고 하지 않는다.

‘현실적·전문적·완벽’은 요구 방향이다. 최종 품질은 실제로 확인한 장면과 테스트로 설명한다. 코드 존재, 클립 62개, UI 버튼, 해시 일치, mock 성공, 과거 영상만으로 완성품을 주장하지 않는다.

## 25. 최종 산출물

실행 가능한 전체 Godot 프로젝트와 검증된 웹 export, Blender 원본과 제작 스크립트, 실제 GLB·리그·클립·contact curve·anchor manifest, 평면/단면/공간 프로그램, 공통 UI, 드래그/의상 편집, 운동/전투/회의/생활/음성 시스템, 저장·마이그레이션, 자동 및 수동 검증 도구, 한국어 실행/설정/배포 안내, 라이선스를 제공한다.

실제 실행한 것과 수동 대기 항목, 실제 관리자 검증과 fixture, 공식 설명과 실제 영상 관찰, Blender 렌더와 게임 캡처, P2P 저장과 서버 보관을 구분한다. 원본비교/결함 수리 보고서에 변경 전후·같은 build 검증·남은 한계를 남긴다.

권한이 없거나 브라우저/영상/Blender 접근이 차단되면 구체적으로 보고하고 독립적으로 진행 가능한 구현과 시험을 계속한다. 그 조건을 이유로 또 다른 기능 없는 프로토타입을 최종 납품하지 않는다. 운영 승인 없는 서비스 생성·배포·PIN 공개는 하지 않는다.

# COMMONS WORKSPACE V5 — 현재 코드 감사와 외부 조사 근거

작성일: 2026-09-17. 이 문서는 조사 결과와 제안의 구분을 위한 부록이다. 앱 수정·운영 배포·관리자 설정 완료 보고가 아니다.

## 1. 확인 범위와 한계

- GitHub 현재 main / codex/commons-workspace-v4 / codex/homeoffice-v3: `27dccb8adeccb51690a5f5c4abbebebf339b850c`.
- 가장 최근 조회된 Pages 배포: run `35205066858`, commit `968554abb7e19802085ef2c43abec2df628d0eda`, artifact `10489900909`.
- 내려받은 실제 Pages 아티팩트: Build ID `cc2f8fbd-ba33-4601-b716-82bb26422424`, source digest `d3f3b1f7bc2bd3343825fd5705089bd5a7807f1fb7cb8ccc3e333d5c12a62514`.
- 아티팩트 manifest의 73개 파일 크기/SHA-256을 검사했고 불일치 0개였다. 이는 내려받은 배포 묶음의 내부 무결성 검사이지 공개 origin의 응답이나 게임 품질 검증이 아니다.
- 저장소/배포 커밋 차이는 비교 API로 조사했다. 후속 커밋은 검증 기록을 갱신하는 커밋이다. commit 문자열과 dirty 표기만으로 옛 빌드나 소스 불일치를 단정하지 않는다.
- 공개 사이트는 웹 조회에서 Internal Error, 컨테이너의 공개 HTTPS 조회에서 DNS 실패가 발생했다.
- 실제 아티팩트의 로컬 브라우저 실행을 시도했으나 `ERR_BLOCKED_BY_ADMINISTRATOR`로 차단되었다. 보안 정책 우회는 하지 않았다.
- 따라서 이번 작성자는 최신 게임을 직접 플레이하거나, 사용자의 다리 떨림/의자 겹침/없는 책상 다리를 화면에서 재현했다고 주장하지 않는다.
- 외부 공식 문서와 게임 소개/개발 설명은 조사했다. 게임 영상의 실제 재생·프레임별 관찰은 완료하지 못했다. 아래 ‘영상 조사 과제’는 구현 에이전트가 수행할 작업이며 이미 관찰한 사실이 아니다.

## 2. 현재 소스에서 확인한 사실 / 해석 / 수정 과제

### F01. V4가 이미 반영되어 있다
현재 README와 TASK_STATE는 일반 3인칭, 메신저, 전역 사격, Clerk 개발 공개 설정, 회의실 마감 추가를 기록한다. 따라서 V3 기준으로 ‘텍스트만 있는 채팅’, ‘수면 외 3인칭 없음’, ‘무기 승인제 그대로’라고 현재를 진단하지 않는다. 기록에 존재하는 시험과 이번 독립 실행은 구분한다.

### F02. 책상 지지대가 소스에 전혀 없는 것은 아니다
`homeoffice/art/author_v4_meeting.py`에는 `ConferenceTop`, `Pedestal`, `PedestalFoot`를 생성하는 코드가 있다. `homeoffice/scripts/world/meeting_finish.gd`는 `meeting-finish.glb`와 상판 충돌체를 추가하고 기존 ID/좌석을 유지한다. 다른 책상까지 다리가 있다는 뜻도, 최종 화면에 제대로 보인다는 뜻도 아니다.

사용자 증상의 후보: 보고 있는 책상 종류 차이, export/mesh packing 누락, 가시성/LOD/재질, 중복 상판, 위치·스케일·원점, 그림자와 조명. 해당 objectId를 먼저 고정한 뒤 Blender→GLB→Godot→PCK→공개 화면을 추적해야 한다.

### F03. 건축은 여전히 이전 배치에 덧붙이는 성격이 있다
`tools/design_v2.py`는 중앙의 긴 홀, 한쪽 생활공간과 다른쪽 회의/자유공간, 구석의 화장실, 별동, 두 코트의 위치를 정의한다. 회의실 제작 스크립트는 명시적으로 기존 topology를 보존하는 additive finish다. 이는 미술 추가와 전체 인접 관계 재설계가 다른 작업임을 보여준다. 화장실이 잘못 배치되었다는 최종 판정은 동선·평면·실제 보행 검토가 필요하다.

### F04. 애니메이션 선택과 접촉 보정의 결합을 검사해야 한다
`homeoffice/scripts/v2/avatar.gd::animate()`에는 속도·방향·접지·동작·자세를 순차 if로 선택하고 마지막 clip을 덮어쓰는 흐름이 있다. 전이 임계값이 여러 군데 있고 `AnimationPlayer.play(name,.12)`는 이름 변화에 따라 실행된다. ‘매 프레임 무조건 play한다’는 주장은 하지 않는다.

`grounded_before`는 `is_on_floor()`에서 계산된다. 원격 캐릭터가 호스트와 같은 방식으로 이동 시뮬레이션을 수행하지 않는 경우 이 접지 판정의 의미를 별도 점검해야 한다. 코드만으로 사용자 증상의 단일 원인을 확정할 수 없다.

### F05. 발 IK의 목표와 손 그립이 단순화되어 있다
`player/contact_ik.gd`는 Animation 이후 두 링크 IK를 적용한다. 발 목표를 광선으로 찾고, 수평 .33m / 높이 .15m 등의 문턱으로 앵커를 갱신한다. 애니메이션의 명시적인 좌/우 발 contact curve와 가중치 혼합은 이 파일에서 확인되지 않는다. 함수의 `_delta` 인자는 실제 계산에 사용되지 않는다.

손 목표는 사물 종류별 상단 높이와 좌우 ±.13m 같은 오프셋으로 잡고 손목/손가락 대신 가상의 .24m 끝부분을 사용한다. 이것은 사용자별 체형, 소파/의자 실제 접촉점, 복잡한 그립을 검증할 필요가 있다는 근거이지 모든 겹침의 확정 원인은 아니다.

### F06. 애니메이션 ‘62개 존재’는 접촉 품질의 증거가 아니다
현재 진행 문서는 13 bones / 62 animations 파생본을 기록하면서 품질 인수가 남았다고 명시한다. 상태 수와 클립 수를 늘리는 것보다 phase, 접지, 전이, 그립, 리그 구조 및 체형 극값 검증이 우선이다.

### F07. 현 방 잠금은 새 관리자 전용 코트 정책과 다르다
`security/room_access.gd::blocks_entry()`는 잠긴 구역 경계 통과를 제어한다. 안내 문구는 관리자가 열면 누구나 들어가는 정책이다. 최신 요구는 농구/축구 코트에 관리자만 들어가는 것이므로 signed actor identity + zone role policy를 추가해야 한다. 문이 열렸다는 사실이 코트 사용권을 의미하면 안 된다.

### F08. 운영 인증 연결은 아직 미완료로 기록되어 있다
README/TASK_STATE에 Clerk 공개 설정과 UI는 연결됐지만 운영 관리자 지정/PIN 검증 서버는 아직 연결되지 않아 잠금/관리 방송이 비활성이라고 명시돼 있다. UI 로그인창 표시를 관리자 인증 완료로 바꾸면 안 된다. 코트는 운영 검증이 안 됐을 때 일반 사용자에게 fail-open하면 안 된다.

### F09. 소품 설치 UI의 현재 형태
다운로드한 `activities.mjs`에는 가구별 버튼을 클릭하면 build_begin을 요청하고 패널을 닫는 흐름이 있다. 사용자 최신 요구인 ‘옆에 열린 설치함에서 월드로 끌어 놓기’는 현재 방식의 이름 변경으로 해결되지 않는다. drag 좌표→실제 게임 viewport→raycast→미리보기→검증→확정을 통합해야 한다.

### F10. 이미 있는 것을 회귀시키지 않는다
현재 메신저/카메라/총/공 물리/Clerk adapter/자료 원본 링크/교실/내보내기 경로를 인벤토리화하고 재사용할 부분을 정한다. V2→V3 상속을 유지한 채 단순히 V5를 다시 상속하는 것만으로 모듈 구조를 개선했다고 주장하지 않는다.

## 4. 제목 해석과 영상 조사 과제

사용자의 ‘EA SPORTS NBA’는 EA의 NBA LIVE를 우선 후보로 삼았다. NBA 2K는 다른 제작사의 시리즈이므로 같은 것으로 쓰지 않는다. ‘EA SPORTS ONLINE’은 FC ONLINE을 우선 후보로 삼고, FC 26 개발 설명을 보조 참고로 구분한다. 특정 작품/연도/영상의 지정은 아직 없다.

구현 에이전트는 공식 게임플레이 영상과 원출처가 분명한 무편집 플레이 영상을 브라우저로 실제 관찰한다. 농구/축구/사격 각각 최소한 아래 플레이 사건을 확인한다. 영상 재생이 막히면 실패 이유를 쓰고 실제로 받은 영상/접근 가능한 자료로 보완한다. 제목이나 자동 자막만 읽고 프레임을 봤다고 하지 않는다.

- 공통: 정지→출발→방향 전환→정지, 카메라 가림, 상하체 분리, 이동과 접지.
- 농구: 무볼 준비, 수비 사이드스텝, 드리블 손 교체, gather, release, landing, rebound.
- 축구: 첫 터치, 작은 볼 터치, 급회전, 패스의 지지발, 킥 follow-through, tackle, 공 소유권 분리.
- 사격: equip, aim, shot, recoil recovery, reload, hit confirm, moving target, round transition.
- 가구: 의자/소파 접근, 정렬, 체중 이동, 착석, 일어서기; 사람과 가구의 기준점.

관찰 기록의 필수 필드: 출처 URL, 게시 주체, 작품/연도, 실제 관찰 timestamp, 재생 속도, 입력/상태, 접촉/무게중심, 카메라, 피드백, 그대로 적용하지 않을 요소, 자체 구현안, 실제 검증 방법. 이 문서는 아직 본 적 없는 timestamp를 만들어 넣지 않는다.

## 5. 보안·범위 메모

코트 관리자 전용은 최신 명시적 제품 정책이다. 처음 표시하는 교육용 안내 문구 때문에 자동 도입하는 기능이 아니다. 다른 방의 PIN 정책, 전역 총 사용 정책, 관리자와 시뮬레이션 호스트의 구분을 섞지 않는다. 비공개 PIN은 이 감사와 공개 프롬프트에 포함하지 않는다.


## 최종 실행 지시

위 명세 전체를 기준으로 먼저 현재 결함을 재현하고, 공간/리그/접촉/권한의 공통 기준을 확정한 뒤 실제 구현·수리·검수를 진행하라. 이 문서와 체크리스트를 다시 써 주는 것만으로 개발을 완료하지 마라. 각 N/T 항목에 실제 파일·Build ID·증거·결과를 연결하고, 미실행·미완료·품질 미달은 그대로 남겨라. 모든 기능이 연결된 완성형을 목표로 하되 관찰하지 않은 결과나 상용 게임 동등성을 주장하지 마라.
