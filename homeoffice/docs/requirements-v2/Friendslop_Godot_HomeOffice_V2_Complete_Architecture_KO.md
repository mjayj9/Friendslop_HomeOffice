# Friendslop 기반 집+회사형 멀티플레이 — 원문 전수 반영·건축 구조 강화 마스터 프롬프트 v2

작성일: 2026-09-14
문서 성격: AI 구현 지시서. 게임 구현, 현재 로컬 사이트 검사, Blender 연결, 배포 또는 테스트를 이미 수행했다는 뜻이 아니다.
사용 방법: 이 파일 전체를 구현 AI에게 전달한다. 이전의 오브젝트 편집기/Firebase 중심 명세 및 기존 Godot 프롬프트와 충돌하면 이 문서의 최신 제품 방향을 우선한다. 원문의 모든 요구는 부록 A에서 U01~U56으로 추적한다.

## 0. 최우선 지시 — 기능 이름만 붙인 단순한 집을 다시 만들지 마라

너는 Godot 멀티플레이 게임 개발자, 테크니컬 아티스트, 환경·레벨 디자이너, 물리·음성·협업 시스템 엔지니어의 역할을 수행한다. 목표는 서류·설계도만 제시하는 것이 아니라 실제 실행 가능한 게임을 만드는 것이다.

내 목표는 친구들이 실제 캐릭터로 같은 집에 들어와 걷고, 앉고, 대화하고, 회의하고, 개인 작업을 하고, 물건을 설치하고 사용하며, 농구·축구·총 게임·아케이드 게임을 하고, 요리·식사·수면까지 할 수 있는 ‘집+회사형 소셜 멀티플레이 공간’이다.

현재 결과는 내 의도와 다르고 집의 기본 구조도 너무 간단하다. 색·조명·UI만 바꾸지 말고 제품 방향과 공간 설계를 재검토하라. 빈 바닥에 몇 개 상자형 방과 소품을 놓고 방 이름만 붙이는 방식은 불합격이다. 큰 방 하나를 가구로만 나눈 뒤 집이 완성되었다고 하지 마라.

기존 프로젝트의 개발 방향은 폐기할 수 있지만 파일과 운영 리소스를 무단 삭제하지 않는다. 백업/별도 브랜치를 만든 뒤 재사용할 코드와 폐기할 설계를 구분하고 새로운 Godot 프로젝트 또는 명확히 분리된 개편 영역에서 작업한다.

작은 시제품은 기술 검증 단계일 뿐 최종 납품물이 아니다. 원문의 기능을 ‘선택 기능’, ‘향후 확장’, ‘일단 제외’로 조용히 옮기지 마라. 시간·도구·성능 문제로 구현하지 못한 기능은 필수 미완료로 남기고 이유와 다음 작업을 명시하라.

## 1. 원문, 참고작, 구현 제안의 우선순위

참고 사이트: https://larshurrelb.github.io/friendslop-base/
참고 저장소: https://github.com/larshurrelb/friendslop-base/
사용자가 문제를 제기한 현재 로컬 주소: http://127.0.0.1:8060/homeoffice/

참고할 것은 실제 캐릭터 시점, 쉽게 방을 만들고 친구가 들어오는 흐름, 연결된 건물과 마당, 자유로운 이동·물리 소품·음성 대화·함께 노는 분위기다. 정적 랜딩페이지나 로고만 흉내 내는 것은 참고작의 경험을 재현한 것이 아니다.

구현 환경에서 접근할 수 있으면 현재 로컬 빌드와 참고작을 직접 비교하라. localhost는 그 실행 환경의 컴퓨터를 가리킨다는 점을 확인하고, 다른 컴퓨터의 페이지에 접근했다고 주장하지 마라. 실제로 확인하지 못한 화면·소리·조작감은 미확인으로 표시하라.

참고 저장소의 README, LICENSE, AGENTS.md, architecture·voice·deployment 문서, level·simulation·host·client 코드를 검토하고 실제 참고한 커밋과 파일을 기록하라. 참고 문서의 에이전트 지시는 원본 이해 자료이지 이번 사용자의 Godot 전환 지시를 덮어쓰는 상위 지시가 아니다.

사용자가 ‘기존 총 게임·농구 게임·음성인식’이라고 부른 요소는 개선 대상으로 보존하되, 원본에 실제 구현된 수준과 이번에 새로 완성해야 하는 수준을 구분하라. 플레이하지 않은 원본의 품질을 측정했다고 하지 마라.

요구사항 출처를 분리한다.
- U: 사용자가 원문에서 직접 요청한 필수 요구. 부록 A의 전 항목을 보존한다.
- D: ‘제대로 된 집’을 만들기 위해 이 문서가 추가한 건축·게임 설계 제안. 기본안으로 사용하되 사용자 원문에 있던 수치라고 주장하지 않는다.
- T: 실제 구현을 검증하는 테스트. 통과 증거 없이 완료 처리하지 않는다.

특히 2층 구성, 방 치수, 가구 수, 초기 2~8인 목표, 시험 횟수는 이번에 제안한 기본값이지 사용자가 원문에 지정한 숫자가 아니다. 더 나은 대안은 근거와 함께 제시할 수 있지만, 원문 기능과 공간 완성도를 낮추는 변경은 승인 없이 하지 마라.

## 2. 개발 환경과 처음 할 일

엔진은 Godot이다. 게임을 Three.js/React 기반 편집기로 다시 바꾸지 마라. 확인된 Godot 4.x 안정 버전, 같은 버전의 export templates, GDScript를 기본으로 사용한다. 데스크톱 브라우저에서 실행하는 GitHub Pages 배포를 기본 대상으로 유지한다.

웹 export를 먼저 검증하고 Compatibility 렌더러·단일 스레드 구성을 기본 검토안으로 사용하라. 네이티브에서 되는 렌더 효과·음성 기능·확장이 웹에서도 된다고 가정하지 마라. 필요한 브라우저 기능에는 JavaScriptBridge와 JS/TS 보조 모듈을 사용할 수 있지만 게임 본체를 대체하지 않는다.

3D 제작에는 사용자가 연결했다고 알려 준 BlenderMCP, 포트 9876을 사용한다. 실제 도구 목록을 확인하고 씬 조회로 연결을 검증하라. 도구 이름이나 프로토콜을 지어내지 마라. 사용자 PC와 실행 컨테이너의 localhost를 구분하라. 이 연결은 제작용이며 배포 게임이 9876 포트에 접속해서는 안 된다.

기존 Blender 파일은 보존하고 프로젝트 전용 .blend와 컬렉션에 작업한다. 연결이 안 되면 그 사실과 실행 가능한 제작 스크립트를 제공하되 실제 MCP 제작 완료라고 쓰지 마라. 무료가 아닌 외부 모델 생성 서비스를 자동 호출하거나 포트를 외부에 노출하지 마라.

사용자는 GitHub 학생 개발자 팩 Pro와 Firebase Blaze를 사용하고 비용 보호를 설정해 두었다. 이번 기본 저장은 파일 내보내기/가져오기다. Firebase를 필수로 붙이거나 기존 DB·Auth·Storage·Functions·비용 보호를 변경하지 마라. 추가 운영비 0원을 목표로 하되 유료 음성 API·TURN·상시 서버를 임의 추가하지 않는다.

처음에 남자 GLB가 이미 제공되었는지 확인하고, 없다면 아래 문장을 사용자에게 요청하라.
“사용할 남자 캐릭터 GLB 파일을 업로드해 주세요. 리깅이나 애니메이션 파일이 따로 있다면 함께 보내 주세요. 우선 남자 캐릭터 한 종류로 구현하겠습니다.”

이 요청은 반드시 한다. 파일을 기다리는 동안 다른 개발은 진행하되, 임시 캡슐을 최종 캐릭터로 확정하지 않는다.

## 3. 건축 계획 — 먼저 집 전체를 설계하라

기본 제안은 ‘2층 본관 + 연결된 게임·무기 별동 + 테라스와 두 스포츠 구역을 가진 마당’이다. 가정집의 따뜻한 생활감과 소규모 공유 오피스의 기능을 함께 가진다. 건물 수를 늘리기만 하거나 복도를 미로처럼 만드는 것은 목표가 아니다.

1층은 현관·홀·거실·식당·주방·회의실·자유방을 중심으로 생활/교류/협업이 이어진다. 2층은 개인 작업실·조용한 복도·수면실·작은 휴식 공간을 중심으로 한다. 게임·무기방은 회의실과 수면실을 방해하지 않도록 전실이나 연결 복도로 분리한다. 마당의 농구와 축구 동선도 겹치지 않게 한다.

기본 공간 관계는 다음과 같다. 이 도식은 인접 관계이며 실제 치수 있는 도면은 따로 만든다.

```text
정문 → 현관/수납 → 홀/계단 → 거실 → 식당 → 주방/팬트리
                      │        │              │
                      │        └────── 테라스/마당 ─ 농구장·축구장
                      ├─ 회의실 ─ 자료/브레인스토밍 구역
                      ├─ 자유방 ─ 연결 전실 ─ 승인문 ─ 게임·무기 별동
                      └─ 2층 계단참
                             ├─ 개인실 복도 ─ 개인실 01, 02, 03 …
                             │                └─ 끝부분부터 실제 확장
                             └─ 조용한 복도 ─ 수면실/독서 휴식/욕실
```

시작 치수는 거실 약 9×8m, 회의실 약 9×7m, 식당/주방 각각 약 6×5m,
자유방 약 8×7m, 개인실 1실 약 4.5×5m, 수면실 약 8×6m,
구획된 게임 별동 약 16×12m를 검토한다.
농구 코트 약 24×14m, 미니 축구 코트 약 30×20m에 각각 주변 여유를 둔다.
모두 게임 설계 제안이며 공식 경기 규격이나 건축 법규 수치가 아니다.
최종 크기는 캐릭터, 가구, 참가 인원, 실제 이동 테스트에 맞춰 조정한다.

현관, 신발장/수납, 계단과 계단참, 욕실·화장실, 작은 수납/다용도실, 창과 문, 지붕·천장·외벽·테라스 등을 추가해 실제 집으로 읽히게 한다. 이 보조 공간은 건축 보완 제안이며 복잡한 위생·생존 시뮬레이션까지 새 필수 기능으로 늘리라는 뜻은 아니다.

모델링 전에 다음 설계 자료를 만든다.
1. 외부 부지 배치도와 층별 치수 있는 평면도.
2. 방별 목적·사용 인원·주요 가구·상호작용 목록.
3. 계단 단면, 층고, 문/창 위치, 통로와 이동 동선.
4. 사람 이동, 음성 구역, 무기 허용 구역, 스포츠 경계를 구분한 도면.
5. 인원 증가에 따라 확장되는 개인실 복도의 예비 영역.

부록 B의 방별 프로그램과 치수 예시를 시작점으로 사용한다. 계획과 실제 Godot 배치가 다르면 변경 내역을 남긴다. 이름표 몇 개나 위에서 본 도식만으로 건축 설계를 완료했다고 하지 마라.

## 4. 집답게 느껴지는 공간의 필수 조건

실제 바닥·천장·지붕·두께 있는 벽·문틀·문짝·창틀·창·난간을 갖춘다. 계단이 2층 바닥과 정확히 만나고, 출입문 뒤에 실제 통로가 있으며, 창 밖으로 일관된 외부 공간이 보여야 한다. 실내 기본 플레이에서 천장을 없애 하늘을 그대로 보이게 하지 마라. 잘라 보기/지붕 숨기기는 건축 확인 모드에만 사용한다.

정문에서 현관, 거실, 회의실, 계단, 개인실, 수면실, 주방, 테라스, 마당과 게임방까지 걸어서 도달할 수 있어야 한다. 이동 메뉴/텔레포트만으로 연결하지 마라. 보조 빠른 이동은 별도 기능일 수 있으나 실제 문·복도·계단을 대신하지 않는다.

침실은 조용하고, 회의실은 서로와 보드가 잘 보이며, 주방은 조리대와 식탁이 자연스럽게 이어지고, 거실은 대화/휴식/소파 놀이가 가능한 배치를 가진다. 각 방을 같은 박스에 책상과 벽 색만 바꾼 복제물로 만들지 마라.

가구, 사람과 물건이 동시에 지나갈 공간을 확보한다. 물건을 든 두 사람이 문·복도에서 억지로 겹쳐야 지나갈 수 있거나, 앉으면 출구가 막히거나, 계단에서 머리가 천장에 걸리면 수정하라.

건축 품질은 실제 캐릭터 눈높이로 확인한다. 전체 평면도, 외관, 각 공간 실내, 복도/계단, 개인실 확장 전후의 실제 게임 캡처와 끊기지 않는 도보 이동 영상으로 증명한다. Blender 렌더를 실제 게임 화면인 것처럼 제출하지 않는다.

## 5. 공간별 완성 기능 — 전부 최종 범위에 포함한다

회의실: 모두가 앉을 좌석, 화이트보드, 실제 보드마카, 브레인스토밍 보드, 마인드맵, 공동 보고서, 발표 스크린, 레이저 포인터, 발표자 권한, 의제·타이머·손들기·투표·회의 결과 정리를 갖춘다. ‘회의에 필요한 것은 모두’라는 요구는 최소 이 기능들을 실제 동작시키는 것으로 구체화한다.

개인 작업방: 참여자마다 별도의 방, 문, 이름표, 책상, 의자, 조명, 책/작업 도구, 수납을 제공한다. 사람 수가 늘면 방과 복도가 자연스럽게 확장된다. 개방된 책상 하나를 개인 작업방이라고 부르지 마라.

자유방: 모든 일반 상호작용과 배치 기능을 폭넓게 사용할 수 있는 공간이다. 책·보드·가구·물리 소품·협업 도구를 실제로 사용한다. 무기 기능도 방장이 해당 구역과 사용자를 허용한 경우 사용할 수 있어야 하지만 ‘자유방’이라는 이유로 허가를 생략하지 않는다.

마당: 농구장과 축구장을 각각 마련하고 골대·경계·공·점수·경기 재시작까지 연결한다. 벤치·휴식/관전 위치·테라스와 보행로를 갖추며, 두 경기와 건물 출입 동선이 무작정 충돌하지 않게 한다.

게임·무기방: 방장 승인 문, 도구 보관/장착 영역, 사격/태그 놀이 영역, 관전 위치, ‘픽맨’과 공룡 게임용 아케이드 기계를 제공한다. 문 열기와 무기 사용 허가는 따로 관리한다.

수면실: 실제 침대·수납·조명·안전한 기립 위치, 눕기→취침→깨기 상태를 제공한다. 자는 사람의 모습과 점유 상태가 다른 사용자에게 보인다. 한 사람의 수면이 세션 전체를 강제로 멈추거나 시간을 넘기지는 않는다.

거실·식당·주방: 대화, 소파 앉기/눕기/점프, 요리, 음식 담기/옮기기, 식탁에 앉아 식사, 정리가 이어진다. ‘요리’ 버튼을 누르면 메시지만 뜨는 상태는 완료가 아니다.

## 6. 개인실과 복도의 실제 자동 확장

실제 참여자 슬롯에 personalRoomId를 안정적으로 연결한다. 초기 예시는 2명이면 2개, 4명이면 4개, 8명이면 8개 개인실이며 이를 시험한다. 최대 인원과 방 수는 설정으로 제한하고 그 이상의 참가 흐름을 안내한다.

새 참가자의 방이 필요할 때 호스트가 복도 끝의 미사용 모듈을 연결하거나 새 모듈을 추가한다. 기존 방과 그 안의 물건·사람을 이동시키지 않는다. 복도 끝벽, 바닥, 천장, 조명, 문/번호, 충돌체, 음성 구역, 계단/외부 경계와의 관계를 함께 갱신한다.

현재 접속자 수가 줄어도 방과 작업물을 즉시 지우지 않는다. 재접속은 같은 슬롯을 재사용하고, 동시 입장·동일 닉네임·호스트 변경에도 중복 생성하지 않는다. 저장 파일에는 생성된 방, 확장 순서, 배정 슬롯과 내용물을 보존한다.

다른 날 가져온 세계에서 닉네임만으로 소유권을 확정하지 말고 새 호스트가 기존 슬롯을 안전하게 재배정한다. 실제 독립 사용자 인증이 없는 상황의 개인실을 호스트에게도 비밀인 보안 저장소라고 설명하지 않는다.

## 7. 남자 캐릭터·모델·애니메이션

사용자 GLB의 스켈레톤·리깅·원점·단위·정면·재질·텍스처·애니메이션을 검사한다. 원본을 보존하고 필요한 리타깃/베이크/최적화와 누락 클립을 기록한다. 우선 남자 한 종류만 완성한다.

대기, 걷기, 달리기, 웅크리기, 점프/착지, 앉기/일어서기, 눕기/깨기, 집기/들기/내려놓기/던지기, 책 읽기, 마카로 쓰기, 조준/발사/재장전/방패 들기, 농구 패스·슛, 축구 차기, 조리·식사를 연결한다. 실제 제공 클립과 새로 제작한 동작을 구분하고 부드러운 전환과 손/발/골반 정렬을 검사한다.

기본은 참고작과 같은 캐릭터 시점의 이동이다. 다른 사람에게는 전신과 행동이 보이고 자기 화면에는 머리 안쪽이 노출되지 않아야 한다. 물건은 손/펜촉/총구 등 실제 anchor에 연결한다. 무기를 들었는데 허공에 뜨거나 의자에서 골반이 관통하거나 발이 계속 미끄러지면 미완료다.

Blender 에셋은 흰 상자 대신 형태·베벨·두께·재질·손잡이·이음부를 가진다. 나무·직물·금속·유리·고무를 구분하되 저사양 웹 실행에 맞춰 텍스처와 드로콜을 관리한다. 장식 소품은 비활성으로 구분하고, 카탈로그에 ‘사용 가능’으로 표시한 물건은 기능을 구현한다.

## 8. 사용자가 설치하고 실제로 쓰는 물건

원문의 ‘기본 인터페이스’는 이 구현에서 ‘사용자가 배치하고 상호작용하는 사물/도구’로 구체화한다. 의자·책상·총·방패·책·보드마카·상자는 모두 필수다. 부록 C의 행동표에 따라 소파·침대·공·문·조명·조리도구·음식도 연결한다.

카탈로그→설치 미리보기→회전/스냅→충돌과 권한 확인→설치→일반 플레이에서 사용의 흐름을 제공한다. 기능별 사용할 키가 가까이서 보이고, 배치 모드를 닫은 뒤에도 상호작용된다. 좌표 패널과 ‘편집 시작’ 버튼을 거쳐야 앉을 수 있는 UI는 금지한다.

의자는 E 등 지정 키로 앉고 일어난다. 마카는 실제로 집은 상태에서 보드면에 접근해 클릭/드래그로 그린다. 책은 펴고 읽고 페이지를 넘기며, 책상 위에는 물건을 올리고, 상자는 밀고 들고 던지고 쌓을 수 있다. 수납형 상자는 열고 넣고 꺼내도록 구현한다.

공통 상호작용 계약은 대상, 거리/가림, 현재 사용자, 권한, 가능한 행동, 점유 상태, 호스트 검증, 상태 변경, 동기화, 저장/복원이다. 두 사람이 동시에 물건을 집거나 한 의자에 앉을 때는 한 명만 성공한다. 사용 중인 가구 이동·삭제, 플레이어 퇴장, 도구 교체 때도 안전하게 정리한다.

문/스폰/계단/코트/다른 좌석을 가구로 막는 배치는 거절한다. 재배치·삭제·Undo는 호스트와 최신 상태를 확인해 다른 사람의 작업을 덮어쓰지 않는다.

## 9. 캐릭터 이동과 물리 완성도

Godot에서 실제 웹 export가 검증된 물리 백엔드를 사용하고 그 위에 이동·상호작용·공 스포츠·총/방패 판정을 정교하게 구현한다. 충돌 엔진 자체를 무리하게 처음부터 새로 만드는 것으로 해석하지 않는다.

렌더 프레임과 고정 물리 틱을 분리한다. 캐릭터 motor, 지면 감지, 경사·계단·문턱, 웅크리기, 점프 입력, 낮은 천장, 모서리, 착지를 테스트한다. 소파의 탄성은 재미있되 무한 가속이나 천장 관통을 만들지 않는다.

물체별 질량·마찰·반발·충돌층·속도 제한·sleep을 설정한다. 빠른 공/투사체는 CCD나 실제 경로 검사로 터널링을 막고 시각 메시와 충돌체를 분리한다. 손에 든 물체를 매 틱 강제 순간이동시켜 무한 충격량을 만들지 않는다.

호스트가 최종 물리와 소유권을 판정하고 로컬 이동 예측, 원격 보간, 보정으로 조작감을 맞춘다. 모든 클라이언트의 공 계산을 동시에 정답으로 사용하지 않는다. 카메라 흔들림·반동·FOV 변화는 절제하고 감도·멀미 감소 설정을 제공한다.

## 10. 총 게임·방패·호스트 권한

총은 단순 소품이 아니라 조준, 그립, 발사, 탄약, 재장전, 적정 반동, 효과음, 피격 피드백, 점수/라운드가 있는 게임으로 보완한다. 기본 표현은 부담 없는 비유혈 장난감 총/태그 게임으로 제안하되 상세 룰은 명시한다.

사격 연습과 짧은 라운드형 게임에 준비→규칙→시작→플레이→종료/결과→재시작을 갖춘다. 총구와 시선 차이, 벽 가림, 연사 제한, 거리, 방패 방향을 호스트가 검사한다. 방패는 정면을 실제로 막고 옆/뒤는 별도 판정한다.

방장이 무기방 출입, 사용자별 도구 사용, 허용 구역, 게임 시작/종료, 즉시 회수를 제어한다. 클라이언트 UI를 숨기는 것만으로 끝내지 않는다. 무기를 가방/손에 넣고 회의실로 나가 사용하거나 저장 파일에서 enabled=true를 넣어 허가를 우회할 수 없어야 한다.

게임방 밖 사용은 기본 불가다. 자유방도 방장이 명시적으로 무기 허용 구역으로 지정하고 사용자 허가를 준 경우에만 가능하다. 허가 취소 시 현재 장착, 예약 발사, 비행 중 효과의 정책까지 일관되게 처리한다. 회의 문서와 집의 구조는 총 놀이로 파괴하지 않는다.

## 11. 농구·축구·픽맨·공룡 게임

농구는 공 잡기, 자연스러운 드리블, 패스, 슛 충전/놓기, 림과 백보드 충돌, 공 회수, 점수판, 게임 종료/재시작을 제공한다. 자유 연습, 시간제 슈팅, 간단한 팀 경기까지 실제로 플레이할 수 있어야 한다. 공을 정해진 애니메이션으로 골대에 자동 넣는 시연으로 대체하지 않는다.

골대의 구멍을 충돌체로 막지 않는다. 호스트가 위→아래 방향으로 림의 유효 영역을 통과한 것만 득점 처리하고, 아래에서 위 통과·링 옆 통과·여러 센서의 중복 이벤트를 득점하지 않는다. 높은 속도·바운스·패스·재접속에도 공과 점수가 일치해야 한다.

축구도 공 제어, 패스, 슛 강도, 골라인 통과, 점수, 외부 공 복귀, 골 이후 재시작과 간단한 경기를 제공한다. 농구장과 축구장이 서로의 게임을 계속 망치지 않도록 경계와 공 복구를 설계한다.

게임방에는 원문의 ‘픽맨’과 ‘공룡 게임’을 모두 포함한다. ‘픽맨’의 정확한 뜻은 사용자 확인 항목으로 보존하고, 팩맨류 미로 게임이라는 해석은 후보로 표시한다. 다른 게임으로 조용히 치환하거나 이 항목을 삭제하지 마라. 확인 전에는 공통 아케이드 프레임과 공룡 러너 등 독립 작업을 진행한다.

확정된 게임은 자체 제작/사용 허가된 자산으로 구현한다. 공룡 게임은 달리기·점프·장애물·난이도 증가·점수·실패·재시작의 루프를 가진다. 아케이드 기계에 접근해 플레이하고 나가면 원래 캐릭터 위치로 돌아오며 주변 사람이 화면/결과를 관전할 수 있다.

## 12. 음성 통화 — 두 모드와 실제 품질 개선

원문의 음성 요구를 ‘소리를 전달하는 통화 품질’과 ‘한국어를 글자로 바꾸는 인식 품질’로 나누어 둘 다 구현한다.

근거리 모드: 거리·방향에 따라 자연스럽게 들리고 멀어지면 줄어든다. 사용자가 설정에서 발화 거리 범위를 조절할 수 있고 방장이 허용 상한을 정한다. 벽, 닫힌 문, 실내외/층간 구분을 반영하며 거리 경계에서 소리가 반복적으로 끊기지 않게 한다. 다른 사람이 수신 설정을 높여 발화자의 허용 범위를 우회하지 못하게 한다.

전체 모드: 거리와 관계없이 같은 세션 전체가 들을 수 있는 모드로 명확히 표시한다. ‘방 전체’가 현재 회의실 전체를 뜻하는 경우를 위해 현재 Zone 범위도 구분해 제공할 수 있지만 세션 전체 기능을 없애지 않는다. 전체 방송과 잔향 효과를 혼동하지 않는다. 방장은 방송 권한을 관리하고 사용자 음소거·차단은 존중한다.

마이크 선택, 입력 레벨/테스트, 눌러 말하기, 열린 마이크 설정, 자기/상대 음소거, 상대별 볼륨, 발화 표시를 제공한다. 에코 제거, 잡음 억제, 자동 이득, clipping 방지, 장치 변경, autoplay와 권한 실패, 장기 지연·중복 재생을 실제 두 사람의 통화로 검사한다.

WebRTC 미디어와 공간 재생 경로를 검증하라. 원격 소리를 audio 요소와 공간 음향 경로에서 두 번 틀지 않는다. 거리 밖 소리를 전부 보내 놓고 볼륨만 0으로 만드는 것을 사생활 보호라고 하지 않는다. 수신 권한과 전송 범위를 맞추고 호스트 중계의 신뢰 한계를 표시한다.

## 13. 한국어 음성인식과 실시간 자막

자막은 사용자 원문에서 원한 기능으로 최종 구현 범위에 포함한다. ko-KR 설정 한 줄이나 텍스트 입력창을 넣고 한국어 인식 완료라고 하지 마라.

실제 한국어 발화에 대해 짧은 문장, 존댓말/반말, 이름, 날짜·숫자, 한국어/영어 혼합, 회의 용어, 잡음·말 겹침을 검증한다. 각 사용자의 자기 마이크를 인식하고 올바른 화자 정보와 함께 허용된 범위에 전달하는 구조를 기본으로 검토한다.

STTProvider로 브라우저 인식, 실제 한국어를 지원하는 온디바이스 인식, 로컬 다국어 모델을 비교한다. 지원 브라우저·언어팩·처리 위치·모델 용량·메모리·지연·게임 FPS를 확인하고 지원 환경에서 가장 적절한 제공자를 선택한다. 전부 구현할 필요는 없지만 선택 이유와 실패 시 대안을 남긴다.

자막의 중간 결과/확정 결과, 화자, 문장 중복, 늦은 결과, 줄 수·크기·대비·표시 시간을 처리한다. 음소거 이후 전송과 오래된 결과를 중단하고, 음성을 들을 수 없는 거리/권한 밖 사용자에게 자막만 전달하지 않는다.

지원 엔진의 실제 용어 힌트 기능을 사용하되 내용을 LLM으로 추측하거나 숫자를 임의 교정하지 않는다. 외부 처리 시 고지/동의를 받고, 로컬 모드 사용자를 몰래 외부 인식으로 전환하지 않는다. 원음은 기본 저장하지 않으며 회의 전사 보관도 별도 선택으로 처리한다.

동의된 한국어 테스트셋과 실제 마이크로 CER/WER·자막 확정 지연·FPS 영향을 측정하라. 합성 음성만의 결과를 사람 대상 검증과 구분한다. 미지원 환경에서는 통화·텍스트 대화를 유지하지만 그것을 해당 환경의 STT 완료라고 보고하지 않는다. 인식 정확도와 개선 효과를 측정 없이 보장하지 마라.

## 14. 회의 도구·PPT 발표·한글 공동 작성

화이트보드는 실제 보드마카로 쓰는 3D 상호작용과 확대해서 쓰는 편의 UI를 모두 제공한다. 선, 도형, 텍스트, 색, 굵기, 지우개, 선택/이동, 사용자별 Undo가 동기화된다. 보드 표면의 좌표를 안정적으로 계산하고 큰 그림 전체를 매 프레임 보내지 않는다.

브레인스토밍에는 메모 작성·이동·색상·그룹·투표·타이머·결과 정리를, 마인드맵에는 노드·연결·이름·이동·삭제·복원을 구현한다. 공동 보고서는 제목·문단·체크리스트·간단한 표를 여러 사람이 동시에 한글로 편집할 수 있게 한다.

CRDT/OT 등 실제 동시 편집을 처리하는 검증된 방법을 적용하고, 한글 IME 조합·복사/붙여넣기·줄바꿈·Undo·재접속에 대해 데이터 수렴을 검사한다. 문서 전체 덮어쓰기로 다른 사람의 글을 지우지 않는다. 문서 권한과 통신량 제한은 별도로 검증한다.

PPT 관련 도구는 큰 발표 화면, 슬라이드 넘기기와 현재 페이지 동기화, 발표자 권한/인계, 레이저 포인터, 주석, 손들기, 질문, 타이머를 포함한다. 최소한 PPT에서 내보낸 PDF/이미지로 실제 발표가 가능해야 한다. PPTX 직접 입력/변환은 지원 범위를 따로 확인하고 안 되면 이유와 변환 절차를 안내한다. 직접 PPTX 지원을 검증하지 않고 지원한다고 하지 마라.

게임 안 책상/보드/스크린에서 도구를 열고 닫으면 캐릭터 시점으로 돌아온다. 문서 편집용 DOM 보조 화면은 허용되지만 집 전체를 대체하는 웹 업무 앱으로 바꾸지 않는다. 입력 중 이동·점프·발사가 함께 실행되지 않게 한다.

회의 의제→발표/토론→메모/투표→공동 보고서→결론/할 일→자료 내보내기의 실제 회의 흐름을 완성한다. 큰 발표 자료는 크기 제한·chunk·검증·취소·재시도로 전송하고 음성/이동을 막지 않게 한다.

## 15. 요리·식사·소파·수면의 생활 루프

거실에서는 자유롭게 대화하고 소파의 좌석별로 앉거나 눕고 점프할 수 있다. 점프할 때 탄성과 착지 반응은 자연스럽고, 다른 사람을 강제로 날리거나 집을 뚫지 않게 한다.

주방은 냉장고/식재료 보관→재료 꺼내기→조리대/도구 사용→조리 진행→접시에 담기→식탁으로 옮기기→앉아서 먹기→정리까지 연결한다. 최소 두 종류의 간단한 조리 흐름을 기본 제안으로 구현하되 복잡한 생존/영양 계산을 추가하느라 핵심을 미루지 않는다.

컵·접시·음식·도구의 상태가 공유되고 두 사람이 같은 음식을 중복 소비하지 않는다. 주변 사람에게도 조리·운반·식사 행동이 보인다. 장식 주방과 토스트 메시지만으로 생활 기능이 구현됐다고 하지 마라.

수면은 침대 접근→눕기→취침 표시/편안한 로컬 환경→사용자 입력으로 깨기→안전한 위치에 일어서기로 연결한다. 다른 사람이 사용 중인 침대를 차지하거나 지우지 못하게 하고 퇴장 시 점유를 해제한다. 수면이 마이크 송출 동의나 접근 권한을 바꾸지 않도록 한다.

## 16. 멀티플레이·역할·입력 상태

세션(Session)과 실제 공간(Zone)을 분리한다. 방장은 물리·배치·소유권·게임 점수·권한의 기준이다. 참여자는 입력과 행동 요청을 보내고, 호스트가 거리·가림·점유·사용 권한을 검증한 결과를 받는다.

WebRTC 시그널링은 실제 동작하는 경로로 구현한다. Godot의 멀티플레이 프로토콜과 PeerJS 채널이 자동 호환된다고 가정하지 마라. 한 transport/bridge 경로를 선택하고 실제 두 브라우저와 가능하면 서로 다른 네트워크에서 검증한다.

이동/물리 상태, 도구/권한 이벤트, 협업 연산, 음성, 자막, 대용량 파일의 전송 목적과 우선순위를 구분한다. 버전·세션 epoch·ID·sequence·크기·유한 숫자·속도 제한을 검사하고 backpressure를 구현한다. 늦은 참가자는 집 전체 구조와 문/가구/개인실/보드/문서/게임 상태를 받아야 한다.

기본 키는 WASD·마우스 이동/시점, Space 점프, Shift 달리기, C/Ctrl 웅크리기, E 상호작용, Q 내려놓기/던지기, B 배치, V 눌러 말하기, Esc 메뉴를 검토하고 변경 가능하게 한다. ‘가볍게 Q=내려놓기, 길게/조합=던지기’처럼 서로 다른 행동이 충돌하지 않는 규칙을 확정한다.

PLAY/BUILD/UI_FOCUSED/SEATED/SLEEPING/MINIGAME 등의 입력 상태를 나누고 한글 조합 중 게임 행동을 차단한다. 상태 전환 시 키가 눌린 채 남거나 포인터락에 갇히지 않게 한다.

방장 이전은 전체 확정 상태·문서 연산을 정리하고 후임 준비 확인, 새 epoch, 기존 호스트 권위 해제까지 수행한다. 관리자 이름만 바꾸는 것으로 끝내지 않는다. 방장 강제 종료 시 무중단 이전을 검증하지 못했다면 마지막 확인 복구본으로 새 세션을 여는 흐름과 손실 가능성을 알린다.

## 17. 내보내기/가져오기 — 모두 나간 뒤 같은 공간으로 돌아오기

핵심 흐름은 ‘모두 나가기 전 대표자/호스트가 내보내기 버튼으로 공간 파일 저장→다음 접속 때 한 사람이 가져오기로 세계 복원→친구들이 그 세션에 합류’이다. 사람마다 다른 로컬 화면을 각자 저장하게 하지 않는다. 모든 사람의 브라우저를 자동으로 닫는 기능이 아니다.

버튼은 ‘공간 내보내기’, ‘내보내고 세션 종료’, ‘공간 가져오기’를 명확히 구분한다. 저장 시각, 반영한 revision, 포함 데이터, 파일 이름/크기, 미저장 변경을 안내한다. 종료 직전에만 저장할 수 있게 하지 말고 중간 저장도 허용한다.

호스트의 확정 상태를 일정 시점에서 모으고 문서/보드 연산을 flush한 뒤 단일 버전 파일로 내보낸다. 제안 포맷은 manifest.json+world.json+문서/첨부물이 든 .homeworld다. 내보내기 중 새 변경을 잠깐 제한하거나 어느 revision까지 포함했는지 표시해 일관성을 지킨다.

저장 범위는 건물/공간 구조, 개인실과 늘어난 복도, 배정 슬롯, 가구/도구의 ID·종류·위치·회전·상태·내용, 문·조명·수납, 화이트보드·브레인스토밍·마인드맵·공동 보고서, 발표 자료, 생활 물건/음식 상태, 필요한 경기 결과와 일반 설정이다.

기본 남자 GLB와 기본 가구는 빌드에 포함하고 assetId/버전으로 참조한다. 사용자가 올린 슬라이드·이미지 등은 누락되지 않게 포함한다. 원음·동의 없는 전사·비밀 토큰·비밀번호·개인키·실행 코드는 넣지 않는다.

가져오기는 파일 크기·압축 해제 한도·경로·버전·checksum·중복 ID·참조·숫자·허용 자산을 먼저 검사한다. 파일 속 임의 스크립트/scene을 실행하지 않는다. 임시 세계에서 검증하고 성공할 때만 교체하며 실패 시 현재 세계를 보존한다. 기존 세션의 교체는 호스트 권한과 참여자 안내를 거친다.

옛 peer ID/호스트 권한/좌석·손 점유/무기 허가는 새 세션에서 안전하게 초기화한다. 무기 허가는 새 방장이 재승인하고 개인실 슬롯도 안전하게 재연결한다. 움직이는 공과 들고 있던 물건의 복원 위치/속도 정책을 명시한다.

기기 내 자동 복구 캐시는 보조다. 서버 저장, 다운로드 요청, 파일 보관 확인을 구분한다. 브라우저 종료 이벤트에만 의존하거나 정전/강제 종료에도 파일이 자동으로 저장된다고 보장하지 마라.

## 18. 화면·성능·자산 품질

시작 화면은 새 공간, 친구 방 참여, 저장 파일 가져오기, 설정으로 구성한다. 기본 게임 화면에는 작은 행동 안내, 필요한 도구 슬롯, 마이크/참여 상태, 선택 자막만 둔다. 상시 객체 목록/좌표 패널과 ‘편집 시작’ 중심 화면은 금지한다.

환경의 디테일을 포기하는 대신 LOD·방별 가시성·메시/재질 공유·텍스처 최적화·단순 충돌체·물체 sleep·제한된 동적 조명으로 조절한다. Compatibility에서 지원되는 효과만 사용하고 정적 베이크 영역과 사용자 가구/복도 확장 영역의 조명을 구분한다.

초기 테스트 목표는 2~8인, 데스크톱 브라우저다. 실제 하드웨어를 적고 1080p에서 60fps 지향, 저품질에서 30fps 지향을 제안하되 보장값으로 쓰지 않는다. 음성·한국어 인식·보드·공 물리가 동시에 실행될 때 메모리·프레임 시간·네트워크를 측정한다.

STT 모델 다운로드를 게임 기본 파일에 무작정 합치지 않는다. WASM/PCK/GLB/텍스처/폰트/문서/모델의 용량과 실제 로딩 경로를 관리하고 GitHub Pages 하위 경로와 호스팅 한도를 확인한다. 지원되지 않는 고급 효과를 몰래 켜거나 집과 기능을 삭제해 성능 숫자만 맞추지 않는다.

## 19. 진행 순서 — 전체 건축을 먼저 확보하고 상세·기능을 완성한다

단계 A: 기존 결과와 참고작 분석, 사용자 요구 U01~U56 확인, GLB 요청, Godot/BlenderMCP/웹/네트워크 검증, 전체 배치도·층별 평면·동선·공간 프로그램 확정.

단계 B: 모든 필수 공간과 건물 외피·계단·문·마당·개인실 확장 영역을 포함한 전체 블록아웃. 이 시점에 모든 공간을 실제로 걸어서 검사한다. 작은 거실과 회의실만 만들고 전체 집이 완성됐다고 하지 않는다.

단계 C: 블록아웃을 실제 환경 에셋과 남자 캐릭터로 교체하고 생활/소품/이동/멀티플레이/저장 기본을 연결한다. 첫 정밀 구역은 세부 스타일을 검증하는 샘플일 뿐 다른 공간을 삭제하는 근거가 아니다.

단계 D: 회의 도구, 한국어 공동 작성, 근거리/전체 음성, 한국어 인식/자막, 가구 카탈로그, 개인실 확장, 요리·식사·수면을 완성한다.

단계 E: 총·방패·허가, 농구·축구, 픽맨의 확인된 게임과 공룡 게임을 플레이 루프로 완성한다.

단계 F: 전체 저장 왕복, 재접속/호스트 이전, 네트워크·입력·성능·개인정보·에셋 품질 검증과 배포를 수행한다.

이 순서는 병렬 작업을 막는 지시가 아니다. 각 단계가 전체 제품의 어느 부분인지 공개하고, 단계 종료를 제품 전체 완료로 바꾸지 마라. 확인이 필요한 미술/치수는 계획을 보여 주되 사용자가 답할 때까지 관련 없는 구현까지 전부 멈추지는 않는다.

## 20. 완료 판정과 제출물

부록 A의 모든 원문 요구에 구현 파일·씬·에셋·실제 동작·테스트·남은 문제를 연결한 requirements-traceability.md를 작성하라. 완료 상태는 미착수/설계/구현/검증완료/제약으로 구분하고, ‘메뉴 있음’이나 ‘씬 파일 있음’을 검증완료로 취급하지 않는다.

부록 D의 테스트를 실제 실행 환경·결과와 연결하라. 코드/엔진 검사, 실제 다중 브라우저, 실제 마이크/한국어, 수동 시각 검사를 구분한다. 수행할 도구가 없으면 미실행으로 남기고 성공을 꾸미지 않는다.

최종 산출물은 실행 가능한 project.godot, 장면/스크립트/입력 맵, 고정 export 설정, 실제 남자 GLB/애니메이션, 전체 건축과 가구 에셋, .blend 원본/제작 스크립트, JS bridge/의존성, 저장 포맷/마이그레이션, 테스트, 실제 웹 빌드, 한국어 실행·배포 문서다. 재사용 자산의 라이선스와 고지를 보존한다.

완성도는 다음 통합 시나리오로 확인한다.
친구들이 집에 들어와 각자 방을 배정받는다. 거실에서 대화한 뒤 회의실에 앉아 마카로 그리고 브레인스토밍·마인드맵·보고서를 함께 작성하고 PPT 자료를 발표한다. 주방에서 요리해 식사하고, 마당에서 농구·축구를 한다. 방장이 게임방을 열어 총·방패·아케이드를 사용한다. 다른 사람은 수면실에서 쉬고 개인방에서 작업한다. 새 친구가 들어오면 복도와 개인실이 늘어난다. 모든 사람이 나가기 전 세계를 내보내고, 다음 날 다른 브라우저에서 가져와 집·물건·문서·보드를 복원한다.

이 중 하나라도 버튼만 있고 실제로 되지 않으면 해당 원문 요구는 미완료다. 단순한 집이나 ‘기능을 넣을 수 있는 구조’를 최종 제품으로 대신하지 마라.

## 부록 B. 상세 건축·공간 프로그램 — 단순한 집으로 축소하지 않기 위한 설계 기본안

### B1. 건축의 크기보다 중요한 것

아래는 사용자의 ‘집+회사’와 ‘너무 간단한 집은 싫다’를 구현하기 위한 추가 설계 제안이다. 원문에 있던 확정 치수나 법규·실제 건물 설계 기준이 아니다. 실제 사람 대신 캐릭터가 다니는 게임 레벨이며 엔진 단위·카메라·충돌체와 함께 검증하고 조절한다.

기본안은 2층 본관, 짧은 연결 복도로 연결한 게임 별동, 테라스, 농구/축구가 분리된 마당이다. 본관은 대략 32×24m 이내의 블록을 출발점으로 잡되 모든 실내가 하나의 빈 홀로 이어지는 것은 아니다. 전체 부지는 예를 들어 약 76×60m를 검토하고 정확한 배치는 평면도로 충돌 없이 확정한다. 숫자를 맞추기 위해 방을 불필요하게 비우거나 늘리지 않는다.

대략적인 인접 관계는 다음과 같다. 아래는 좌표 도면이 아니며 실제 치수 도면을 별도로 만들어야 한다.

| 독서/휴식 공간 | 약 5×4m | 책장·작은 좌석·낮은 소음·난간/창 | 책 읽기·휴식, 복도를 불필요하게 점유하지 않음 |
| 화장실/욕실·다용도 | 기능에 맞춘 작은 실, 예: 2×3m/3×3m | 집의 기본 구조·수납·문·조명 | 구조 완성, 생활 필수 요구를 대체하지 않음 |
| 게임 별동 | 약 16×12m에서 구획 | 승인 전실·보관대·사격/태그 영역·관전 위치·아케이드 | 도구 장착과 놀이, 본관 작업 방해 최소화 |
| 테라스 | 약 10×4m | 실내에서 이어지는 문·난간/데크·벤치·외부 조명 | 식당/거실에서 마당으로 이동·휴식 |
| 농구 영역 | 코트 약 24×14m+주변 여유 | 명확한 경계·골대·백보드·공 회수·점수판 | 간단 경기용 치수이며 공식 규격이라고 주장하지 않음 |
| 축구 영역 | 미니 코트 약 30×20m+주변 여유 | 두 골대·경계·복귀 경로·관전 자리 | 소규모 실제 패스/슛/경기 |

복도는 약 2.2~2.8m, 일반 출입 유효 폭은 약 1.0~1.2m, 넓은 출입은 약 1.5~1.8m, 실내 유효 높이는 약 2.8~3.3m를 초기 게임 설계값으로 검토한다. 모형/물체 크기와 충돌 캡슐에 맞춰 플레이 테스트 후 변경할 수 있다. 계단 높이/폭은 motor가 통과하도록 실제 검증하고 건축 법규 적합성 수치라고 설명하지 않는다.

### B3. 공간 품질 6단계

모든 주 공간은 다음 여섯 층을 가진다. ‘소품을 몇 개 더 넣기’만으로 디테일이라고 하지 않는다.
1. 구조: 벽/바닥/천장/문/창/계단/외피와 충돌이 맞는다.
2. 건축 마감: 문틀·손잡이·걸레받이·난간·창턱·재질 이음이 보인다.
3. 주 가구: 그 방의 행동에 맞는 크기·방향·좌석·작업면을 가진다.
4. 생활 단서: 책, 식기, 문구, 수납, 조명 등 과하지 않은 사용 흔적을 둔다.
5. 사용성: 행동 안내, anchor, 접근 거리, 점유, 실제 상태 변화를 제공한다.
6. 공유/저장: 다른 사람이 같은 결과를 보고 다음 날 복원할 수 있다.

모든 표면에 미세 디테일이나 고해상도 텍스처를 강제하지 않는다. 실루엣·비례·가구 관계·재질·적절한 조명이 먼저다. 멀리 있는 장식과 자주 사용하는 손잡이/도구는 자산 예산을 다르게 준다.

### B4. 개인실 증축 불변조건

예비 영역은 최초 부지/건축 계획부터 확보한다. 복도 끝에 모듈을 추가하되 기존 침실, 외벽, 농구장, 계단, 위층/아래층과 겹치지 않게 한다. 일반 참가자에게 사람이 없는 벽이 순간적으로 사라지는 것보다 짧은 공사/확장 표시와 안전 경계를 제공한다.

확장은 memberSlotId → personalRoomId → moduleIndex → doorId → objectIds로 추적한다. world generator version/seed와 이미 확정된 모듈 좌표를 저장해 다른 버전에서 다시 가져왔을 때 방이 바뀌지 않게 한다. 재입장·동시 두 명 입장·호스트 이전·저장 복원 중 중복 생성이 없어야 한다.

### B5. 건축 합격 게이트

사용자가 볼 첫 전체 공간 검토에는 다음을 포함한다. 전체 부지/층별 도면, 정면·후면 외관, 현관→거실→회의실→계단→개인실→수면실→주방→마당→게임방의 연속 이동, 일반 시점에서 천장이 있는 실내, 2/4/8 개인실 확장 전후, 보드와 발표 화면의 실제 가독성, 물건을 든 플레이어의 문/계단 통과.

단계를 구분한다. 전체 블록아웃의 동선이 합격해도 최종 미술 합격은 아니다. 정교한 거실 한 장의 스크린샷이 있어도 전체 집 합격은 아니다. 구조 누락과 기능 누락을 장식으로 가리지 않는다.

### C2. 음성/자막 수신 정책

발화자의 mode·range, 호스트의 정책, 참가자 위치/Zone, 참가자 차단·음소거를 조합해 실제 수신 집합을 정한다. 자막은 발화 시점에 허용된 범위 밖으로 뒤늦게 퍼지지 않게 segment/utterance의 수신 범위와 세션 세대를 묶는다. 정확한 정책은 문서화하고 클라이언트 메시지의 임의 range/role을 그대로 신뢰하지 않는다.

근거리 보호는 음량 계산만이 아니라 데이터 전달 범위를 포함한다. 다만 직접 P2P의 주소 노출, 신뢰한 호스트의 메모리 접근, 이미 전달된 소리/자막을 받은 사용자의 녹음·복사까지 막는다고 주장하지 않는다.

### C3. 저장 경계와 식별자

worldId는 보존 세계, sessionId/sessionEpoch는 현재 접속, participantId는 현재 참가자, memberSlotId는 저장된 개인실 배정 슬롯이다. 혼용하지 않는다. 저장 파일의 방장/닉네임/peer ID만으로 새 세션의 권한을 부여하지 않는다.

필수 저장 schema 예시는 manifest(schemaVersion, appVersion, worldId, assetPackVersion, generatorVersion, timestamp, checksums), world(zones, modules, props, doors, lights, roomSlots), collaboration(boards, brainstorming, mindMaps, reports), presentations(assets, page state), activities(games, cooking states)다. 원음·동의 없는 전사·실행 파일·토큰은 제외한다.

PDF·이미지 자료는 실제 bytes와 메타데이터를 보존하고 경로 문자열만 저장해 다음 날 사라지게 하지 않는다. 기본 캐릭터/가구와 사용자가 가져온 문서의 배포·보관 범위를 구분한다. 비공개 자료의 내보내기는 범위를 보여 주고 승인받는다.

zip bomb/경로 탈출/잘못된 MIME/수치 폭주/unknown asset/순환 참조/임의 script를 거절한다. checksum은 손상 탐지이지 신뢰할 수 있는 작성자 서명이라고 설명하지 않는다. 엔진 오브젝트를 직접 역직렬화하기보다 검증된 데이터→허용 장면 매핑으로 복원한다.

### C4. 한국어 품질 비교 방식

엔진/브라우저별 테스트 조건을 고정하고 동의된 발화 자료를 쓴다. 예: 일상 대화 15문장, 회의/발표 15문장, 숫자/고유명사/한영 혼합 20문장으로 50문장 이상을 구성하고 조용한/잡음 환경, 헤드셋/노트북 마이크, 여러 화자를 포함한다. 이것은 시험 설계 제안이다.

CER은 띄어쓰기/문장부호 포함 여부를 밝히고 WER은 한국어 어절 기준 등 분할 규칙을 명시한다. 임의로 유리한 전처리를 적용해 정확도 향상을 주장하지 않는다. 자막의 문장 끝→최종 확정 지연, 원음 대비 누락·환각, 마이크 mute 뒤 잔여 발화 유출, 장기 플레이에서 FPS/발열을 같이 측정한다.

제공자 선택은 한국어 내용 보존, 지연, 장치 부하, 비용, 개인정보를 함께 고려한다. 외부 STT/언어팩/모델이 지원되지 않는 경우 명확히 알리되 기능 자체를 개발 범위에서 삭제하지 않는다.

## 부록 E. 구현 AI의 첫 응답과 납품 보고 형식

처음에는 (1) 현재 도구/로컬 주소 접근의 실제 가능 여부, (2) GLB 업로드 요청 또는 이미 제공된 파일 검사 결과, (3) 참고작과 현재 결과의 확인된 차이, (4) 전체 건축 기본안과 원문 전수 대조표, (5) 실제 시작할 작업을 짧게 제시한 뒤 구현하라. 자료가 미확인인 곳은 미확인이라고 표시한다.

건축 승인에 필요한 도면/블록아웃, 실제 게임 스크린샷/영상, 단계별 실행 빌드를 제공한다. 문서만 여러 개 만들고 실행은 하지 않은 상태를 ‘개발 완료’로 보고하지 않는다. 블록아웃 이후에도 전체 공간 목록과 요구 추적표를 항상 유지한다.

최종 보고는 다음 순서로 한다. 실행 방법과 실제 빌드, 변경 파일과 에셋, 전체 집 구조, 원문 요구별 상태, 네트워크/음성/한국어/저장 테스트, 성능/라이선스, 미완료·제약, 운영 배포 여부. 실행하지 않은 명령, 존재하지 않는 엔진 옵션, 가짜 테스트 결과를 쓰지 않는다.

## 부록 F. 참고 확인과 한계

이 프롬프트는 사용자가 붙여넣은 원문과 ‘기본 집 구조가 너무 간단하다’는 최신 피드백을 최우선 근거로 다시 작성했다. 이전 Godot 프롬프트의 방 목록·상호작용·음성·저장 요구도 대조했으나, 이전 문서의 ‘작은 거실+회의실’ 단계를 최종 제품으로 축소할 근거로 사용하지 않는다.

작성 과정에서 참고 저장소 README를 GitHub 연결 도구로 다시 읽었다. 원본은 2~8인 starter, 호스트 물리, 소품, 공유 건물·마당, 근거리 음성을 설명하고 완성된 점수제 경기나 한국어 STT 구현을 보장하는 자료가 아니다. 이번 문서에서 요구한 2층 본관·치수·생활 보조 공간·세부 게임 규칙은 원본의 현재 기능이 아니라 확장 설계다.

공개 배포 사이트의 웹 열기에서는 내부 오류가 반환되었으며 플레이 화면·마이크 품질을 직접 측정하지 않았다. 사용자의 127.0.0.1 주소와 BlenderMCP 9876에는 접속/작업하지 않았다. 이 파일 생성은 구현·배포 완료가 아니다.

아래 공식 문서는 웹 지원을 확인한 출발점이다. 실행 시점의 버전과 정책을 다시 확인하고 docs/references.md에 기록한다.

- 참고작 README: https://github.com/larshurrelb/friendslop-base/blob/main/README.md
- 참고작 architecture: https://github.com/larshurrelb/friendslop-base/blob/main/docs/architecture.md
- 참고작 voice: https://github.com/larshurrelb/friendslop-base/blob/main/docs/voice.md
- Godot Web export: https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html
- Godot WebRTC: https://docs.godotengine.org/en/stable/tutorials/networking/webrtc.html
- 브라우저 SpeechRecognition: https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition
- 종료 이벤트 제약: https://developer.mozilla.org/en-US/docs/Web/API/Window/beforeunload_event

기술 주의: 확인한 Godot 문서는 웹 Compatibility·WebGL2와 단일 스레드 export, 웹 오디오 모드별 제한을 설명한다. WebRTC에는 별도 시그널링 경로가 필요하다. 브라우저 SpeechRecognition은 지원 차이가 있고 일부 처리 경로는 외부 서버에 음성을 전송할 수 있다. beforeunload는 모든 종료 상황에서 실행되지 않는다. 이것들은 사용자 프로젝트를 실행해 확인한 사실과 다르며, 이 문서의 마이크/저장/배포 검증 요구에 반영했다.

> 음성 인식 기술도 모드를 가까이 있어야 들리는 모드와(이건 사용자 설정 가능. 거리 조절 가능) 방 전체가 울리는 모드로 나눠야 함(기존에는 한 개만 있음) 또한 음성 인식 기술이 아직 안 좋으니 더 발전해야만 해. 특히 한국어에 특화 되어야만 해(자막도 제공하는 거면 좋겠어. 그렇기 위해서는 한국어 인식이 잘 되어야만 함)
> 사용자가 직접 기본 인터페이스(의자, 책상, 총, 방패, 책, 보드마카, 상자 등)를 방에 설치 가능하고, 실제로 상호작용 가능해.(의자를 설치하고 특정 버튼을 누르면 앉거나, 특정 버튼을 클릭하면 보드마카로 그릴 수 있고... 그런 식으로 모두 상호작용 되도록 해야 해)
> 그리고 총과 같은 놀이 도구도 사용하게 할 건데, 이건 방장이 허락해야만 쓸 수 있어.(그래서 후에 설명한 게임-무기방 같은 곳에 있음)
> 그리고, 방을 좀 더 많이 만들어야 해. 현재는 3방과 마당 밖에 없어. 이번에는 더 보완해서 회의방(화이트 보드 사용 가능하고, 회의를 하기 위한 툴(브레인스토밍, 마인드맵, 보고서 같이 쓰기 등등), PPT와 관련된 도구(레이저 등)등등 회의에 필요한 건 모두 있음) , 개인 일하는 방(이건 사용자 수에 따라 자동 생성. 따로 복도 같은 거 만들어서 방 수에 따라 복도가 늘어나는 등), 자유 방(모든 기능을 사용 가능), 마당(농구장, 축구장 등등), 게임-무기 방(이건 방장이 승인 해야 열림. 총 같은 것을 쓸 수 있음. 거기서는 간단한 픽맨, 공룡 게임 같은 것을 할 수 있음), 자는 방(말 그대로 수면 취침이 되는 방), 거실(이건 밥 먹고, 요리 하고, 소파에서 점프도 가능하고 자유럽게 소통도 가능하고 등등) 등등을 집+회사처럼 짜줘.(엔진은 godot, 3d 툴은 blenderMCP(연결 됨. 포트 9876 임))
